GitHub Actions — автоматизация

GitHub Actions выполняет задачи автоматически при определённых событиях — например при каждом git push. Мы используем его для автоматической публикации сайта.

Аналогия: GitHub Actions — это помощник которому ты дал инструкцию заранее. Ты отправил файлы (git push) — помощник автоматически опубликовал сайт. Ты занимаешься своим делом, он своим.

Структура workflow файла

YAML .github/workflows/pages.yml 
name: Deploy to GitHub Pages
# название — только для читаемости

on:
  push:
    branches:
      - main
# когда запускать — при каждом push в ветку main

permissions:
  contents: read
  pages: write
  id-token: write
# разрешения — что этому скрипту разрешено делать
# pages: write — разрешить публикацию на GitHub Pages

jobs:
  deploy:
    runs-on: ubuntu-latest
    # runs-on — на какой виртуальной машине выполнять
    # ubuntu-latest — GitHub предоставляет бесплатно

    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    # environment — окружение деплоя, сюда пишется URL сайта

    steps:
      - name: Checkout
        uses: actions/checkout@v4
        # скачать репозиторий на виртуальную машину

      - name: Setup Pages
        uses: actions/configure-pages@v4
        with:
          enablement: true
        # настроить GitHub Pages

      - name: Upload artifact
        uses: actions/upload-pages-artifact@v3
        with:
          path: ./frontend
        # упаковать папку frontend/ для публикации

      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v4
        # опубликовать на GitHub Pages

Что происходит после git push

BASH Полный цикл деплоя 
1. git push                          # ты отправляешь изменения
2. GitHub читает pages.yml           # находит инструкцию
3. Запускает виртуальную машину Ubuntu
4. actions/checkout — скачивает репозиторий
5. actions/configure-pages — настраивает Pages
6. actions/upload-pages-artifact — упаковывает frontend/
7. actions/deploy-pages — публикует на сайт
8. Сайт обновлён за 1-2 минуты
refusing to allow — нет прав на workflow
refusing to allow a Personal Access Token to update workflow

Причина: токен не имеет галочки workflow в правах.

Решение

GitHub → Settings → Developer settings → Personal access tokens → найди токен → добавь галочку workflow → сохрани новый токен → обнови в системе через GIT_TERMINAL_PROMPT=1 GIT_ASKPASS="" git push

Запомни: uses: actions/checkout@v4 — это готовые блоки от GitHub, как кубики Lego. Не пишем всё с нуля — берём готовое и собираем pipeline из блоков.

CI/CD pipeline — три джоба

Один workflow может содержать несколько джобов. Они могут работать параллельно или по очереди. Мы построили цепочку: test → build → deploy.

Аналогия: Это как сборочный конвейер на заводе. Сначала ОТК проверяет деталь (test). Параллельно другой рабочий красит корпус (build). Только если оба справились — деталь идёт в упаковку (deploy). Один брак — вся линия стоит.
YAML .github/workflows/pages.yml — три джоба 
jobs:

  test:                          # джоб 1 — запускаем тесты
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - run: |
          cd backend
          pip install -r requirements.txt
          pip install pytest httpx
      - run: |
          cd backend
          pytest tests/ -v         # -v = verbose, показывает каждый тест

  build:                         # джоб 2 — билдим Docker образ
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t portfolio-backend ./backend

  deploy:                        # джоб 3 — деплоим на GitHub Pages
    runs-on: ubuntu-latest
    needs: [test, build]         # ← КЛЮЧЕВОЕ: ждать test И build
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/configure-pages@v4
        with:
          enablement: true
      - uses: actions/upload-pages-artifact@v3
        with:
          path: ./frontend
      - id: deployment
        uses: actions/deploy-pages@v4

needs: — зависимость между джобами

YAML Как работает needs: 
needs: [test, build]

# Если test упал  → deploy НЕ запускается
# Если build упал → deploy НЕ запускается
# Оба прошли      → deploy запускается

# build и test работают ПАРАЛЛЕЛЬНО (оба без needs)
# deploy ждёт пока оба закончат
Зачем это нужно: Мы намеренно сломали тест (написали "broken" вместо "healthy") и убедились: test стал красным, deploy не запустился вообще. Сломанный код не попадёт на сайт — это главный принцип CI/CD.

pytest — тесты для FastAPI

PYTHON backend/tests/test_main.py 
from fastapi.testclient import TestClient
from app.main import app

client = TestClient(app)    # имитирует браузер, не нужен реальный сервер

def test_root():
    response = client.get("/")
    assert response.status_code == 200       # проверяем HTTP код
    assert response.json()["status"] == "ok" # проверяем содержимое ответа

def test_health():
    response = client.get("/health")
    assert response.status_code == 200
    assert response.json()["status"] == "healthy"
BASH Запустить тесты локально 
cd backend
pytest tests/ -v

# Вывод при успехе:
# PASSED tests/test_main.py::test_root
# PASSED tests/test_main.py::test_health
# 2 passed in 0.31s

# Вывод при ошибке:
# FAILED tests/test_main.py::test_health
# AssertionError: assert 'healthy' == 'broken'

concurrency — защита от конфликтов

Если два push прилетают подряд, два pipeline запускаются одновременно и оба пытаются задеплоить — возникает конфликт артефактов. Решение: concurrency.

YAML Concurrency в workflow 
concurrency:
  group: pages              # имя группы — все запуски с этим именем конкурируют
  cancel-in-progress: true  # если новый пуш пришёл — отменить старый запуск

# Результат: всегда деплоится только ПОСЛЕДНИЙ пуш
# Старые запуски автоматически отменяются
Multiple artifacts uploaded — конфликт деплоя
Error: Multiple artifacts with the same name were uploaded

Причина: два pipeline запустились одновременно и оба создали артефакт github-pages.

Решение

Добавить блок concurrency: в начало workflow файла. Новый push отменит предыдущий запуск автоматически.
