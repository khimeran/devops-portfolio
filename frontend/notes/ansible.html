Ansible — автоматизация конфигурации

Ansible — инструмент для автоматического управления настройками серверов. Вместо того чтобы вручную настраивать каждый сервер по-очереди, ты описываешь в YAML файле что должно быть установлено и настроено — Ansible сам всё сделает на всех серверах.

Аналогия: Представь что у тебя 50 серверов и на каждый нужно установить nginx, создать пользователя и скопировать конфиг. Вручную — это 50 раз одно и то же. С Ansible — пишешь инструкцию один раз, запускаешь — готово на всех сразу.

Ключевые концепции

BASH Основные понятия 
Control node    — твой компьютер с которого запускается Ansible
Managed nodes   — серверы которыми управляет Ansible
Inventory       — список серверов (адреса, группы)
Playbook        — YAML файл с инструкциями что делать
Task            — одно конкретное действие (установить пакет, скопировать файл)
Role            — набор tasks сгруппированных по функции (nginx, postgres)
Module          — встроенный инструмент Ansible (apt, copy, service, template)

# Ansible не требует агента на серверах!
# Подключается по SSH — нужен только SSH доступ и Python на сервере

[production:children]

# [название_группы] — объединить серверы логически

# ansible_host — IP если имя не резолвится

Playbook — главный файл инструкций

YAML playbook.yml — установить и запустить nginx 
---
# --- обязательно в начале YAML файла

- name: Настроить веб-серверы
  # name — описание для читаемости

  hosts: webservers
  # hosts — на каких серверах выполнять (из inventory)

  become: true
  # become: true — выполнять с правами root (sudo)

  tasks:
    # tasks — список действий по порядку

    - name: Установить nginx
      apt:
        name: nginx
        state: present
        update_cache: true
      # apt — модуль для управления пакетами (Ubuntu/Debian)
      # state: present — убедиться что установлен
      # state: absent — убедиться что удалён

    - name: Скопировать конфиг nginx
      copy:
        src: files/nginx.conf
        dest: /etc/nginx/nginx.conf
        owner: root
        mode: '0644'
      # copy — скопировать файл с control node на сервер

    - name: Запустить и включить nginx
      service:
        name: nginx
        state: started
        enabled: true
      # service — управление системными сервисами
      # enabled: true — запускать автоматически при загрузке

    - name: Создать пользователя deploy
      user:
        name: deploy
        shell: /bin/bash
        groups: sudo
      # user — управление пользователями

Запуск Ansible

BASH Основные команды 
# Проверить подключение ко всем серверам:
ansible all -m ping -i inventory/hosts
# all — все серверы из inventory
# -m ping — использовать модуль ping
# -i — указать файл inventory

# Запустить playbook:
ansible-playbook -i inventory/hosts playbook.yml

# Режим проверки (ничего не менять, только показать что будет):
ansible-playbook -i inventory/hosts playbook.yml --check

# Запустить только на конкретной группе:
ansible-playbook -i inventory/hosts playbook.yml --limit webservers

# Запустить только определённые задачи (по тегу):
ansible-playbook -i inventory/hosts playbook.yml --tags nginx

# Вывод: changed=2 — что изменилось
#        ok=3     — что уже было в нужном состоянии
#        failed=0 — что не получилось

Идемпотентность — главный принцип

Идемпотентность — запусти playbook 10 раз, результат всегда одинаковый. Если nginx уже установлен — Ansible не будет устанавливать снова. Это безопасно: можно запускать повторно без риска сломать то что работает. state: present означает "убедись что есть", а не "установи заново".
UNREACHABLE — не может подключиться к серверу
UNREACHABLE! => {"msg": "Failed to connect to the host via ssh"}

Причина: неверный IP, закрытый порт SSH, неверный ключ, или сервер выключен.

Диагностика
ssh ubuntu@192.168.1.10               # проверить SSH вручную
ansible all -m ping -vvv -i hosts     # подробный вывод (-vvv)
# в inventory проверить ansible_user, ansible_port, ansible_host
Changed: 0 но ошибки нет — ничего не применилось

Причина: задача уже в нужном состоянии (идемпотентность). Это нормально — Ansible не меняет то что уже правильно.

Установка агента на сервер — правильно

Задача, которая на проде встречается чаще всех остальных: раскатать на весь парк агента — мониторинга (node_exporter, zabbix-agent2), сбора логов (promtail, filebeat), конфиг-менеджмента (puppet-agent), бэкапа. Выглядит как «скачай и запусти», но именно здесь ломают идемпотентность и получают парк из машин-снежинок.

Антипаттерны установки агента — что именно ломается
Как делаютЧто ломаетсяКак надо
shell: curl … | bash Не идемпотентно — выполняется каждый прогон, всегда changed. Что скрипт сделал внутри, никто не знает. Нечего откатывать и нечем проверить Пакет из репозитория вендора или unarchive с creates
get_url без checksum Приедет что угодно: обрезанный файл, страница ошибки прокси, подменённый бинарь Всегда указывать checksum: sha256:… с сайта релиза
shell: nohup /usr/local/bin/agent & Переживёт ровно до первого ребута. Никакого автозапуска, рестарта и логов systemd-юнит из template + service: enabled=true
Версия latest Завтра на 300 машинах разные версии → «метрика пропала, но не у всех» Версия — переменная роли, обновление = коммит в git
Забыли enabled: true Сервер перезагрузили — агент не поднялся. Классика state: started и enabled: true
Агент слушает 0.0.0.0 без firewall Метрики (а иногда и API) торчат наружу для всех желающих Rich-rule только для источников, которым порт нужен
Нет проверки в конце «Вроде поставили»: сервис активен, но метрика не отдаётся wait_for порт + uri на /metrics с failed_when
ПРИНЦИПЫ 7 правил правильной установки агента 
1. ВЕРСИЯ ФИКСИРОВАНА переменной роли. Обновление = смена переменной в git.
2. Источник — репозиторий вендора (dnf/apt) ИЛИ бинарь с ПРОВЕРКОЙ checksum.
3. Отдельный системный пользователь, shell=/sbin/nologin, без домашки и sudo.
4. Управляет systemd: unit из шаблона, daemon-reload через handler.
5. Конфиг — из template, с notify на restart. Правка конфига = рестарт, и только тогда.
6. Порт открыт ТОЛЬКО источникам, которым он нужен (не 0.0.0.0 всему миру).
7. В конце — ПРОВЕРКА: сервис активен и метрика реально отдаётся.
   Установка без проверки = «вроде поставили».
YAML Способ 1 — пакет из репозитория вендора (если он есть — берём его) 
- name: GPG-ключ репозитория Zabbix
  ansible.builtin.rpm_key:
    key: https://repo.zabbix.com/RPM-GPG-KEY-ZABBIX-A14FE591
    state: present

- name: Репозиторий Zabbix
  ansible.builtin.dnf:
    name: https://repo.zabbix.com/zabbix/7.0/rhel/9/x86_64/zabbix-release-7.0-2.el9.noarch.rpm
    state: present
    disable_gpg_check: false

- name: Агент нужной версии (⭐ версия зафиксирована!)
  ansible.builtin.dnf:
    name: "zabbix-agent2-{{ zabbix_agent_version }}"
    state: present
  notify: restart zabbix-agent2

- name: Конфиг из шаблона
  ansible.builtin.template:
    src: zabbix_agent2.conf.j2
    dest: /etc/zabbix/zabbix_agent2.conf
    owner: root
    group: zabbix
    mode: '0640'
  notify: restart zabbix-agent2

- name: Сервис запущен и в автозагрузке
  ansible.builtin.service:
    name: zabbix-agent2
    state: started
    enabled: true
TREE Способ 2 — бинарь без пакета. Полная роль node_exporter 
roles/node_exporter/
├── defaults/main.yml                 переменные (версия, порт, кто скрейпит)
├── tasks/main.yml                    установка
├── templates/node_exporter.service.j2 systemd-юнит
└── handlers/main.yml                 daemon-reload + restart
YAML defaults/main.yml — всё настраиваемое здесь 
---
node_exporter_version: "1.8.2"
node_exporter_port: 9100
node_exporter_user: node_exporter
node_exporter_install_dir: /opt/node_exporter
# ⭐ checksum берётся с страницы релиза (sha256sums.txt), а не выдумывается
node_exporter_checksum: "sha256:6809dd0b3ec45fb6e59d0a4b0f2e0f0c69b3a3a1e6e3a9d2b1f0a7c5d4e3f2a1"
node_exporter_allowed_sources:          # кому разрешаем скрейп
  - "10.0.0.5"                          # prometheus-01
  - "10.0.0.6"
YAML tasks/main.yml — разбор по шагам 
---
- name: Системный пользователь для агента
  ansible.builtin.user:
    name: "{{ node_exporter_user }}"
    system: true                        # ⭐ UID из системного диапазона
    shell: /sbin/nologin                # ⭐ под ним нельзя залогиниться
    createhome: false

- name: Каталог установки
  ansible.builtin.file:
    path: "{{ node_exporter_install_dir }}"
    state: directory
    owner: root
    mode: '0755'

- name: Скачать и распаковать релиз
  ansible.builtin.unarchive:
    src: "https://github.com/prometheus/node_exporter/releases/download/v{{ node_exporter_version }}/node_exporter-{{ node_exporter_version }}.linux-amd64.tar.gz"
    dest: "{{ node_exporter_install_dir }}"
    remote_src: true                    # качает сам сервер, а не control node
    checksum: "{{ node_exporter_checksum }}"   # ⭐ битый/подменённый файл не приедет
    creates: "{{ node_exporter_install_dir }}/node_exporter-{{ node_exporter_version }}.linux-amd64/node_exporter"
    # ⭐ creates = идемпотентность: файл на месте → задача пропускается,
    #    а не качает 20 МБ каждые полчаса

- name: Симлинк на текущую версию
  ansible.builtin.file:
    src: "{{ node_exporter_install_dir }}/node_exporter-{{ node_exporter_version }}.linux-amd64/node_exporter"
    dest: /usr/local/bin/node_exporter
    state: link
  notify: restart node_exporter         # ⭐ сменили версию → рестарт

- name: systemd-юнит
  ansible.builtin.template:
    src: node_exporter.service.j2
    dest: /etc/systemd/system/node_exporter.service
    owner: root
    mode: '0644'
  notify:
    - reload systemd                    # ⭐ порядок важен: сначала daemon-reload,
    - restart node_exporter             #    потом рестарт

- name: Сервис запущен и в автозагрузке
  ansible.builtin.service:
    name: node_exporter
    state: started
    enabled: true                       # ⭐ переживёт ребут

- name: Открыть порт только для Prometheus
  ansible.posix.firewalld:
    rich_rule: "rule family=ipv4 source address={{ item }} port port={{ node_exporter_port }} protocol=tcp accept"
    permanent: true
    immediate: true
    state: enabled
  loop: "{{ node_exporter_allowed_sources }}"

# ── ПРИЁМКА: без неё установка не считается сделанной ────────────────
- name: Порт слушается
  ansible.builtin.wait_for:
    port: "{{ node_exporter_port }}"
    host: 127.0.0.1
    timeout: 15

- name: Метрики реально отдаются
  ansible.builtin.uri:
    url: "http://127.0.0.1:{{ node_exporter_port }}/metrics"
    return_content: true
  register: metrics
  failed_when: "'node_cpu_seconds_total' not in metrics.content"
  changed_when: false                   # ⭐ проверка НЕ является изменением
JINJA2 + YAML Шаблон юнита и handlers 
# templates/node_exporter.service.j2
[Unit]
Description=Prometheus Node Exporter
After=network-online.target
Wants=network-online.target

[Service]
User={{ node_exporter_user }}
ExecStart=/usr/local/bin/node_exporter --web.listen-address=:{{ node_exporter_port }}
Restart=always
RestartSec=5
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true

[Install]
WantedBy=multi-user.target

# handlers/main.yml
---
- name: reload systemd
  ansible.builtin.systemd:
    daemon_reload: true

- name: restart node_exporter
  ansible.builtin.service:
    name: node_exporter
    state: restarted
BASH Раскатка и проверка идемпотентности 
# 1) Сначала вхолостую — что вообще произойдёт:
ansible-playbook -i inventory/prod site.yml --tags node_exporter --check --diff

# 2) Одна машина (канарейка):
ansible-playbook -i inventory/prod site.yml --tags node_exporter --limit web01

# 3) ⭐⭐ ГЛАВНЫЙ ТЕСТ: повторный прогон должен дать changed=0
ansible-playbook -i inventory/prod site.yml --tags node_exporter --limit web01
#    PLAY RECAP: ok=9  changed=0  failed=0
#    ⭐ changed НЕ ноль на втором прогоне = роль НЕ идемпотентна, чинить.

# 4) Весь парк, пачками по 20 машин, чтобы не положить сеть/репозиторий:
ansible-playbook -i inventory/prod site.yml --tags node_exporter --forks 20

# 5) Проверить снаружи:
ansible all -i inventory/prod -m uri \
  -a "url=http://{{ ansible_host }}:9100/metrics status_code=200" --one-line
Отдельный случай — установка Puppet-агента через Ansible. Очень частая прод-схема: Ansible один раз ставит и регистрирует агента (репозиторий, csr_attributes.yaml с ролью ноды, первый прогон с --waitforcert), дальше машину держит уже Puppet. Полный playbook разобран в разделе IaC → Ansible + Puppet.

Puppet — тот же конфиг-менеджмент, но с агентами

Второй по популярности инструмент управления конфигурацией (в энтерпрайзе и банках — часто первый). Решает ту же задачу, что Ansible — «приведи 100 серверов к описанному состоянию», — но противоположным способом.

КОНЦЕПТ Push vs Pull — главное различие с Ansible 
Ansible = PUSH: ты запускаешь playbook со своей машины, он идёт по SSH
          на серверы и приводит их в порядок. Агентов нет. Разовый визит.

Puppet  = PULL: на каждом сервере живёт АГЕНТ (демон puppet), который сам
          раз в 30 минут ходит к Puppet-серверу: «какой я должен быть?» —
          получает каталог и приводит себя в порядок.

Следствия pull-модели:
+ самолечение: руками поменял конфиг на сервере → через 30 минут агент
  вернул как в манифесте (дрейф конфигурации невозможен в принципе)
+ масштаб: 10 000 серверов сами себя обслуживают, никто их не обходит
- нужен агент на каждой машине и центральный сервер (сложнее вход)
- изменения не мгновенные (жди цикла агента или пинай вручную)
CONFIG Манифест .pp — декларативный DSL 
# Puppet описывает СОСТОЯНИЕ (что должно быть), а не шаги (что сделать):
package { 'nginx':
  ensure => installed,
}
service { 'nginx':
  ensure  => running,
  enable  => true,
  require => Package['nginx'],   # зависимость: сначала пакет, потом сервис
}
file { '/etc/nginx/nginx.conf':
  source => 'puppet:///modules/nginx/nginx.conf',
  notify => Service['nginx'],    # файл поменялся → перезапустить сервис
}

# Идемпотентность та же, что у Ansible: 10 запусков = один результат.
# facter — сборщик фактов о машине (ОС, IP, память), аналог ansible facts.
Формула для собеса: Ansible — agentless push по SSH, просто начать, хорош для оркестрации и разовых раскаток. Puppet — агентный pull с центральным сервером, хорош там, где тысячи машин должны постоянно сами держать себя в заданном состоянии. Не «кто лучше», а разные модели доставки одного и того же.
