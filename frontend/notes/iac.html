🏗 IaC — Infrastructure as Code

«Инфраструктура как код» — описание серверов, сетей, балансировщиков и баз в виде текстовых файлов в git, вместо кликов в админке. Любое изменение прода — это PR с ревью. Главная цель — повторяемость: один набор файлов разворачивается одинаково в dev, staging, prod.

Раздел состоит из трёх подразделов: Terraform (создать инфраструктуру), Ansible (настроить её push-моделью) и Puppet (держать её в заданном состоянии pull-моделью, с агентами).

Три инструмента: кто за что отвечает

Их постоянно путают и пытаются сравнивать «кто лучше». На проде они живут слоями и делают разную работу.

СЛОИ Кто на каком этапе жизни сервера 
СЛОЙ 1 — PROVISIONING (чего ещё нет)          → Terraform
   создать VM, диск, сеть, security group, DNS-запись, managed-БД,
   S3-бакет, балансировщик. Работает через API облака.

СЛОЙ 2 — BOOTSTRAP (первое касание живой машины) → cloud-init / Ansible
   поставить агента, положить ключи, зарегистрировать ноду,
   подписать сертификат. Один раз в жизни сервера.

СЛОЙ 3 — CONFIGURATION (то, что уже есть)     → Ansible ИЛИ Puppet
   пакеты, пользователи, конфиги, сервисы, приложения.
   Ansible — push: пришёл по SSH, сделал, ушёл.
   Puppet  — pull: агент сам каждые 30 мин приводит машину к манифесту.

СЛОЙ 4 — ДЕПЛОЙ ПРИЛОЖЕНИЯ                     → CI/CD (Actions/Jenkins)
   выкатка новой версии кода поверх настроенной машины.
СРАВНЕНИЕ Terraform vs Ansible vs Puppet — одной таблицей 
                    Terraform        Ansible            Puppet
Что делает         создаёт ресурсы  настраивает ОС     настраивает ОС
Модель             API облака       PUSH по SSH        PULL агентом
Агент на сервере   не нужен         не нужен           нужен (демон)
Центральный сервер не нужен*        не нужен           нужен (puppetserver)
Язык               HCL (.tf)        YAML (.yml)        Puppet DSL (.pp)
Помнит состояние   да, tfstate      нет                да, каталог + PuppetDB
Когда применяется  когда запустил   когда запустил     каждые 30 мин сам
Дрейф конфигурации не лечит         лечит при запуске  лечит сам, всегда
Порог входа        средний          низкий             высокий
Где чаще встретишь облака, k8s      всё подряд         банки, телеком, 1000+ VM

* state всё равно хранят централизованно (S3 + lock).
Как отвечать на собесе: «Terraform создаёт то, чего ещё нет, и помнит это в state. Ansible и Puppet приводят уже существующие машины к описанному состоянию — разница в модели доставки: push по SSH против pull агентом. На проде обычно связка: Terraform поднял VM → cloud-init поставил агента → Puppet/Ansible держит конфигурацию → CI/CD катает релизы приложения.»

Terraform — жизненный цикл

HashiCorp, написан на Go в 2014-м. Multi-cloud — один синтаксис работает в AWS, GCP, Azure, Yandex Cloud, локальном Docker'е. С 2023-го у HashiCorp поменялась лицензия (BSL), сообщество форкнуло в OpenTofu — полностью совместимый, более «свободный». Синтаксис идентичный, команда tofu вместо terraform.

ДО vs ПОСЛЕ Зачем оно вообще 
ДО Terraform:
   - Клики в AWS-консоли: EC2, RDS, Load Balancer, VPC...
   - Записываю шаги в Confluence (если не забыл)
   - Через неделю "сделай dev" — кликаю снова, получается ИНАЧЕ
   - Друг разворачивает по моей инструкции — снова ИНАЧЕ

ПОСЛЕ Terraform:
   - Пишу .tf-файлы → коммитю в git
   - terraform apply разворачивает ТОЧНО так же где угодно
   - Любое изменение = PR с ревью
   - Откат — git revert + terraform apply
   - Поднять dev на копии prod = git checkout dev-branch + apply
BASH init → plan → apply → destroy 
terraform init      # ⭐ скачать провайдеры (раз в проекте)
                    # создаёт .terraform/ и .terraform.lock.hcl

terraform plan      # ⭐ "что будет?" — dry-run, ничего не делает
                    # ВСЕГДА смотри, особенно "destroy" в плане

terraform apply     # сделать
                    # спросит "yes" — нужно вписать ПОЛНОСТЬЮ
                    # -auto-approve = без вопросов (для CI)

terraform destroy   # снести всё, что terraform создал
                    # ⚠️ опасно на проде — снесёт всю инфру

terraform fmt       # причесать форматирование (в CI: fmt -check)
terraform validate  # проверить синтаксис без обращения к облаку

Terraform — HCL: ресурсы, ссылки, интерполяция

HCL main.tf — минимальный рабочий пример на Docker 
terraform {
  required_providers {
    docker = {
      source  = "kreuzwerker/docker"
      version = "~> 3.0"
    }
  }
}

provider "docker" {}

resource "docker_image" "nginx" {
  name         = "nginx:alpine"
  keep_locally = false
}

resource "docker_container" "web" {
  image = docker_image.nginx.image_id
  name  = "tf-web"
  ports {
    internal = 80
    external = 8090
  }
}
РАЗБОР Что значит каждый блок 
terraform { required_providers { ... } }
   ⭐ корневой блок про сам terraform
      какие провайдеры нужны и каких версий
      version = "~> 3.0" — любая 3.x, но не 4.0 (защита от breaking)

provider "docker" {}
   инициализация провайдера, {} = дефолты

resource "тип" "локальное_имя" { ... }
   тип        — что создаём (docker_container, aws_instance, ...)
   локальное_имя — по нему ссылаемся в коде
   { ... }    — атрибуты ресурса

image = docker_image.nginx.image_id
   ⭐ ссылка на ДРУГОЙ ресурс
   синтаксис: ТИП.ИМЯ.АТРИБУТ
   terraform автоматически поймёт зависимость (image создаётся ПЕРВЫМ)
HCL Интерполяция: внутри двойных кавычек ${...} — это выражение 
"http://localhost:${var.external_port}"     ← подставится 8090
"backend-${var.environment}"                ← "backend-prod"
"${path.module}/scripts/init.sh"            ← абсолютный путь к файлу

# Это как f-strings в Python: f"http://localhost:{port}"

Terraform — state, главная концепция

terraform.tfstate — JSON-файл, в котором terraform запомнил, какие реальные ресурсы создал и какие у них ID в облаке. При каждом plan terraform сравнивает три вещи:

FLOW Как terraform решает «что изменилось» 
1. Что в твоих .tf-файлах    ← ЖЕЛАЕМОЕ
2. Что в terraform.tfstate    ← что я знаю, что создал
3. Что РЕАЛЬНО в облаке       ← API запрос

# Plan = разница между 1 и (2+3).
⚠️ Грабли state'а на проде:
• В state могут быть секреты (пароли БД, ключи) → в git НЕ кладут.
• Работают двое — нужен remote state (S3 + DynamoDB-lock, Terraform Cloud), иначе apply одновременно сломает инфру.
• Случайно удалил state — terraform забыл, что создал. Нужен terraform import для каждого ресурса вручную.
• terraform state list / state show / state rm — команды для управления.
BASH Управление state вручную 
terraform state list                       # список всех ресурсов в state
terraform state show docker_container.web  # подробности по ресурсу

# Самое частое — "забудь про этот ресурс":
terraform state rm docker_image.nginx
   # удаляет из state, в реальности НЕ трогает
   # полезно когда ресурс используется кем-то ещё и destroy падает

# Импортировать существующий ресурс в state:
terraform import docker_container.web CONTAINER_ID
   # нужно если ресурс уже создан руками, а ты хочешь
   # начать им управлять через terraform

terraform state mv docker_container.web docker_container.frontend
   # переименовать ресурс БЕЗ пересоздания (иначе -/+ destroy and recreate)
SYMBOLS Как читать plan — что значит каждый символ 
+ create                    создать новый ресурс
- destroy                   удалить
~ update in-place           поменять атрибут БЕЗ пересоздания
-/+ destroy and recreate    ⚠️ снести и создать заново
                              (когда атрибут "forces replacement")

# forces replacement — в комментарии плана:
~ external = 8090 -> 8091 # forces replacement

# На проде "forces replacement" на БД = потеря данных!
# ВСЕГДА читай plan, особенно ищи знак "-" там, где не ждёшь.

# Идемпотентность: повторный apply без изменений →
Apply complete! Resources: 0 added, 0 changed, 0 destroyed.

# Альтернативы:

Terraform — модули и структура прод-репозитория

Модуль — папка с .tf-файлами, которую вызывают как функцию: передали переменные — получили ресурсы и outputs. Всё, что делаешь дважды (сервер, сеть, вся среда), выносится в модуль.

│   ├── network/
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   └── outputs.tf
│   ├── vm/
│   └── postgres/
├── envs/                     ← окружения: у каждого свой state
│   ├── dev/
│   │   ├── main.tf           ← вызовы модулей
│   │   ├── backend.tf        ← где лежит state этого окружения

│   ├── stage/
│   └── prod/
│       ├── main.tf
│       ├── backend.tf
│       └── terraform.tfvars
└── .github/workflows/terraform.yml   ← plan на PR, apply на merge

Terraform — backend, workspaces, окружения

HCL backend.tf — state в S3 с блокировкой 
terraform {
  backend "s3" {
    bucket         = "company-tf-state"
    key            = "prod/infra.tfstate"   # ⭐ у каждого окружения свой key
    region         = "ru-central1"
    dynamodb_table = "tf-locks"             # ⭐ lock: двое одновременно не применят
    encrypt        = true
  }
}

# Почему lock критичен: без него два apply одновременно перезапишут
# state друг друга → terraform "потеряет" половину инфраструктуры.

# Посмотреть/снять зависший лок (например, упал CI-раннер):
# terraform force-unlock LOCK_ID    ← только когда точно уверен
BASH Workspaces — второй способ разделить окружения 
terraform workspace new dev
terraform workspace new prod
terraform workspace select prod
terraform workspace list      # * помечает текущий

# В коде текущий workspace виден как terraform.workspace:
name = "web-${terraform.workspace}"

# Когда что выбирать:
#   папки envs/*  — разные размеры и состав ресурсов (prod ≠ dev). Прод-стандарт.
#   workspaces    — та же инфра, отличается только размером/количеством.
# Главная опасность workspaces: одна ошибка select — и apply ушёл в прод.

Terraform — count, for_each, data, lifecycle

HCL Циклы, чтение чужих ресурсов и защита от сноса 
# COUNT — «сделай N штук»
resource "docker_container" "web" {
  count = 3
  name  = "web-${count.index}"     # web-0, web-1, web-2
}
# Минус: удалил средний — terraform пересоздаст все последующие (сдвиг индексов).

# FOR_EACH — «сделай по элементу на каждый ключ» (безопаснее count)
resource "docker_container" "web" {
  for_each = {
    web-a = 8081
    web-b = 8082
  }
  name = each.key
  ports { internal = 80, external = each.value }
}
# Удаление web-a не трогает web-b: ключ, а не индекс.

# DATA SOURCE — read-only «посмотри, что уже есть в облаке»
data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"]
}
# использование: ami = data.aws_ami.ubuntu.id

# LIFECYCLE — управление поведением ресурса
lifecycle {
  prevent_destroy       = true      # ⭐ на прод-БД: apply упадёт, но не снесёт
  create_before_destroy = true      # новый создаётся ДО удаления старого (без даунтайма)
  ignore_changes        = [tags]    # это поле правят руками — не воюй с ним
}

Terraform → Ansible/Puppet: передача эстафеты

Terraform создал голую VM. Дальше её кто-то должен настроить. Три рабочих способа — от худшего к лучшему.

HCL Способ 1 (антипаттерн): remote-exec прямо из terraform 
resource "null_resource" "setup" {
  provisioner "remote-exec" {
    inline = ["dnf install -y nginx"]     # ⛔ так не делают
  }
}
# Почему плохо:
#   - не идемпотентно: terraform не знает, что там внутри произошло
#   - падение посреди скрипта → ресурс "tainted", state рассинхронизирован
#   - нет отката, нет проверки, нет повторного применения
# Сам HashiCorp пишет: provisioners — last resort.
HCL Способ 2: cloud-init — сервер сам ставит агента при первом старте 
# envs/prod/main.tf
resource "yandex_compute_instance" "web" {
  name = "web-01"
  metadata = {
    user-data = templatefile("${path.module}/cloud-init.yaml", {
      puppet_server = "puppet.example.com"
      pp_role       = "webserver"
      env           = "prod"
    })
  }
}
YAML cloud-init.yaml — bootstrap Puppet-агента одной машиной 
#cloud-config
write_files:
  # ⭐ trusted facts: сервер узнает роль ноды из САМОГО сертификата,
  #    подделать нельзя — это основа автоклассификации в Puppet
  - path: /etc/puppetlabs/puppet/csr_attributes.yaml
    content: |
      extension_requests:
        pp_role: ${pp_role}
        pp_environment: ${env}

runcmd:
  - rpm -Uvh https://yum.puppet.com/puppet8-release-el-9.noarch.rpm
  - dnf install -y puppet-agent
  - /opt/puppetlabs/bin/puppet config set server ${puppet_server} --section main
  - /opt/puppetlabs/bin/puppet agent -t --waitforcert 60
  - systemctl enable --now puppet

# Дальше машина живёт сама: каждые 30 минут забирает каталог с сервера.
# Terraform к ней больше не прикасается.
BASH Способ 3: terraform output → динамический inventory Ansible 
# В terraform:
output "web_ips" { value = module.web[*].public_ip }

# В CI после apply:
terraform output -json web_ips \
  | jq -r '.[] | "\(.) ansible_user=deploy"' > inventory/prod_web.ini

ansible-playbook -i inventory/prod_web.ini site.yml --limit webservers

# Ещё чище: плагин динамического inventory облака —
# ansible читает список машин прямо из API, без промежуточных файлов.
Итог по Terraform: 4 команды (init → plan → apply → destroy). Plan читать ВСЕГДА, особенно искать «destroy» там, где не ждёшь. State — JSON с тем, что terraform знает; в git НЕ кладут (секреты), на проде — remote backend (S3 + lock). Модули в modules/ без хардкода, различия сред — в envs/*/terraform.tfvars. Настройку ОС terraform НЕ делает: его работа заканчивается на «машина создана и агент поставлен».

Ansible + Puppet: не «или», а «и»

Частая прод-схема в крупных конторах: Ansible ставит и регистрирует агента, Puppet дальше держит конфигурацию. Каждый делает то, что умеет лучше.

YAML playbooks/bootstrap_puppet.yml — разовая раскатка агента 
---
- name: Bootstrap Puppet-агента на новые машины
  hosts: new_nodes
  become: true
  vars:
    puppet_server: puppet.example.com

  tasks:
    - name: Репозиторий Puppet 8
      ansible.builtin.dnf:
        name: https://yum.puppet.com/puppet8-release-el-9.noarch.rpm
        state: present
        disable_gpg_check: true

    - name: Пакет агента
      ansible.builtin.dnf:
        name: puppet-agent
        state: present

    - name: Роль ноды в csr_attributes (trusted facts, подделать нельзя)
      ansible.builtin.copy:
        dest: /etc/puppetlabs/puppet/csr_attributes.yaml
        content: |
          extension_requests:
            pp_role: {{ node_role }}
            pp_environment: {{ node_env | default('production') }}
        mode: '0640'

    - name: Указать сервер
      ansible.builtin.command:
        cmd: /opt/puppetlabs/bin/puppet config set server {{ puppet_server }} --section main
      changed_when: false

    - name: Первый прогон — заказать сертификат и дождаться подписи
      ansible.builtin.command:
        cmd: /opt/puppetlabs/bin/puppet agent -t --waitforcert 60
      register: r
      failed_when: r.rc not in [0, 2]     # ⭐ rc=2 у puppet значит "были изменения", это НЕ ошибка
      changed_when: r.rc == 2

    - name: Демон агента включён
      ansible.builtin.service:
        name: puppet
        state: started
        enabled: true
Кто где сильнее: Ansible — разовые операции и оркестрация по порядку (выкатить релиз на 5 машин по очереди, накатить патчи, эвакуировать ноду). Puppet — непрерывное удержание состояния: правил конфиг руками — через 30 минут он вернулся как в git. Поэтому Ansible часто зовут «руками админа», а Puppet — «иммунной системой парка».

Puppet — архитектура и цикл агента

Puppet — система управления конфигурацией с агентами. Ты описываешь на своём DSL, каким должен быть сервер; агент на каждой машине сам, без твоего участия, приводит машину к этому описанию. Раз в 30 минут. Вечно.

КОНЦЕПТ Push (Ansible) vs Pull (Puppet) 
Ansible = PUSH: ты запускаешь playbook со своей машины, он идёт по SSH
          на серверы и приводит их в порядок. Агентов нет. Разовый визит.

Puppet  = PULL: на каждом сервере живёт АГЕНТ (демон puppet), который сам
          раз в 30 минут ходит к Puppet-серверу: «какой я должен быть?» —
          получает каталог и приводит себя в порядок.

Следствия pull-модели:
+ самолечение: руками поменял конфиг на сервере → через 30 минут агент
  вернул как в манифесте (дрейф конфигурации невозможен в принципе)
+ масштаб: 10 000 серверов сами себя обслуживают, никто их не обходит
+ новая машина сама себя настраивает, как только получила сертификат
- нужен агент на каждой машине и центральный сервер (сложнее вход)
- изменения не мгновенные (жди цикла агента или пинай вручную)
FLOW Что происходит за один прогон агента — 6 шагов 
1. FACTS. Агент запускает facter и собирает факты о себе:
   ОС, версия, IP, память, диски, виртуализация, hostname, кастомные факты.
   Это ДАННЫЕ О МАШИНЕ, которые уедут на сервер.

2. ЗАПРОС. Агент идёт на puppetserver (порт 8140/tcp, mTLS по сертификатам)
   и отдаёт: «я web01.example.com, вот мои факты, дай каталог».

3. КОМПИЛЯЦИЯ. Сервер:
   - определяет, КАКИЕ КЛАССЫ у этой ноды (site.pp / Hiera-классификация)
   - берёт для них данные из Hiera, подставляя факты в пути иерархии
   - выполняет манифесты .pp, рендерит шаблоны .epp
   - на выходе — КАТАЛОГ: плоский список ресурсов с зависимостями (JSON)

   ⭐ Важно: манифест выполняется НА СЕРВЕРЕ, на ноду едет уже результат.

4. ПРИМЕНЕНИЕ. Агент получает каталог и по каждому ресурсу спрашивает
   систему: «пакет nginx стоит?» — если да, ничего не делает (idempotent),
   если нет — ставит. И так по всем ресурсам, в порядке зависимостей.

5. ОТЧЁТ. Агент отправляет на сервер report: что изменилось, что упало,
   сколько заняло. Сервер складывает в PuppetDB / отчёты.

6. СОН до следующего runinterval (по умолчанию 1800 секунд = 30 минут).
СЛОВАРЬ Термины, без которых чужой прод не читается 
Манифест (.pp)   файл на языке Puppet с описанием ресурсов
Ресурс           единица «что должно быть»: package, file, service, user…
Класс            именованный набор ресурсов, который можно включить (include)
Модуль           папка со структурой: манифесты + файлы + шаблоны + метаданные
Каталог          скомпилированный под КОНКРЕТНУЮ ноду список ресурсов
Facter / факты   сведения о машине (os.family, networking.fqdn, memory…)
Hiera            хранилище ДАННЫХ (yaml), отдельно от кода
Profile          твоя обёртка над технологией: «наш nginx, настроенный по-нашему»
Role             набор профилей: «это веб-сервер». Нода получает ровно одну роль
PuppetDB         база фактов, каталогов и отчётов всех нод (по ней делают запросы)
r10k / Code Mgr  инструмент, который выкачивает код из git на puppetserver
Environment      окружение (production/dev) = ВЕТКА git = папка на сервере
certname         имя ноды в сертификате — её идентификатор во всей системе
trusted facts    факты из сертификата, которые нода НЕ может подделать

Puppet — язык: ресурсы, атрибуты, зависимости

Puppet описывает состояние, а не шаги. Единица описания — ресурс. Читается как предложение: «тип ресурса { заголовок: атрибут => значение }».

PUPPET Разбор синтаксиса по скобкам 
package { 'nginx':
  ensure => installed,
}
│         │         │
│         │         └─ значение атрибута
│         └─ атрибут (свойство желаемого состояния)
└─ ЗАГОЛОВОК ресурса (title) — уникальный идентификатор в каталоге

package   ← ТИП ресурса (что за сущность)
{ }       ← тело ресурса
'nginx'   ← title, после него ДВОЕТОЧИЕ

PUPPET ⭐ Как ВКЛЮЧАТЬ класс: include / resource-like / contain / require 
# 1) include — ОСНОВНОЙ способ. Параметры придут автоматически из Hiera.
include profile::web::nginx
include profile::base::users, profile::base::ssh    # можно списком
#   Можно писать сколько угодно раз в разных местах — дубликата НЕ будет.
#   ⭐ 95% кода на проде — именно include.

# 2) resource-like — параметры прямо в коде:
class { 'profile::web::nginx':
  server_name => 'shop.example.com',
  port        => 8080,
}
#   ⛔ ГЛАВНАЯ ЛОВУШКА: так класс можно объявить ТОЛЬКО ОДИН РАЗ во всём каталоге.
#   Второе объявление (даже include в другом месте) → ошибка:
#      "Duplicate declaration: Class[Profile::Web::Nginx] is already declared"
#   Поэтому на проде параметры кладут в Hiera и пишут include.

# 3) contain — «класс ВНУТРИ меня»: гарантия, что зависимости на мой класс
#    распространятся и на вложенный (иначе он «выпадает» из порядка).
class profile::app::shopfront {
  contain profile::app::shopfront::db
  contain profile::app::shopfront::web
  Class['profile::app::shopfront::db'] -> Class['profile::app::shopfront::web']
}

# 4) require — include + «сначала он, потом я»:
class profile::web::nginx {
  require profile::base::firewall
  ...
}

# 5) Порядок между классами на верхнем уровне:
Class['profile::base'] -> Class['profile::web::nginx'] -> Class['profile::app::shopfront']
PUPPET Defined type — «класс, который можно создать много раз» 
# Класс — синглтон: один на каталог. Нужно 5 виртуальных хостов nginx?
# Нужен defined type (define). Это «свой тип ресурса».

define profile::web::vhost (
  String       $server_name,
  Stdlib::Port $port     = 80,
  String       $root     = "/var/www/${title}",   # ⭐ $title = заголовок вызова
) {

    ensure  => file,

    notify  => Service['nginx'],
  }
}

  server_name => 'admin.example.com',

}

Шаблон нужен, когда файл на каждой машине почти одинаковый: отличается hostname, портом, списком бэкендов. Статику кладут в files/, изменяемое — в templates/.

      String            $env,
      String            $role,

| -%>

  Роль:    <%= $role %>   (<%= $env %>)

<%# коммент   %>  комментарий, в файл не попадёт

Puppet — Roles & Profiles: как заполнять роль и профиль

Это отраслевой стандарт организации Puppet-кода. Без него любой проект через полгода превращается в кашу, где непонятно, кто и что накатывает на ноду. Три уровня, у каждого строго своя работа.

⭐ МОДЕЛЬ Три слоя и правила для каждого 
СЛОЙ 3 — МОДУЛИ (чужие, с forge: nginx, postgresql, prometheus)
         Умеют «как поставить технологию вообще». Ничего не знают о твоей компании.
         ⛔ НИКОГДА не правь их напрямую.

СЛОЙ 2 — PROFILE (твой) — «как ЭТА технология настроена У НАС»
         profile::web::nginx = наш nginx: наши логи, наш TLS, наши заголовки,
         наш firewall-порт, наш мониторинг этого nginx.
         ✅ здесь: include чужих модулей, ресурсы, логика, обращение к Hiera
         ⛔ здесь НЕ хардкодят значения (пароли, домены) — они в Hiera

СЛОЙ 1 — ROLE (твой) — «ЧТО ЭТО ЗА СЕРВЕР»
         role::webserver = набор профилей, который делает машину веб-сервером.
         ✅ здесь: ТОЛЬКО include профилей. Ни одного ресурса, ни одной переменной,
            ни одного if. Роль читается как оглавление.
         ⭐ ЗОЛОТОЕ ПРАВИЛО: у ноды РОВНО ОДНА роль.
            Нужен «веб + база»? Это не две роли, это НОВАЯ роль role::allinone.

class profile::web::nginx (

  #    Значения придут автоматически по ключу 'profile::web::nginx::ИМЯ'
  Stdlib::Port          $port           = 80,
  Boolean               $ssl            = false,
  Integer[1]            $worker_conns   = 1024,
  Array[Stdlib::Host]   $upstreams      = [],
  Hash[String, String]  $vhosts         = {},
) {

  # 1) технологию ставит ЧУЖОЙ модуль
  package { 'nginx': ensure => installed }

  # 2) наши настройки поверх
  file { '/etc/nginx/nginx.conf':
    ensure  => file,
    owner   => 'root',
    mode    => '0644',
    content => epp('profile/nginx/nginx.conf.epp', {
      'workers'      => $facts['processors']['count'],
      'worker_conns' => $worker_conns,
      'upstreams'    => $upstreams,
    }),
    require => Package['nginx'],
    notify  => Service['nginx'],
  }

  # 3) виртуальные хосты из Hiera — сколько задали, столько и создастся
  $vhosts.each |$name, $opts| {
    profile::web::vhost { $name:
      server_name => $opts['server_name'],
      port        => pick($opts['port'], $port),
    }
  }

  # 4) сервис
  service { 'nginx':
    ensure  => running,
    enable  => true,
    require => Package['nginx'],
  }

  # 5) наш стандарт: открыть порт и отдать метрики мониторингу
  include profile::base::firewall
  firewalld_port { "nginx-${port}":
    ensure   => present,
    zone     => 'public',
    port     => $port,
    protocol => 'tcp',
  }
}
Как быстро понять, где ошибка в чужом коде: если в role::* есть хоть один file{} или if — код положили не туда. Если в profile::* есть строка с реальным паролем или доменом — данные положили не туда (их место в Hiera). Эти два признака ловят 80% беспорядка в Puppet-репозиториях.

Puppet — Hiera: иерархия и автоматический lookup

Hiera — отдельное хранилище данных. Главная идея Puppet-архитектуры: код в .pp, данные в .yaml. Код одинаков для всех; различия между нодами, ролями, ЦОДами и окружениями живут в yaml-файлах.

YAML hiera.yaml — иерархия поиска. Разбор каждой строки 
---
version: 5                          # ⭐ формат 5 (v3 — легаси, синтаксис другой)

defaults:
  datadir: data                     # где искать файлы (относительно окружения)
  data_hash: yaml_data              # чем читать: yaml_data / json_data / hocon_data

hierarchy:                          # ⭐ ПОРЯДОК ВАЖЕН: сверху вниз, кто выше — тот главнее
  - name: "Секреты ноды и общие"
    lookup_key: eyaml_lookup_key    # этот уровень читает ЗАШИФРОВАННЫЕ значения
    paths:
      - "secrets/nodes/%{trusted.certname}.eyaml"
      - "secrets/common.eyaml"
    options:
      pkcs7_private_key: /etc/puppetlabs/puppet/eyaml/private_key.pkcs7.pem
      pkcs7_public_key:  /etc/puppetlabs/puppet/eyaml/public_key.pkcs7.pem

  - name: "Конкретная нода"                       # ⭐ САМЫЙ ТОЧНЫЙ уровень
    path: "nodes/%{trusted.certname}.yaml"        # nodes/web01.example.com.yaml

  - name: "Роль в конкретном окружении"
    path: "roles/%{trusted.extensions.pp_role}/%{server_facts.environment}.yaml"

  - name: "Роль"
    path: "roles/%{trusted.extensions.pp_role}.yaml"    # roles/webserver.yaml

    path: "dc/%{facts.datacenter}.yaml"

  - name: "Семейство ОС"
    path: "os/%{facts.os.family}.yaml"            # os/RedHat.yaml

  - name: "Общее для всех"                        # ⭐ САМЫЙ ОБЩИЙ уровень

# иерархия обслуживает 5000 разных машин.
# Файла нет → уровень просто пропускается, ошибки нет.
⭐ ГЛАВНОЕ Автоматический параметр-lookup: как данные попадают в класс 
# Есть класс:
class profile::web::nginx (
  Stdlib::Port $port = 80,
) { ... }

# Когда ты пишешь просто:
include profile::web::nginx

# Puppet САМ идёт в Hiera и ищет ключ, собранный по правилу:
#        имя_класса :: имя_параметра
#        profile::web::nginx::port

# Порядок приоритета значения параметра:
#   1. resource-like объявление class { '...': port => 8080 }   ← сильнее всего
#   2. значение из Hiera по ключу profile::web::nginx::port
#      (первый найденный уровень иерархии, сверху вниз)
#   3. значение по умолчанию из определения класса ( = 80 )
#   4. ничего нет и дефолта нет → ОШИБКА компиляции

# Поэтому на проде почти нигде нет class{...}: есть include + yaml.

  - vim
  - htop
  - tmux

# ⭐ lookup_options — как СКЛЕИВАТЬ этот ключ между уровнями иерархии
lookup_options:
  classes:
    merge: unique                  # списки классов складываются со всех уровней
  profile::base::packages::list:
    merge: unique                  # пакеты дополняются, а не заменяются
  profile::base::users::accounts:
    merge:

      knockout_prefix: '--'        # '--kirill' на уровне ноды = удалить эту ветку
СТРАТЕГИИ merge — четыре поведения, которые надо знать 
first (по умолчанию)  взять значение с САМОГО ВЕРХНЕГО уровня, где нашлось.
                      Остальные игнорируются. Так работают обычные параметры.

unique                собрать значения со ВСЕХ уровней в один плоский массив,
                      убрать дубликаты. Для списков: классы, пакеты, правила.

hash                  слить хеши по верхнему уровню ключей
                      (вложенное значение целиком берётся с верхнего уровня).

deep                  слить хеши РЕКУРСИВНО, до самых глубоких ключей.
                      Для сложных структур вроде users/accounts.

# Явно, прямо в коде:
$pkgs  = lookup('profile::base::packages::list', Array[String], 'unique', [])
$users = lookup({'name' => 'users', 'merge' => {'strategy' => 'deep'}})

Три уровня зрелости работы с секретами: (1) пароль прямо в манифесте — так делать нельзя никогда; (2) hiera-eyaml — секрет в git зашифрован, ключ только на сервере — рабочий отраслевой минимум; (3) внешний Vault (модуль hiera_vault) — Puppet ходит за секретом в HashiCorp Vault на каждой компиляции, в git секретов нет вообще. Puppet — пример 1: пользователи, sudo и SSH-ключи

Самая частая задача: «заведи Пете доступ на все веб-серверы, а Васю убери отовсюду». В Puppet это правка одного yaml-файла — дальше парк разъедется сам за 30 минут.

PUPPET site-modules/profile/manifests/base/users.pp 
class profile::base::users (
  Hash[String, Hash]  $accounts = {},     # кого завести (данные из Hiera)
  Array[String]       $revoked  = [],     # кого выпилить отовсюду
  String              $sudo_group = 'wheel',
) {

  # ── 1. Заводим людей ────────────────────────────────────────────────
  $accounts.each |$login, $opts| {

    group { $login:
      ensure => present,
      gid    => $opts['gid'],             # undef = система выберет сама
    }

    user { $login:
      ensure     => present,
      uid        => $opts['uid'],
      gid        => $login,               # личная группа
      groups     => pick($opts['groups'], []),   # доп. группы: docker, wheel…
      comment    => pick($opts['comment'], $login),
      shell      => pick($opts['shell'], '/bin/bash'),
      home       => "/home/${login}",
      managehome => true,                 # ⭐ создать /home и скелет
      purge_ssh_keys => true,             # ⭐⭐ ключи, добавленные РУКАМИ, будут снесены
      require    => Group[$login],
    }

    # ── 2. SSH-ключи ──────────────────────────────────────────────────
    pick($opts['keys'], []).each |$index, $keyline| {
      # строка вида 'ssh-ed25519 AAAAC3Nza... kirill@laptop' → режем на части
      $parts = split($keyline, ' ')
      ssh_authorized_key { "${login}_${index}":
        ensure => present,
        user   => $login,
        type   => $parts[0],
        key    => $parts[1],
        require => User[$login],
      }
    }

    # ── 3. sudo — отдельным файлом, а не правкой /etc/sudoers ─────────
    if pick($opts['sudo'], false) {
      file { "/etc/sudoers.d/10-${login}":
        ensure       => file,
        owner        => 'root',
        group        => 'root',
        mode         => '0440',           # ⭐ иначе sudo ругается и НЕ работает
        content      => "${login} ALL=(ALL) NOPASSWD: ALL\n",
        validate_cmd => '/usr/sbin/visudo -cf %',   # ⭐⭐ проверка ДО подмены:
        require      => User[$login],     #     кривой sudoers = потеря root-доступа
      }
    } else {
      file { "/etc/sudoers.d/10-${login}": ensure => absent }
    }
  }

  # ── 4. Уволенные — снести везде и сразу ─────────────────────────────
  $revoked.each |$login| {
    user { $login:
      ensure => absent,
      # домашний каталог оставляем: в нём могут быть рабочие данные
    }
    file { "/etc/sudoers.d/10-${login}": ensure => absent }
  }
}

PUPPET А) Баннер в SSH: /etc/motd (после входа) и /etc/issue.net (до входа) 
# site-modules/profile/manifests/base/motd.pp
class profile::base::motd (
  Array[String]    $owners  = [],
  Optional[String] $ticket  = undef,     # идут работы — предупредить входящих
  String           $wiki    = 'https://wiki.company.ru/servers',
) {

  # 1) MOTD — показывается ПОСЛЕ успешной авторизации
  file { '/etc/motd':
    ensure  => file,
    owner   => 'root',
    group   => 'root',
    mode    => '0644',
    content => epp('profile/motd.epp', {
      'hostname' => $facts['networking']['fqdn'],
      'ip'       => $facts['networking']['ip'],
      'os'       => "${facts['os']['name']} ${facts['os']['release']['full']}",
      'role'     => pick($trusted['extensions']['pp_role'], 'нет роли'),
      'env'      => $server_facts['environment'],
      'owners'   => $owners,
      'ticket'   => $ticket,
      'wiki'     => $wiki,

    mode    => '0644',

class profile::monitoring::node_exporter (
  String       $version    = '1.8.2',
  Stdlib::Port $port       = 9100,
  Array[String] $prom_servers = [],       # кому разрешить скрейпить
) {

  # 1) системный пользователь без логина
  user { 'node_exporter':
    ensure => present,
    system => true,
    shell  => '/sbin/nologin',
    home   => '/var/lib/node_exporter',
  }

  # 2) бинарь: качаем и распаковываем (модуль puppet/archive)
  archive { "/tmp/node_exporter-${version}.tar.gz":
    ensure       => present,
    source       => "https://github.com/prometheus/node_exporter/releases/download/v${version}/node_exporter-${version}.linux-amd64.tar.gz",
    extract      => true,
    extract_path => '/opt',
    creates      => "/opt/node_exporter-${version}.linux-amd64/node_exporter",  # ⭐ идемпотентность
    cleanup      => true,
  }

  file { '/usr/local/bin/node_exporter':
    ensure  => link,
    target  => "/opt/node_exporter-${version}.linux-amd64/node_exporter",
    require => Archive["/tmp/node_exporter-${version}.tar.gz"],
    notify  => Service['node_exporter'],   # ⭐ сменили версию → рестарт
  }

  # 3) systemd-юнит из шаблона
  file { '/etc/systemd/system/node_exporter.service':
    ensure  => file,
    mode    => '0644',
    content => epp('profile/monitoring/node_exporter.service.epp', { 'port' => $port }),
    notify  => [Exec['systemd-daemon-reload'], Service['node_exporter']],
  }

  exec { 'systemd-daemon-reload':
    command     => 'systemctl daemon-reload',
    path        => ['/bin','/usr/bin'],
    refreshonly => true,                   # ⭐ только по notify, не каждый прогон
  }

  service { 'node_exporter':
    ensure  => running,
    enable  => true,
    require => File['/usr/local/bin/node_exporter'],
  }

  # 4) порт — только для prometheus-серверов
  $prom_servers.each |$src| {
    firewalld_rich_rule { "node_exporter from ${src}":
      ensure => present,
      zone   => 'public',
      source => $src,
      port   => { 'port' => $port, 'protocol' => 'tcp' },
      action => 'accept',
    }
  }

  # 5) ⭐⭐ ГЛАВНОЕ: нода ЭКСПОРТИРУЕТ себя как цель мониторинга.
  #    Два @@ = «положи это в PuppetDB, применит кто-то другой»
  @@concat::fragment { "prom_target_${facts['networking']['fqdn']}":
    target  => '/etc/prometheus/file_sd/nodes.yml',
    content => epp('profile/monitoring/target.yaml.epp', {
      'fqdn' => $facts['networking']['fqdn'],
      'port' => $port,
      'role' => pick($trusted['extensions']['pp_role'], 'unknown'),
      'env'  => $server_facts['environment'],
      'dc'   => pick($facts['datacenter'], 'unknown'),
    }),
    tag     => 'prometheus_node_target',
  }
}

class profile::app::shopfront (
  String            $version,                    # ⭐ обязателен: что катим
  Stdlib::HTTPUrl   $repo_url,
  String            $app_user   = 'shopfront',
  Stdlib::Absolutepath $app_dir = '/opt/shopfront',
  Stdlib::Port      $port       = 8000,
  Integer[1]        $workers    = 4,
  String            $domain     = 'shop.example.com',
  Sensitive[String] $db_password,                # ← из eyaml
  String            $db_host    = 'db01.example.com',
  Hash[String,String] $extra_env = {},
) {

  # ── 1. Кто будет владеть приложением ──────────────────────────────
  group { $app_user: ensure => present }

  user { $app_user:
    ensure  => present,
    gid     => $app_user,
    system  => true,
    shell   => '/sbin/nologin',            # ⭐ сервисному юзеру логин не нужен
    home    => $app_dir,
    require => Group[$app_user],
  }

  # ── 2. Каталоги ───────────────────────────────────────────────────
  file { [$app_dir, "${app_dir}/releases", "/var/log/shopfront"]:
    ensure  => directory,
    owner   => $app_user,
    group   => $app_user,
    mode    => '0750',
    require => User[$app_user],
  }

  # ── 3. Код: качаем нужную версию (идемпотентно через creates) ─────
  archive { "/tmp/shopfront-${version}.tar.gz":
    ensure       => present,
    source       => "${repo_url}/shopfront-${version}.tar.gz",
    extract      => true,
    extract_path => "${app_dir}/releases",
    creates      => "${app_dir}/releases/${version}",   # ⭐ уже есть — не качаем
    user         => $app_user,
    cleanup      => true,
    require      => File["${app_dir}/releases"],
  }

  # ── 4. Симлинк current → нужная версия. Смена = деплой/откат ──────
  file { "${app_dir}/current":
    ensure  => link,
    target  => "${app_dir}/releases/${version}",
    owner   => $app_user,
    require => Archive["/tmp/shopfront-${version}.tar.gz"],
    notify  => Service['shopfront'],       # ⭐ переключили версию → рестарт
  }

  # ── 5. Конфиг приложения (секреты внутри) ─────────────────────────
  file { "${app_dir}/shared/app.env":
    ensure    => file,
    owner     => $app_user,
    group     => $app_user,
    mode      => '0640',                   # ⭐ читает только приложение
    show_diff => false,                    # ⭐ пароль не светим в отчётах
    content   => Sensitive(epp('profile/app/shopfront.env.epp', {
      'db_host'  => $db_host,
      'db_pass'  => $db_password.unwrap,
      'port'     => $port,
      'workers'  => $workers,
      'extra'    => $extra_env,
    })),
    notify    => Service['shopfront'],
  }

  # ── 6. systemd-юнит ───────────────────────────────────────────────
  file { '/etc/systemd/system/shopfront.service':
    ensure  => file,
    mode    => '0644',
    content => epp('profile/app/shopfront.service.epp', {
      'user'    => $app_user,
      'app_dir' => $app_dir,
      'port'    => $port,
      'workers' => $workers,
    }),
    notify  => [Exec['shopfront-daemon-reload'], Service['shopfront']],
  }

  exec { 'shopfront-daemon-reload':
    command     => 'systemctl daemon-reload',
    path        => ['/bin','/usr/bin'],
    refreshonly => true,
  }

  # ── 7. Сервис ─────────────────────────────────────────────────────
  service { 'shopfront':
    ensure    => running,
    enable    => true,
    subscribe => File["${app_dir}/current"],   # то же, что notify, только с другой стороны
  }

  # ── 8. Прокси: наружу торчит nginx, а не приложение ───────────────
  include profile::web::nginx
  profile::web::vhost { 'shopfront':
    server_name => $domain,
    port        => 80,
    proxy_pass  => "http://127.0.0.1:${port}",
  }

  # ── 9. Firewall: 80 — всем, 8000 — только локально ────────────────
  firewalld_port { 'shopfront-http':
    ensure => present, zone => 'public', port => 80, protocol => 'tcp',
  }

  # ── 10. SELinux на RHEL/РЕД ОС: без этого nginx получит 502 ───────
  if $facts['os']['selinux']['enabled'] {
    selboolean { 'httpd_can_network_connect':
      value      => 'on',
      persistent => true,
    }
  }

  # ── 11. Мониторинг именно этого приложения ────────────────────────
  @@concat::fragment { "prom_target_app_${facts['networking']['fqdn']}":
    target  => '/etc/prometheus/file_sd/apps.yml',
    content => "- targets: ['${facts['networking']['fqdn']}:${port}']\n    labels: {app: 'shopfront'}\n",
    tag     => 'prometheus_app_target',
  }

  # ── 12. Логи в ротацию ────────────────────────────────────────────
  logrotate::rule { 'shopfront':
    path       => '/var/log/shopfront/*.log',
    rotate     => 14,
    rotate_every => 'day',
    compress   => true,
    su_owner   => $app_user,
  }
}

Puppet — как разобраться в чужом проде

Тебя пустили на незнакомый сервер. Задача: понять, кто им управляет, что именно накатывается и откуда берутся значения. Порядок действий — сверху вниз, без гадания.

⭐ ПРОЦЕДУРА Разведка на ноде — 8 шагов 
# 0) Puppet тут вообще есть и живой?
rpm -q puppet-agent || dpkg -l | grep puppet-agent
systemctl status puppet
export PATH=$PATH:/opt/puppetlabs/bin        # ⭐ бинарей в PATH обычно нет

# 1) КТО МНОЙ УПРАВЛЯЕТ и как часто
puppet config print server certname environment runinterval noop
#   server      → адрес puppetserver
#   certname    → под каким именем меня знают (ключ ко ВСЕЙ иерархии Hiera!)
#   environment → какую ветку кода я получаю
#   noop=true   → ⚠️ нода в холостом режиме: Puppet смотрит, но НЕ применяет

# 2) КОГДА он последний раз отработал и что сделал
cat /opt/puppetlabs/puppet/cache/state/last_run_summary.yaml
#   changes.total  — сколько ресурсов поменял
#   events.failure — сколько упало       ⭐ не ноль → тут проблема
#   time.last_run  — когда (unixtime); если давно — агент мёртв или отключён

puppet agent --disable                      # (посмотреть причину отключения)
cat /opt/puppetlabs/puppet/cache/state/agent_disabled.lock

# 3) ЧТО ИМЕННО он мне накатывает — полный список ресурсов из последнего каталога
jq -r '.resources[] | "\(.type)[\(.title)]"' \
   /opt/puppetlabs/puppet/cache/client_data/catalog/$(puppet config print certname).json | sort | head -50
#   ⭐ самый честный ответ на вопрос «что здесь под управлением»

# 4) КАКИЕ КЛАССЫ на мне висят
jq -r '.resources[] | select(.type=="Class") | .title' \
   /opt/puppetlabs/puppet/cache/client_data/catalog/*.json | sort
#   увидишь Role::Webserver, Profile::Base, Profile::Web::Nginx… — это оглавление ноды

# 5) ПРОГОН ВХОЛОСТУЮ — что он хочет поменять прямо сейчас
puppet agent -t --noop
#   строки "would have been changed" = дрейф: кто-то правил руками
puppet agent -t --noop --debug --evaltrace 2>&1 | tee /tmp/puppet.log

# 6) КТО Я С ТОЧКИ ЗРЕНИЯ ФАКТОВ (по ним строится вся иерархия Hiera)
puppet facts show | jq '{fqdn: .networking.fqdn, os: .os.family, role: .trusted}'
facter -p os.family networking.fqdn          # facter 3; в facter 4: puppet facts show

# 7) ТЕКУЩЕЕ состояние объекта в синтаксисе Puppet (удобно для написания манифеста)
puppet resource user deploy
puppet resource service nginx
puppet resource package nginx

# 8) ЛОГИ
journalctl -u puppet --since '-2h'           # что делал агент
less /opt/puppetlabs/puppet/cache/state/last_run_report.yaml   # подробный отчёт
⭐ ПРОЦЕДУРА Разведка в коде: «почему на ноде именно так» 
# 1) Найти control-repo (на сервере) и понять точку входа
cd /etc/puppetlabs/code/environments/production
cat .r10k-deploy.json          # какой коммит и ветка тут развёрнуты
cat manifests/site.pp          # ⭐ как ноды получают классы

# 2) Какие классы получит КОНКРЕТНАЯ нода (не заходя на неё)
puppet lookup classes --node web07.example.com --merge unique --environment production

# 3) Идём по цепочке: роль → профили → ресурсы
grep -rn 'class role::webserver' site-modules/role/manifests/
cat site-modules/role/manifests/webserver.pp        # список профилей
cat site-modules/profile/manifests/web/nginx.pp     # что реально делает профиль

# 4) ⭐⭐ Откуда взялось КОНКРЕТНОЕ значение — самый частый вопрос:
puppet lookup profile::web::nginx::port --node web07.example.com --explain
#   покажет ВСЕ проверенные файлы иерархии, найденное значение и что чем перебито

# 5) Кто ещё трогает этот файл/пакет (ищем дубли и «сюрпризы»)
grep -rn "'/etc/nginx/nginx.conf'" site-modules/ modules/
grep -rn 'shopfront' data/

# 6) Скомпилировать каталог для ноды прямо на сервере, ничего не применяя:
puppet catalog compile web07.example.com --environment production > /tmp/cat.json
jq -r '.resources[] | "\(.type)[\(.title)]"' /tmp/cat.json | sort

# 7) Если развёрнут PuppetDB — вопросы ко всему парку сразу:
puppet query 'nodes[certname] { facts { name = "os.family" and value = "RedHat" } }'
puppet query 'resources[certname] { type = "Class" and title = "Role::Webserver" }'
#   «на каких машинах стоит эта роль», «у кого какая версия пакета», «кто давно не отчитывался»
Порядок чтения любого Puppet-прода одной строкой: site.pp → какая роль у ноды → какие профили в роли → что делает профиль → откуда данные (puppet lookup --explain). Пять шагов, и ты знаешь про сервер больше, чем половина команды.

Другие частые ошибки — коротко
"Could not find data item X in any Hiera data file"
   → параметр без дефолта и без значения в Hiera.
     Проверить: puppet lookup X --node NODE --explain (увидишь все проверенные пути)

"Error: Could not retrieve catalog; skipping run"
   → сервер не отдал каталог. Смотреть /var/log/puppetlabs/puppetserver/puppetserver.log

"Server hostname 'puppet' did not match server certificate"
   → у сервера нет нужного dns_alt_names. Перевыпустить сертификат сервера.

"Exiting; no certificate found and waitforcert is disabled"
   → CSR не подписан. На сервере: puppetserver ca sign --certname NODE

"Class[...]: expects a value for parameter 'x'"
   → обязательный параметр не задан ни в Hiera, ни в коде.

Агент «ничего не делает», ошибок нет
   → либо noop=true в puppet.conf, либо агент disabled (agent_disabled.lock),
     либо нода вообще не попала ни в один node-блок / список classes.

Изменения в git есть, на ноде нет
   → r10k не выкатил ветку: r10k deploy environment production -p
     и проверить .r10k-deploy.json

Puppet — cheatsheet и best practices

ПРАВИЛА 10 правил, за которые говорят «человек работал с Puppet» 
1.  Roles & Profiles обязательны. Роль — только include. У ноды одна роль.
2.  Код в .pp, данные в Hiera. Ни одного пароля/домена/IP в манифестах.
3.  include, а не class {}. Параметры приходят автолукапом из Hiera.
4.  Типы у всех параметров (String, Integer, Enum, Stdlib::Port) — бесплатная валидация.
5.  Секреты — eyaml + Sensitive[String] + show_diff => false.
6.  Ничего не править руками в /etc/puppetlabs/code — только git → r10k.
7.  Сначала --noop, потом канарейка, потом парк. Всегда в таком порядке.
8.  Версии внешних модулей в Puppetfile пиньтся жёстко. ':latest' = инцидент.
9.  В CI: puppet parser validate + puppet-lint + rspec-puppet на каждый PR.
10. Мониторить сам Puppet: last_run_summary.yaml (failures > 0, старый time.last_run)
    — «агент молча умер» обнаруживается только так.

Итог по разделу: Puppet — это непрерывное удержание состояния парка машин. Агент каждые 30 минут забирает с сервера каталог, скомпилированный лично под него из кода (Roles & Profiles) и данных (Hiera), и приводит машину в соответствие. Правило одной ноды и правило «на всех» — это просто разные уровни иерархии Hiera: data/nodes/имя.yaml против data/common.yaml. Развернуть что угодно — значит написать профиль по скелету «пользователь → каталоги → код → конфиг из шаблона → systemd → сервис → прокси → firewall → мониторинг», а различия между машинами вынести в yaml. Разобраться в чужом проде — пять шагов: site.pp → роль → профили → ресурсы → puppet lookup --explain.
