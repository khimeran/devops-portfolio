⚡ Важно для DevOps

Универсальный справочник — инструменты, подходы и хитрости которые нужны в работе независимо от проекта. Раздел пополняется по мере работы.

Главная задача DevOps: приложение должно работать стабильно, быстро восстанавливаться после сбоев, и любой инженер должен разобраться в проблеме за минуты — не часы. Тебе неважно на чём написано приложение — важно чтобы оно запускалось, мониторилось и чинилось.

Операционные системы

DevOps работает преимущественно с Linux — большинство серверов в мире работают на нём. Windows используется на рабочих машинах разработчиков.

BASH Популярные дистрибутивы Linux 
Ubuntu / Debian    — самые популярные, много документации
                   apt install пакет — менеджер пакетов

Fedora / RHEL /    — корпоративный стандарт, есть SELinux
CentOS / Rocky     dnf install пакет — менеджер пакетов
                   используется в крупных компаниях

Alpine Linux       — минималистичный, часто внутри Docker образов
                   apk add пакет — менеджер пакетов
                   размер образа ~5MB против ~100MB у Ubuntu

Arch Linux         — для продвинутых, всегда свежие пакеты
                   pacman -S пакет
BASH Windows для DevOps 
WSL2 (Windows Subsystem for Linux)
— полноценный Linux внутри Windows
— можно запускать Docker, bash скрипты, всё то же что на Linux
— установка: wsl --install в PowerShell от администратора

PowerShell — мощная замена CMD, есть аналоги Linux команд
— ls, cd, cat, grep (Select-String) работают похоже
— но синтаксис отличается от bash

Git Bash — bash эмулятор для Windows, устанавливается с Git
— позволяет использовать Linux команды на Windows

Текстовые редакторы в терминале

Иногда нет графического интерфейса — только терминал. Нужно уметь редактировать файлы прямо в нём.

BASH nano — простой редактор для новичков 
nano файл.txt          # открыть файл

# Управление внутри nano:
Ctrl+O → Enter         # сохранить (O = Output)
Ctrl+X                 # выйти
Ctrl+K                 # удалить строку
Ctrl+W                 # поиск по файлу
Ctrl+G                 # справка

# Внизу экрана всегда видны подсказки — ^ означает Ctrl
BASH vim — мощный редактор, нужно знать основы 
vim файл.txt           # открыть файл

# vim работает в режимах:
i                      # войти в режим вставки (можно печатать)
Esc                    # выйти из режима вставки
:w                     # сохранить
:q                     # выйти
:wq                    # сохранить и выйти
:q!                    # выйти без сохранения

# В режиме команд (после Esc):
dd                     # удалить строку
yy                     # скопировать строку
p                      # вставить
/слово                 # найти слово
n                      # следующее совпадение

# Лайфхак: если случайно открыл vim и не знаешь как выйти
Esc → :q! → Enter      # аварийный выход без сохранения
BASH mc (Midnight Commander) — файловый менеджер в терминале

# mc показывает два окна с файлами — как Total Commander
# управление:
F4                     # редактировать файл

F6                     # переместить
F8                     # удалить

# установка:

curl — проверка HTTP запросов

curl — универсальный инструмент для отправки HTTP запросов. Незаменим для проверки API и диагностики.

BASH curl — основные флаги 
# Основной синтаксис:
curl [флаги] URL

# Флаги (можно комбинировать):
-X GET/POST/PUT/DELETE  # метод запроса (по умолчанию GET)
-H "Key: Value"         # добавить заголовок
-d '{"key":"value"}'    # тело запроса (данные)
-o файл.json            # сохранить ответ в файл
-s                      # тихий режим (без прогресса)
-v                      # подробный вывод (запрос + ответ)
-L                      # следовать редиректам
-u user:password        # базовая авторизация

# Примеры:
curl http://localhost:8000/topics
# простой GET запрос

curl -s http://localhost:8000/topics | python3 -m json.tool
# -s убирает прогресс, json.tool форматирует JSON красиво

curl -X PUT "http://localhost:8000/topics/1?progress=90" \
  -H "Content-Type: application/json"
# PUT запрос с заголовком
# \ в конце строки — перенос команды на следующую строку

curl -v http://localhost:8000/health
# подробный вывод — видно заголовки запроса и ответа
# полезно при отладке CORS и авторизации

sed — замена текста в файлах

sed — потоковый редактор. Позволяет менять текст в файлах без открытия редактора. Незаменим в скриптах.

BASH sed — основные операции 
# Замена текста:
sed 's/старое/новое/' файл.txt
# s — substitute (заменить), заменит первое вхождение в каждой строке

sed 's/старое/новое/g' файл.txt
# g — global, заменит все вхождения

sed -i 's/старое/новое/g' файл.txt
# -i — изменить файл на месте (без -i только выводит результат)

# Примеры:
sed -i 's/localhost/production-server/g' config.yml
# заменить адрес во всём файле конфига

sed -n '5,10p' файл.txt
# показать строки с 5 по 10

grep "ERROR" app.log | sed 's/ERROR/❌ ERROR/g'
# найти ошибки и подсветить их

Bash скрипты

Шпаргалка по синтаксису bash — что с чем не путать (кавычки, скобки, операторы, слеши) плюс лайфхаки. Полный разбор «как из одной команды вырастает боевой скрипт» — в разделе 🐧 Linux → «Bash — скрипты и автоматизация».

BASH Структура скрипта 
#!/bin/bash
# !/bin/bash — шебанг, указывает какой интерпретатор использовать
# без этой строки скрипт может не запуститься

# Переменные:
NAME="world"
echo "Hello, $NAME"    # Hello, world
# $NAME — обращение к переменной

# Условия:
if [ -f файл.txt ]; then
    echo "файл существует"
else
    echo "файла нет"
fi
# -f — проверить что это файл
# -d — проверить что это папка
# -z — проверить что строка пустая

# Цикл:
for i in 1 2 3; do
    echo "Число: $i"
done

# Запуск скрипта:
chmod +x script.sh     # дать права на выполнение
./script.sh            # запустить
QUOTES Кавычки и апострофы — не путать 
"двойные"   — bash ПОДСТАВЛЯЕТ переменные и $( ):  echo "$USER" → kirill
'одинарные' — всё БУКВАЛЬНО, $ не трогается:        echo '$USER' → $USER
`обратные`  — старый аналог $( ); НЕ используй, легко спутать с ' — пиши $( )

# Спецсимволы ($ ! @ \) — только в ОДИНАРНЫХ, иначе bash их съест:
echo "P@$$w0rd"   # $$ = PID процесса → строка испорчена
echo 'P@$$w0rd'   # символ в символ — как надо
# " и ' — это РАЗНЫЕ режимы, не взаимозаменяемы.
BRACKETS Скобки: круглые / квадратные / фигурные 
$( ... )   выполнить команду, подставить РЕЗУЛЬТАТ:  D=$(date +%F)
${ ... }   явные границы имени переменной:           echo "${NAME}_bak"
( ... )    подоболочка (отдельный процесс) / при объявлении функции f()
{ ...; }   группа команд в ТЕКУЩЕЙ оболочке / тело функции (пробелы и ; нужны)
[ ... ]    тест-условие (это команда test!):  if [ -f файл ]; then
[[ ... ]]  продвинутый тест bash: умеет && || и =~ (regex)
(( ... ))  арифметика:  (( i++ )) ,  if (( a > b ))

# НЕ ПУТАТЬ:
#  ( ) подоболочка  ≠  { } та же оболочка
#  [ ] тест         ≠  { } блок команд
#  $(...) команда   ≠  ${...} переменная
OPERATORS Операторы и разделители 
;     разделитель: команды по очереди, независимо друг от друга
&&    "И":   следующее ТОЛЬКО если предыдущее успешно (код 0)
||    "ИЛИ": следующее ТОЛЬКО если предыдущее упало (код ≠ 0)
&     отправить команду в ФОН (не ждать её завершения)
|     пайп: stdout левой команды → stdin правой:  ps aux | grep nginx
>     перенаправить вывод в файл — ЗАТЕРЕТЬ
>>    перенаправить вывод в файл — ДОПИСАТЬ (для логов!)
2>&1  направить ошибки (stderr) туда же, куда обычный вывод (stdout)

# НЕ ПУТАТЬ:
#  &  (фон)      ≠  &&  (логическое И)
#  |  (пайп)     ≠  ||  (логическое ИЛИ)
#  >  (затереть) ≠  >>  (дописать)
BACKSLASH Обратный слеш \ — перенос и экранирование 
# 1) В КОНЦЕ строки — перенос длинной команды на несколько строк:
cmd1 \
  && cmd2 \
  && cmd3            # bash склеит всё в одну команду
# ⚠️ после \ НЕ должно быть ни пробела, ни таба — только конец строки,
#    иначе \ экранирует пробел, а не перенос — и команда развалится.

# 2) Перед символом — экранировать (снять спецсмысл):
echo "цена 5\$"      # \$ = просто доллар, а не начало переменной
cd my\ file          # \(пробел) = пробел внутри имени файла
grep "\." file       # \. = точка как символ, а не "любой символ"
LIFEHACKS Лайфхаки — проверка и защита 
set -euo pipefail        # первые строки взрослого скрипта: падать честно
bash -n script.sh        # проверить СИНТАКСИС, ничего не запуская
bash -x script.sh        # трассировка: печатает каждую команду перед запуском
shellcheck script.sh     # ⭐ линтер: ловит кучу багов и опечаток ДО запуска

"$var"                   # ВСЕГДА бери переменные в кавычки — спасает от пробелов
${VAR:-default}          # подставить default, если VAR пустая/не задана
${#var}                  # длина строки в переменной
cmd && echo OK || echo FAIL   # быстрый одноразовый итог прямо в терминале
mkdir -p a/b/c           # -p создаёт всю цепочку папок и не ругается, если есть
!!                       # повторить прошлую команду целиком:  sudo !!

Cron — планировщик задач

Cron запускает команды по расписанию. Бэкапы, очистка логов, проверки — всё это делается через cron.

BASH Синтаксис cron 
# Открыть редактор cron задач:
crontab -e

# Формат записи:
# минута час день месяц день_недели команда
# *      *   *    *     *            команда

# Примеры:
0 2 * * *    /scripts/backup.sh
# каждый день в 2:00 ночи запускать бэкап

*/5 * * * *  curl http://localhost:8000/health
# каждые 5 минут проверять здоровье сервиса

0 0 * * 1    docker system prune -f
# каждый понедельник в полночь чистить Docker

# Спецсимволы:
*    — любое значение
*/5  — каждые 5 единиц
1-5  — от 1 до 5
1,3,5 — конкретные значения

# Проверить список задач:
crontab -l

systemd на проде — главные приёмы

Самые частые ситуации, в которых DevOps использует systemd на боевом сервере.

DIAG Что-то сломалось — первое движение 
systemctl status  <сервис>       # 70% инцидентов закрываются ЗДЕСЬ
                                  # видно: жив/мёртв, когда упал, хвост логов

journalctl -u <сервис> -n 100 -r  # последние 100 строк, свежие сверху
journalctl -u <сервис> -p err     # только ошибки
journalctl -u <сервис> --since "1 hour ago"
journalctl -u <сервис> -f         # live tail, чтобы поймать момент

systemctl list-units --state=failed   # все упавшие сервисы на сервере
RELOAD Корректное обновление конфига без даунтайма 
# БОЛЬШИНСТВО сервисов умеют reload:
sudo systemctl reload nginx       # перечитать конфиг без обрыва соединений
sudo systemctl reload sshd        # перечитать sshd_config

# reload работает, ТОЛЬКО если в .service есть ExecReload=
# проверить:
systemctl cat nginx | grep -i reload

# если сервис не умеет reload — есть только restart (с обрывом):
sudo systemctl restart myapp
EDIT Правильная правка чужого юнита 
# НЕ редактируй файл в /usr/lib/systemd/system/ напрямую —
# при обновлении пакета он будет затёрт.

# Вместо этого — override:
sudo systemctl edit nginx
# откроет редактор, сохрани туда ТОЛЬКО изменения:
# [Service]
# Restart=on-failure
# RestartSec=2

# Override сохранится в /etc/systemd/system/nginx.service.d/override.conf
# и automatic daemon-reload + рестарт сервиса.
# Изменения переживут обновление пакета.
TIMER systemd-timer как замена cron 
# Современная альтернатива cron'у — пара юнитов:
# /etc/systemd/system/backup.service — что запускать (Type=oneshot)
# /etc/systemd/system/backup.timer   — когда запускать

# backup.timer:
[Unit]
Description=Daily backup

[Timer]
OnCalendar=*-*-* 02:00:00    # каждый день в 2:00
Persistent=true              # если машина была выключена — догнать запуск
Unit=backup.service

[Install]
WantedBy=timers.target

# Преимущества над cron:
# + Логи в journalctl (cron логирует в /var/log/cron, не везде удобно)
# + Persistent=true — догон пропущенных запусков (cron этого не умеет)
# + Зависимости через After=/Requires=
# + Случайный сдвиг через RandomizedDelaySec= (распределить нагрузку)

# Управление:
sudo systemctl enable --now backup.timer
systemctl list-timers           # увидеть все таймеры с next-trigger
journalctl -u backup.service    # логи прошлых запусков
DOCKER Стек docker-compose под systemd (паттерн) 
# Зачем: автозапуск стека при перезагрузке сервера +
#        автоматический рестарт при падении + единый журнал.

# /etc/systemd/system/myapp.service:
[Unit]
Description=My App Stack
After=docker.service network-online.target
Requires=docker.service

[Service]
Type=simple
WorkingDirectory=/opt/myapp
ExecStart=/usr/bin/docker compose up
ExecStop=/usr/bin/docker compose down
Restart=on-failure
RestartSec=5
User=appuser           # ⭐ НЕ root, иначе файлы данных будут root:root

[Install]
WantedBy=multi-user.target

# Деплой:
sudo systemctl daemon-reload
sudo systemctl enable --now myapp
Главное правило прода: любой сервис должен (1) запускаться через systemd-юнит с Restart=on-failure, (2) логировать в journal (просто пиши в stdout/stderr), (3) обрабатывать SIGTERM для корректного завершения. Без этих трёх — сервис нельзя считать прод-готовым.

SELinux — безопасность на Fedora/RHEL

SELinux — дополнительный слой защиты. Часто мешает Docker и другим инструментам на Fedora.

BASH Диагностика и управление SELinux 
getenforce
# Enforcing — активен и блокирует
# Permissive — только логирует, не блокирует
# Disabled — выключен

sestatus               # подробный статус
ausearch -m avc -ts recent  # что заблокировал недавно

# Docker + SELinux:
volumes:
  - ./папка:/путь/в/контейнере:z
# :z — shared (несколько контейнеров)
# :Z — private (только этот контейнер)

# Временно отключить (только для отладки!):
setenforce 0           # Permissive режим
setenforce 1           # вернуть Enforcing
Permission denied в Docker на Fedora
Permission denied: '/путь/к/папке'

Это SELinux — не права файловой системы. chmod не поможет. Добавь :z к volume.

Диагностика — универсальный порядок

BASH Что делать когда что-то сломалось 
# 1. Статус процессов/контейнеров
docker ps -a           # для Docker
systemctl status nginx # для systemd сервисов
ps aux | grep python   # найти процесс по имени

# 2. Логи
docker logs контейнер 2>&1 | tail -50
journalctl -u сервис -n 50 --no-pager
tail -f /var/log/nginx/error.log
# 2>&1 — объединить stdout и stderr
# tail -50 — последние 50 строк
# -f — следить в реальном времени

# 3. Сеть и порты
ss -tlnp | grep 8000   # кто занимает порт
curl -v http://localhost:8000  # проверить HTTP
ping hostname          # проверить доступность хоста

# 4. Ресурсы
df -h                  # место на диске
free -h                # оперативная память
htop                   # мониторинг в реальном времени

Диски и RAID — боевые приёмы

BASH Дежурный набор при «что-то с диском» 
# Карта местности: кто диск, кто раздел, где смонтирован, какие UUID:
lsblk -f

# «Диск полный!» — кто сожрал:
df -h                      # по файловым системам: где болит
du -xh --max-depth=1 / | sort -h | tail   # кто именно ест (-x = не лезть в другие ФС)
# df видит, du не видит? Файлы-призраки ПОД точкой монтирования
# или удалённый файл, который держит процесс: lsof | grep deleted

# Здоровье RAID — одна команда:
cat /proc/mdstat           # [UU] = оба живы; [U_] = деградировал, меняй диск!
mdadm --detail /dev/md0    # подробности: какой именно диск выпал

# Перед ЛЮБЫМ ребутом после правки fstab:
systemctl daemon-reload && mount -a   # ошибка вылезет сейчас, а не в emergency shell
# И nofail на всё, без чего система может жить.

HashiCorp Vault — сейф для секретов

Файлик .env хорош, пока у тебя один сервер и один ты. Когда серверов сто, деплоев двадцать в день, а пароль от базы знает каждый второй скрипт — нужен центральный сейф. Это и есть Vault.

КОНЦЕПТ Как устроен: сейф, ключи, аренда 
Идея: секреты лежат ЗАШИФРОВАННЫМИ в одном месте; приложения и люди
приходят за ними по API с ТОКЕНОМ, а Vault решает по ПОЛИТИКАМ, кому что.

Ключевые понятия:
seal/unseal   после старта Vault «запечатан» — данные есть, читать нельзя.
              Распечатывается НЕСКОЛЬКИМИ ключами (схема Шамира: ключ
              разрезан, скажем, на 5 частей, любые 3 открывают). Ни один
              человек в одиночку сейф не откроет.
policy        кому какие пути можно: app-у — читать secret/db, людям — своё.
secret engine движки хранения: kv (ключ-значение), database (⭐ генерирует
              ВРЕМЕННЫЕ логины к БД на лету), pki (выписывает TLS-серты).
lease / TTL   секрет выдаётся В АРЕНДУ на время. Истекла — секрет мёртв.
              Утёкший пароль, который сам умирает через час, — уже не трагедия.
audit log     каждый чих записан: кто, когда, какой секрет читал.
BASH Как это выглядит руками 
vault kv put secret/myapp db_pass=s3cr3t     # положить секрет
vault kv get secret/myapp                    # прочитать (если политика пускает)

# Приложению пароль в конфиге больше не нужен:
# оно логинится в Vault и просит секрет в рантайме.

# Магия движка database — временные креды к PostgreSQL:
vault read database/creds/my-role
# → username: v-token-my-role-x7f2..., password: A1b2..., lease: 1h
# Через час Vault САМ удалит этого юзера из базы. Паролей «навсегда» нет.
Формула: .env — секрет лежит у каждого; Vault — секрет лежит в одном сейфе, выдаётся по токену, по политике, на время и под запись. На собесе достаточно: seal/unseal по Шамиру, политики, kv vs динамические секреты, lease/TTL.

PostgreSQL — администрирование

DevOps должен уметь подключиться к базе, посмотреть что происходит, найти медленные запросы и не сломать продакшн.

SQL Полезные команды psql 
\l          — список всех баз данных
\c dbname   — подключиться к базе
\dt         — список таблиц
\d topics   — структура таблицы (колонки, типы, индексы)
\di         — список индексов
\du         — список пользователей
\x          — расширенный вывод (удобно для широких таблиц)
\timing     — показывать время выполнения каждого запроса
\q          — выйти
SQL Диагностика производительности 
-- Найти медленные запросы (нужен модуль pg_stat_statements):
SELECT query, calls, mean_exec_time, total_exec_time
FROM pg_stat_statements
ORDER BY mean_exec_time DESC
LIMIT 10;

-- Активные подключения и что они делают:
SELECT pid, usename, application_name, state, query
FROM pg_stat_activity
WHERE state != 'idle';

-- Размер таблиц:
SELECT relname, pg_size_pretty(pg_total_relation_size(relid))
FROM pg_stat_user_tables
ORDER BY pg_total_relation_size(relid) DESC;

-- Размер базы данных:
SELECT pg_size_pretty(pg_database_size('portfolio'));

-- Статистика использования индексов:
SELECT indexrelname, idx_scan, idx_tup_read
FROM pg_stat_user_indexes
ORDER BY idx_scan;
SQL Управление пользователями и правами 
-- Создать пользователя:
CREATE USER readonly WITH PASSWORD 'secret';

-- Дать права только на чтение:
GRANT SELECT ON ALL TABLES IN SCHEMA public TO readonly;

-- Дать все права на базу:
GRANT ALL PRIVILEGES ON DATABASE portfolio TO devops;

-- Отозвать права:
REVOKE SELECT ON topics FROM readonly;

-- Посмотреть права на таблицу:
\dp topics
BASH Бэкап и восстановление PostgreSQL 
# Сделать бэкап базы:
pg_dump -U devops -d portfolio > backup.sql
# или в сжатом формате:
pg_dump -U devops -d portfolio -Fc > backup.dump

# Восстановить из бэкапа:
psql -U devops -d portfolio < backup.sql
# или из сжатого:
pg_restore -U devops -d portfolio backup.dump

# Бэкап через Docker:
docker exec devops-portfolio-db-1 pg_dump -U devops portfolio > backup.sql

# Расписание бэкапов через cron (каждый день в 3:00):
0 3 * * * docker exec devops-portfolio-db-1 pg_dump -U devops portfolio > /backups/$(date +%Y%m%d).sql
Золотое правило DevOps и PostgreSQL: EXPLAIN ANALYZE перед любым изменением схемы на продакшн. Добавил индекс → проверь что запросы стали быстрее. Удалил индекс → убедись что ничего не замедлилось. Никогда не делай миграции без бэкапа.

NULL — заражает всё

SQL Как NULL ведёт себя в выражениях 
SELECT 1 + NULL;           -- результат: NULL (не 1, не ошибка — именно NULL)
SELECT 'text' || NULL;     -- результат: NULL
SELECT COUNT(notes) FROM topics;  -- не считает строки где notes = NULL
SELECT COUNT(*) FROM topics;      -- считает ВСЕ строки включая NULL

-- NULL "заражает" всё к чему прикасается
-- Любая операция с NULL = NULL

-- COALESCE — спасение от NULL:
SELECT name, COALESCE(notes, 'нет заметок') FROM topics;
-- если notes = NULL → вернёт 'нет заметок'
-- если notes = 'текст' → вернёт 'текст'

-- NULLIF — обратное: вернуть NULL если значение равно чему-то:
SELECT NULLIF(progress, 0) FROM topics;
-- если progress = 0 → вернёт NULL
-- удобно чтобы не делить на ноль

Боевые приёмы — закрепляем разобранное

Короткие приёмы, которые всплыли на тестировании. Каждый — про реальную ситуацию «что-то сломалось, надо чинить».

BASH Процессы, сигналы, контейнеры 
# Убивать процесс ПРАВИЛЬНО (не лупить -9 сразу):
kill 4242              # SIGTERM — вежливо, даёт закрыть файлы/БД
# подождал пару секунд, не сдох:
kill -9 4242           # SIGKILL — насильно (рвёт данные, оставляет .lock)
# SIGKILL нельзя поймать; сразу -9 = битые данные и осиротевшие локи

# Процесс в состоянии D (uninterruptible sleep) не убить НИЧЕМ,
# даже -9 — он ждёт мёртвый диск/NFS. Лечится только ребутом.
ps -eo pid,stat,cmd | grep ' D'

# Влезть в контейнер с упрямым ENTRYPOINT (например ENTRYPOINT=python):
docker run --entrypoint bash myimage   # перебить entrypoint напрямую
docker exec -it мой_контейнер bash     # зайти в уже запущенный

# База не успевает чисто остановиться за 10 сек grace period:
docker stop -t 30 db_container          # дать 30 сек на флаш данных

# В Dockerfile ВСЕГДА exec form — иначе процесс не PID 1
# и SIGTERM застрянет в sh:
# CMD ["python", "app.py"]   ✅   а не   CMD python app.py  ❌
BASH Сеть, доступ, безопасность
