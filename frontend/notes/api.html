🔌 API — интерфейсы, HTTP и curl

API (Application Programming Interface) — способ одной программы попросить что-то у другой. Не «страница для человека», а интерфейс для машин: строгий формат запроса, строгий формат ответа. Для DevOps это базовый навык — потому что всё вокруг является API: Docker, Kubernetes, Prometheus, GitHub, облако, Puppet. Даже kubectl и terraform внутри просто ходят по HTTP.

Аналогия: ресторан. Кухня (сервер) не пускает тебя внутрь и не даёт трогать плиту. Есть официант (API) и меню (документация): говоришь строго по меню — получаешь блюдо. Скажешь не по формату — получишь «такого нет» (404) или «так нельзя» (400). Официант не даст тебе больше, чем разрешено, и не покажет чужие заказы (403).

Что такое API и какие они бывают

КОНЦЕПТ API — это контракт 
API = договор между двумя программами:
   «Пришли мне ТАКОЙ запрос по ТАКОМУ адресу — я верну ТАКОЙ ответ»

Из чего состоит договор:
   АДРЕС     https://api.github.com/repos/khimeran/devops-portfolio
   МЕТОД     GET (прочитать) / POST (создать) / DELETE (удалить)…
   ЗАГОЛОВКИ кто я (токен), в каком формате шлю и жду ответ
   ТЕЛО      данные (обычно JSON) — для POST/PUT/PATCH
   ОТВЕТ     код статуса (200, 404, 500) + тело (обычно JSON)

⭐ Ключевая мысль: сайт и API — это ОДИН И ТОТ ЖЕ HTTP.
   Разница только в том, что сайт отдаёт HTML для глаз,
   а API отдаёт JSON для кода.
Виды API — что встретишь и чем отличаются
ТипКак выглядитГде встретишьОсобенность
REST / HTTP
99% случаев		 GET /api/v1/users/42 → JSON GitHub, Docker, Kubernetes, Prometheus, любое веб-приложение Ресурс = URL, действие = HTTP-метод. Читается глазами, тестируется curl
GraphQL Один URL /graphql, запрос описывает нужные поля GitHub v4, современные фронтенды Клиент сам решает, какие поля забрать — нет лишних данных, но сложнее кэшировать
gRPC Бинарный протокол поверх HTTP/2, схема в .proto Внутренние сервисы, k8s-компоненты, высоконагруженное Быстрый и строго типизированный, но curl его не прочитает — нужен grpcurl
SOAP / XML-RPC XML-конверты, WSDL-описание Легаси: банки, госуслуги, 1С, телеком Тяжёлый и многословный. Новое на нём не пишут, но поддерживать приходится
WebSocket wss://, соединение держится открытым Чаты, live-дашборды, стриминг логов Двусторонний канал: сервер может слать сам, не дожидаясь запроса
Webhook Обычный HTTP POST, но к тебе GitHub → CI, Alertmanager → Telegram, платёжки Перевёрнутый API: не ты спрашиваешь, а тебе присылают событие. Нужен публичный URL
Unix-socket API /var/run/docker.sock Docker, systemd, containerd Тот же HTTP, но через файл-сокет, а не через сеть
Главный вывод: научился REST + curl — умеешь работать с 90% инструментов DevOps. Остальные типы встречаются точечно, и подход к ним такой же: найти документацию, повторить один запрос руками, потом завернуть в скрипт.

Коды ответа — что они означают на практике
КодЗначениеЧто делать
200 OKВсё хорошо, ответ в теле—
201 CreatedОбъект создан, ссылка в заголовке Location—
204 No ContentСделано, но отвечать нечем (типично для DELETE)Не искать тело — его нет
301 / 308Переехало навсегдаИдти по новому адресу, curl -L. Браузер запомнит
302 / 307Временно тутТо же, но не кэшировать
304 Not ModifiedНе менялось с прошлого разаБрать из кэша (работает по ETag)
400 Bad RequestКривой запрос: сломан JSON, не тот типЧитать тело ответа — там написано, что не так
401 UnauthorizedЯ тебя не узнал: токена нет, протух, неверныйПроверить Authorization, обновить токен
403 ForbiddenУзнал, но тебе нельзя: не хватает правПрава/скоупы токена, RBAC. Токен менять бесполезно
404 Not FoundНет такого адреса или объектаПроверить путь, версию (/v1/), id
409 ConflictКонфликт: уже существует, версия устарелаПеречитать объект и повторить
422 UnprocessableФормат верный, но данные не проходят валидациюЛюбимый код FastAPI: в теле — список полей с ошибками
429 Too Many RequestsПревышен лимит запросовЖдать Retry-After, снизить темп
500 Internal ErrorУпало у них внутриСмотреть логи приложения
502 Bad GatewayПрокси не достучался до бэкенда⭐ Бэкенд лежит / не тот порт / SELinux. Логи nginx
503 UnavailableСервис временно недоступен, перегруженРетрай с backoff
504 Gateway TimeoutБэкенд жив, но не успел ответитьТяжёлый запрос или proxy_read_timeout мал
Три пары, которые спрашивают на собеседовании:
• 401 vs 403 — «не знаю, кто ты» против «знаю, но нельзя».
• 502 vs 504 — «не смог соединиться с бэкендом» против «соединился, но ответа не дождался». Разбор со стороны nginx — в разделе nginx.
• 4xx vs 5xx — 4xx это твоя вина (запрос кривой), 5xx — их (сервер сломался). Начинать чинить нужно с разных сторон.

curl — главный инструмент: флаги и отладка

curl — это «сделай HTTP-запрос из терминала». Умеет всё, что умеет браузер, только без картинок и без CORS. В DevOps им проверяют живость сервисов, дёргают API, отлаживают редиректы и TLS.

BASH Боевые примеры на каждый день 
# GET с параметрами (кавычки обязательны — иначе & уведёт в фон!)
curl -s "http://localhost:8000/topics?limit=10&page=2"

# ⭐ POST с JSON — классическая связка
curl -sS -X POST http://localhost:8000/topics \
  -H "Content-Type: application/json" \
  -d '{"title":"Ansible","progress":40}'

# то же самое, современно и короче:
curl -sS --json '{"title":"Ansible","progress":40}' http://localhost:8000/topics

# тело из файла (когда JSON большой):
curl -sS --json @payload.json http://localhost:8000/topics

# GET, но параметры из -d (curl сам склеит в query-строку):
curl -sG -d 'query=up' -d 'time=2026-08-08T12:00:00Z' \
  http://prometheus:9090/api/v1/query

# ⭐ Только код ответа — для мониторинга и CI:
curl -s -o /dev/null -w '%{http_code}\n' https://example.com/healthz

# ⭐ Где тормозит: DNS, коннект, TLS или сам сервер:
curl -s -o /dev/null -w \
  'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' \
  https://example.com

# ⭐⭐ Проверить НОВЫЙ сервер по боевому домену ДО переключения DNS:
curl -I --resolve example.com:443:203.0.113.10 https://example.com

# Загрузка файла (multipart, как форма в браузере):
curl -sS -F "file=@report.pdf" -F "comment=отчёт" http://localhost:8000/upload

# Скачать артефакт с проверкой ошибок и повторами:
curl -fsSL --retry 3 --retry-delay 2 -o app.tar.gz https://nexus/app-1.2.3.tar.gz

# Сохранить cookies и переиспользовать (сессионная авторизация):
curl -sc jar.txt -d 'user=admin&pass=secret' http://app/login
curl -sb jar.txt http://app/profile

JQ Ответ пришёл — как его разобрать 
# Красиво напечатать (без jq — питоном):
curl -s http://localhost:8000/topics | python3 -m json.tool
curl -s http://localhost:8000/topics | jq            # с подсветкой

# Достать одно поле:
curl -s http://api/user | jq -r '.login'             # -r = без кавычек

# Пройтись по массиву:
curl -s http://api/topics | jq -r '.[] | "\(.id)\t\(.title)"'

# Отфильтровать:
curl -s http://api/topics | jq '[.[] | select(.progress < 50)]'

# Сколько элементов:
curl -s http://api/topics | jq 'length'

# ⭐ Достать токен из ответа авторизации в переменную:
TOKEN=$(curl -s --json '{"user":"admin","pass":"secret"}' http://api/login | jq -r '.access_token')
curl -s -H "Authorization: Bearer $TOKEN" http://api/private
Частые грабли curl
1. curl http://api?a=1&b=2     → "&" уводит команду в фон!
   ✅ ВСЕГДА кавычки: curl "http://api?a=1&b=2"

2. -d '{"a":1}' без -H         → уйдёт как form-urlencoded, сервер вернёт 400/422
   ✅ -H "Content-Type: application/json" или --json

3. curl вернул 500, а скрипт продолжил работу
   ✅ -f (или --fail-with-body), иначе код возврата 0 на любой HTTP-ошибке

4. Токен прямо в командной строке
   ⚠️ попадёт в ~/.bash_history и в ps у соседних процессов
   ✅ -H "Authorization: Bearer $TOKEN" с export, или --netrc

5. -k «чтобы заработало»
   ⚠️ отключает проверку сертификата целиком = MITM возможен
   ✅ --cacert /path/ca.pem или добавить CA в систему

6. Одинарные кавычки внутри JSON с переменными bash
   ✅ либо --json @file.json, либо аккуратно: -d "{\"x\":\"$VAL\"}"

BASH Как это выглядит в командах 
# Basic:
curl -u admin:secret https://internal.example.com/metrics

# API-key заголовком (лучше, чем в URL):
curl -H "X-API-Key: $API_KEY" https://api.weather.example/v1/now

# ⭐ Bearer — самый частый вариант:
export TOKEN='eyJhbGciOiJIUzI1NiIs...'
curl -H "Authorization: Bearer $TOKEN" https://api.github.com/user

# OAuth2 client_credentials — «логин для машин»:
TOKEN=$(curl -s -X POST https://auth.example.com/oauth/token \
  -d 'grant_type=client_credentials' \
  -d "client_id=$CID" -d "client_secret=$CSECRET" | jq -r .access_token)

# mTLS — предъявляем свой сертификат:
curl --cert client.pem --key client-key.pem --cacert ca.pem https://api.internal/

# JWT — посмотреть, что внутри токена (он НЕ зашифрован, просто base64):
echo "$TOKEN" | cut -d. -f2 | base64 -d 2>/dev/null | jq
#   увидишь sub (кто), exp (когда протухнет), scope/roles (что можно)
#   ⚠️ раз содержимое читается кем угодно — секретов внутрь JWT не кладут
Гигиена токенов: не в URL (осядет в логах прокси), не в git (сканеры вроде gitleaks ловят это в pre-commit), не в history (используй переменные окружения или ~/.netrc с правами 600), у токена должен быть срок жизни и минимальный набор прав. Утёк — отзывать, а не «менять пароль потом». То же правило, что для секретов в IaC: eyaml/vault/ansible-vault существуют ровно для этого.

Как работать с незнакомым API

ПРОЦЕДУРА Порядок действий, который всегда работает 
1. НАЙТИ ДОКУМЕНТАЦИЮ. У 90% сервисов она машинная:
      /docs         Swagger UI (FastAPI даёт бесплатно) — можно кликать прямо там
      /redoc        та же схема, другой вид
      /openapi.json машинное описание всех эндпоинтов
      /api/v1/      часто отдаёт список доступных путей

2. ПОВТОРИТЬ ОДИН ЗАПРОС РУКАМИ через curl. Не писать код, пока
   в терминале не получил 200. ⭐ Половина проблем отваливается здесь.

3. РАЗОБРАТЬСЯ С АВТОРИЗАЦИЕЙ. 401 — токен; 403 — права.

4. ПРОЧИТАТЬ ПРО ПАГИНАЦИЮ. Почти всегда отдаётся не всё сразу.

5. УЗНАТЬ ЛИМИТЫ. 429 в проде посреди ночи — обидно.

6. ЗАВЕРНУТЬ В СКРИПТ. curl + jq, а лучше — готовый клиент/модуль
   (ansible uri, python requests, terraform provider).

# ── ПАГИНАЦИЯ — три распространённые схемы ──────────────────────
?page=2&per_page=100              страницами (GitHub)
?limit=100&offset=200             смещением (SQL-подобно)
?cursor=eyJpZCI6MTAwfQ            курсором (стабильно при вставках)

# Сколько всего — часто в заголовках:
Link: <https://api/repos?page=3>; rel="next", <…?page=9>; rel="last"

# Забрать ВСЁ в цикле:
page=1
while :; do
  data=$(curl -s -H "Authorization: Bearer $TOKEN" "https://api/items?page=$page&per_page=100")
  [ "$(echo "$data" | jq 'length')" -eq 0 ] && break
  echo "$data" | jq -r '.[].name'
  page=$((page+1))
done

CORS ⭐ «Из curl работает, из браузера — нет» 
Симптом в консоли браузера:
   Access to fetch at 'https://api.example.com/data' from origin
   'https://site.example.com' has been blocked by CORS policy

ЧТО ПРОИСХОДИТ:
   CORS — это ограничение БРАУЗЕРА, а не сервера и не сети.
   Браузер запрещает JS со страницы site.example.com читать ответы
   с ДРУГОГО домена, если тот явно не разрешил.
   ⭐ curl никаких CORS не знает — поэтому у тебя «в терминале работает».

КАК БРАУЗЕР ПРОВЕРЯЕТ (preflight):
   OPTIONS /data                       ← сначала спрашивает разрешение
   Origin: https://site.example.com
   Access-Control-Request-Method: POST
   ↓ сервер должен ответить:
   Access-Control-Allow-Origin: https://site.example.com
   Access-Control-Allow-Methods: GET, POST, OPTIONS
   Access-Control-Allow-Headers: Content-Type, Authorization

ЛЕЧЕНИЕ (в порядке правильности):
   1. ⭐ Отдавать фронт и API с ОДНОГО домена через nginx:
         /      → фронтенд
         /api/  → proxy_pass на бэкенд
      Тогда CORS вообще не возникает — origin один и тот же.
   2. Настроить CORS в приложении (FastAPI: CORSMiddleware).
   3. Прописать заголовки в nginx (если приложение трогать нельзя).
   ⛔ Allow-Origin: * на API с авторизацией — так не делают.

# Проверить preflight руками:
curl -i -X OPTIONS https://api.example.com/data \
  -H "Origin: https://site.example.com" \
  -H "Access-Control-Request-Method: POST"

API в работе DevOps: всё вокруг — API

Инструменты, которыми ты пользуешься каждый день, — это клиенты к HTTP-API. Понимая это, можно автоматизировать что угодно без ожидания «а есть ли для этого команда».

BASH Однострочники, которые реально пригождаются 
# ── DOCKER (API через unix-сокет) ───────────────────────────────
curl -s --unix-socket /var/run/docker.sock http://localhost/containers/json | jq -r '.[].Names[0]'
curl -s --unix-socket /var/run/docker.sock http://localhost/version | jq .ApiVersion
#   ⚠️ доступ к docker.sock = фактически root на хосте. Не монтировать в контейнеры бездумно.

# ── KUBERNETES ──────────────────────────────────────────────────
kubectl get pods -v=8                     # ⭐ показать, какой HTTP-запрос ушёл
kubectl proxy --port=8001 &               # локальный доступ без токенов
curl -s localhost:8001/api/v1/namespaces/default/pods | jq -r '.items[].metadata.name'

# ── PROMETHEUS (мониторинг — тоже просто HTTP) ──────────────────
curl -sG http://prometheus:9090/api/v1/query --data-urlencode 'query=up == 0' \
  | jq -r '.data.result[].metric.instance'          # ⭐ кто сейчас лежит
curl -s http://prometheus:9090/api/v1/targets | jq -r '.data.activeTargets[] | "\(.health)\t\(.labels.instance)"'

# ── ALERTMANAGER: заглушить алерты на время работ ───────────────

# ── GITHUB ──────────────────────────────────────────────────────

#   ⭐ Запустить workflow руками:

BASH Healthcheck-скрипт: как API проверяют в мониторинге 
#!/usr/bin/env bash
set -euo pipefail

URL="https://api.example.com/healthz"

# -f: HTTP-ошибка = ненулевой код возврата
# -s -S: тихо, но ошибки показать
# --max-time: не висеть вечно
# -w: забрать код и время ответа
read -r code time_total < <(
  curl -fsS --max-time 5 -o /tmp/body.json \
       -w '%{http_code} %{time_total}\n' "$URL"
) || { echo "CRITICAL: $URL недоступен"; exit 2; }

status=$(jq -r '.status' /tmp/body.json)

if [[ "$code" == "200" && "$status" == "ok" ]]; then
  echo "OK: $URL ответил за ${time_total}s"
  exit 0
else
  echo "WARNING: код=$code status=$status"
  exit 1
fi

# ⭐ Тот же принцип внутри: Prometheus blackbox_exporter, healthcheck
#    в docker-compose, readiness-проба в Kubernetes, приёмка в Ansible
#    (модуль uri с failed_when).

Шпаргалка и итог

CHEATSHEET Всё нужное на одном экране 
# ── ПРОВЕРИТЬ ───────────────────────────────────────────────────
curl -I URL                                только заголовки (жив? редиректит?)
curl -sS -o /dev/null -w '%{http_code}\n' URL   только код ответа
curl -v URL                                весь диалог: DNS → TLS → HTTP
curl -sIL URL | grep -E 'HTTP/|location'   ⭐ цепочка редиректов целиком

# ── ЗАПРОСЫ ─────────────────────────────────────────────────────
curl -s "URL?a=1&b=2"                       GET с параметрами (в кавычках!)
curl --json '{"k":"v"}' URL                 POST с JSON
curl -X DELETE URL -H "Authorization: Bearer $TOKEN"
curl -F 'file=@x.pdf' URL                   загрузка файла
curl -fsSL -o out.tgz URL                   надёжное скачивание

# ── РАЗОБРАТЬ ОТВЕТ ─────────────────────────────────────────────
| jq                     красиво
| jq -r '.field'         одно поле без кавычек
| jq -r '.[] | .name'    поле у каждого элемента массива
| jq 'length'            сколько элементов

# ── КОДЫ ────────────────────────────────────────────────────────
2xx хорошо · 3xx переехало · 4xx ТЫ не прав · 5xx ОНИ сломались
401 не узнал тебя   403 узнал, но нельзя
404 нет адреса      422 данные не прошли валидацию
429 сбавь темп      502 бэкенд недоступен   504 бэкенд не успел

# ── ОТЛАДКА ПО ПОРЯДКУ ──────────────────────────────────────────
1. dig домен          имя вообще резолвится?
2. curl -v            дошло до TLS? до HTTP?
3. curl -I            какой код и куда редиректит?
4. логи nginx         запрос вообще долетел до сервера?
5. логи приложения    5xx — искать здесь
Итог темы: API — это договор: адрес + метод + заголовки + тело → код ответа + JSON. 99% того, что встретишь, — REST поверх обычного HTTP, поэтому curl с jq закрывают почти любую задачу. Ключевые различия, которые надо помнить: 401 vs 403, 502 vs 504, 4xx vs 5xx, идемпотентность методов (POST ретраить нельзя без Idempotency-Key). Авторизация — почти всегда Authorization: Bearer, токен держать в переменной окружения, а не в URL и не в git. «Из curl работает, а из браузера нет» — это CORS, и правильное лечение чаще всего архитектурное: отдавать фронт и API с одного домена через nginx. И главное — всё вокруг API: kubectl, docker, terraform, Prometheus внутри делают ровно те же HTTP-запросы, которые ты умеешь повторить руками.
