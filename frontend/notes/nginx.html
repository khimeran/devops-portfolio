🟢 nginx — веб-сервер и reverse proxy

nginx — программа, которая слушает TCP-порт и отвечает на HTTP-запросы. То же делают Python http.server, Apache, Node Express, Go net/http — но nginx сделан под высокую нагрузку и обычно стоит перед другими приложениями (reverse proxy). Этот блок: модель процессов, конфиги, server/location, proxy_pass, балансировка, SSL, SELinux-ловушка на Fedora, а в конце — два практических раздела: как выложить приложение в интернет (белый IP, проброс портов, туннели, VPN) и почему тебя перекидывает на другой адрес или порт.

Модель процессов

FLOW Что происходит при systemctl start nginx 
1. systemd запускает /usr/sbin/nginx (от root — нужно чтобы привязаться к :80)
2. nginx форкается в МАСТЕР-процесс
3. Мастер читает /etc/nginx/nginx.conf
4. Мастер форкает РАБОЧИЕ процессы (workers) —
   по одному на ядро CPU (worker_processes auto)
5. Мастер дальше следит за воркерами, перечитывает конфиг по reload
6. Воркеры слушают порты, сразу понижают права до юзера nginx
   ⭐ безопасность: дыра в воркере = атакующий получит права nginx,
   а не root

# Проверь:
ps -ef | grep nginx
# увидишь: 1 master + N workers (N = nproc)

Структура файлов

PATHS Где что лежит на Fedora/RHEL 
/usr/sbin/nginx           бинарник
/etc/nginx/               конфиги, ты их редактируешь
   nginx.conf             корневой
   conf.d/*.conf          ⭐ СЮДА кладёшь свои server-блоки
   default.d/*.conf       в дефолтный server-блок добавочные location'ы
   mime.types             расширение → MIME-тип

/var/log/nginx/
   access.log             ⭐ каждый запрос — строка
   error.log              ⭐ ошибки конфига и обработки
/var/cache/nginx/         кэш (если включён)

#    /etc/nginx/sites-available/  +  /etc/nginx/sites-enabled/
#    (симлинки between them, аналог /etc/systemd/system/*.wants/)

Структура конфига

HIERARCHY Блоки nginx.conf 
main context (глобальные настройки)
  ├─ user nginx;                       воркеры от этого юзера
  ├─ worker_processes auto;            по одному на ядро
  └─ events { worker_connections 1024; }  каждый воркер тянет 1024 коннекта
       # 4 ядра × 1024 = ~4096 одновременных соединений

  http {
       sendfile on;                    ⭐ zero-copy отдача статики (быстро)
       keepalive_timeout 65;           держать коннект 65 сек после ответа
       include /etc/nginx/mime.types;

       log_format main '$remote_addr - $remote_user [$time_local] ...';
       access_log /var/log/nginx/access.log main;

       server {                        ВИРТУАЛЬНЫЙ ХОСТ (сайт)
           listen 80;
           server_name example.com;
           root /var/www/example;

           location / { ... }          КАК обрабатывать конкретный путь
           location /api/ { ... }
       }

       include /etc/nginx/conf.d/*.conf;    ⭐ подгрузить твои конфиги
  }

Как nginx выбирает server и location

VIRTUAL HOSTS Несколько сайтов на одном IP 
# На один порт может слушать несколько server { } блоков:
server {
    listen 80;
    server_name example.com;       ← если Host: example.com → сюда
    root /var/www/example;
}
server {
    listen 80;
    server_name kirill.dev;        ← если Host: kirill.dev → сюда
    root /var/www/kirill;
}
server {
    listen 80 default_server;
    server_name _;                 ← всё, что не подошло → сюда
    root /usr/share/nginx/html;
}

# nginx смотрит ЗАГОЛОВОК Host: в HTTP-запросе (его шлёт браузер всегда)
# и выбирает подходящий server. На одном IP — сотни сайтов.
LOCATION Правила выбора внутри server 
location = /exact          ТОЧНОЕ совпадение — самый высокий приоритет
location ^~ /assets/       префикс, не проверять регулярки после
location ~ \.php$          регулярка, регистрозависимая
location ~* \.(png|jpg)$   регулярка, БЕЗ учёта регистра
location /api/             обычный префикс — самый длинный выигрывает
location /                 «всё остальное», fallback

# Алгоритм:
# 1. Точное совпадение (=) — если есть, ВЫИГРАЛО, стоп.
# 2. Префиксы с ^~ — если есть, регулярки не смотрим.
# 3. Регулярки (~ и ~*) — по порядку записи.
# 4. Обычные префиксы — самый длинный выигрывает.

Reverse proxy через proxy_pass

EXAMPLE Передача запросов бэкенду 
location /api/ {
    proxy_pass http://127.0.0.1:9000/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
⚠️ Слэш в proxy_pass — главная грабля nginx:
proxy_pass http://backend:9000/; (со слэшем) — УДАЛИТЬ /api/ из URL, передать остаток. Запрос /api/users уйдёт бэкенду как /users.
proxy_pass http://backend:9000; (без слэша) — оставить путь как есть. Запрос /api/users уйдёт как /api/users.
Запомни: есть слэш = подменить префикс, нет слэша = оставить весь путь.
HEADERS Зачем proxy_set_header 
По умолчанию бэкенд видит:
   Host: имя из proxy_pass (т.е. "127.0.0.1:9000")
   IP клиента: IP nginx'а (т.е. 127.0.0.1)
   Схема: всегда HTTP, не HTTPS

⭐ Это часто ЛОМАЕТ приложение:
   — генерация ссылок будет на "127.0.0.1:9000"
   — логи будут показывать nginx как клиента
   — приложение не знает, что снаружи был HTTPS

Поэтому стандартный набор заголовков:
   proxy_set_header Host $host;
                    ← передать оригинальный Host: ("example.com")
   proxy_set_header X-Real-IP $remote_addr;
                    ← реальный IP клиента
   proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
                    ← цепочка прокси (если их несколько)
   proxy_set_header X-Forwarded-Proto $scheme;
                    ← была ли изначально HTTPS-схема

# Приложение (FastAPI, Django) умеет читать эти заголовки
# через middleware (например, TrustedHostMiddleware + ProxyHeadersMiddleware).

SELinux-ловушка на Fedora

SYMPTOM 502 Bad Gateway при правильном конфиге 
# Конфиг правильный, бэкенд жив:
curl http://127.0.0.1:9000/      ✓ работает напрямую
curl http://localhost:8080/api/  ✗ 502 Bad Gateway

# В /var/log/nginx/error.log:
connect() to 127.0.0.1:9000 failed (13: Permission denied)
                                    ↑ это SELinux, не файловые права!

# Причина: SELinux запрещает nginx делать ИСХОДЯЩИЕ TCP-соединения.
# Политика httpd_t не пускает в обычные порты.

# Лечение:
sudo setsebool -P httpd_can_network_connect on
                ↑ -P = persistent (сохранить через ребут)

# Проверка:
getsebool httpd_can_network_connect       # должно: on

# Альтернатива (для конкретного порта):
sudo semanage port -a -t http_port_t -p tcp 9000

Балансировка нагрузки через upstream

EXAMPLE Несколько бэкендов за одним nginx 
http {
    upstream backend {
        server 127.0.0.1:9000;
        server 127.0.0.1:9001;
        server 127.0.0.1:9002 weight=2;        ← в 2 раза больше нагрузки
        server backup.local:9000 backup;        ← резерв, если все основные упали

        # Алгоритм:
        # (по умолчанию) round-robin — по очереди
        # least_conn;      — кому меньше всего соединений
        # ip_hash;         — один клиент всегда на один сервер (sticky)
        # hash $request_uri consistent;  — по URL (для кэшей)

        # Таймауты:
        keepalive 32;     ← держать 32 коннекта к каждому бэкенду
    }

    server {
        listen 8080;
        location / {
            proxy_pass http://backend;          ← упомянуть имя из upstream
            proxy_set_header Host $host;
        }
    }
}

# Если бэкенд не ответил — nginx сам перенаправит к следующему,
# и пометит мёртвый как недоступный на fail_timeout (по умолчанию 10 сек).

SSL/TLS — HTTPS на nginx

EXAMPLE Минимальный HTTPS-блок 
server {
    listen 443 ssl;
    listen [::]:443 ssl;
    http2 on;
    server_name example.com;

    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

    # Рекомендованная Mozilla конфигурация:
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers HIGH:!aNULL:!MD5;
    ssl_prefer_server_ciphers off;
    ssl_session_cache shared:SSL:10m;
    ssl_session_timeout 1d;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

# Редирект с HTTP на HTTPS:
server {
    listen 80;
    server_name example.com;
    return 301 https://$host$request_uri;
}

# Сертификаты — через Let's Encrypt:
sudo dnf install certbot python3-certbot-nginx
sudo certbot --nginx -d example.com
# certbot сам пропишет конфиг и поставит автообновление

Базовые команды управления

BASH Чеклист действий 
sudo nginx -t                          # ⭐ ПЕРВОЕ что делать после правки
                                       # проверка синтаксиса, не применяет

                                       # (включая все include)

# Принудительно отправить SIGHUP мастеру (то же что reload):
sudo nginx -s reload
sudo nginx -s stop                     # быстрый стоп
sudo nginx -s quit                     # graceful — дать доработать запросам

🌍 Выложить приложение в интернет: от localhost до домена

Приложение крутится на localhost:8000 и надо, чтобы оно открывалось по адресу myapp.ru из любой точки мира. Задача выглядит как одна, а на самом деле это цепочка из шести звеньев — и «не работает» почти всегда означает, что порвано ровно одно из них.

⭐ ЦЕПОЧКА Шесть звеньев — по ним и надо идти при отладке 
1. ПРОЦЕСС СЛУШАЕТ
   Приложение реально принимает соединения — и на нужном адресе.
   ss -tlnp | grep 8000
   ⚠️ Слушает 127.0.0.1:8000 → доступно ТОЛЬКО с самой машины.
      Чтобы пустить снаружи, нужен 0.0.0.0:8000 —
      но правильнее оставить 127.0.0.1 и поставить впереди nginx.

2. ЛОКАЛЬНЫЙ FIREWALL ПУСКАЕТ
   firewall-cmd --list-all → порты 80/443 открыты?

3. ТРАФИК ИЗ ИНТЕРНЕТА ДОХОДИТ ДО МАШИНЫ
   ⭐ Самое сложное звено. Здесь решается: белый IP, проброс на роутере,
      туннель или VPN. Про него — весь этот раздел ниже.

4. ИМЯ ПРЕВРАЩАЕТСЯ В АДРЕС (DNS)
   A-запись myapp.ru → твой публичный IP.
   dig +short myapp.ru

5. NGINX УЗНАЁТ СВОЙ САЙТ
   Запрос приходит с заголовком Host: myapp.ru — должен быть
   server { server_name myapp.ru; }, иначе попадёшь в default_server.

6. HTTPS
   Сертификат на это имя (certbot), и редирект 80 → 443.

# Порвано звено 1 или 2 → «connection refused»
# Порвано звено 3       → бесконечное ожидание, таймаут
# Порвано звено 4       → «не удалось найти сервер» / NXDOMAIN
# Порвано звено 5       → открылась «Welcome to nginx» или чужой сайт
# Порвано звено 6       → «Ваше подключение не защищено»

Шаг нулевой: узнай, какой у тебя случай

Всё дальнейшее зависит от одного вопроса: может ли интернет сам к тебе достучаться. Проверяется за минуту.

BASH Есть ли у меня белый (публичный) IP 
# 1. Какой IP видит интернет:
curl -s ifconfig.me ; echo
curl -s https://api.ipify.org ; echo

# 2. Какой IP на самом деле у машины/роутера:
ip -4 addr show | grep inet

# ⭐ СРАВНИВАЕМ:
#   Совпали → у тебя БЕЛЫЙ IP прямо на машине (типично для VPS).
#   Не совпали, а локальный адрес из диапазонов
#      10.x.x.x / 172.16–31.x.x / 192.168.x.x
#   → ты за NAT (домашний роутер). Нужен проброс портов на роутере.
#   Локальный адрес 100.64.x.x – 100.127.x.x
#   → ⚠️ CGNAT: белого IP нет даже у роутера, провайдер раздаёт один
#     адрес на сотни абонентов. Проброс портов НЕВОЗМОЖЕН —
#     только туннель (варианты C и D ниже) или белый IP за доплату.

# 3. Проверить снаружи, виден ли порт (с телефона по мобильному интернету
#    или через онлайн-сервис проверки портов):
curl -v --max-time 5 http://ТВОЙ_ПУБЛИЧНЫЙ_IP/
#    «Connection refused» — дошли, но никто не слушает (звено 1–2)
#    «Connection timed out» — не дошли вообще (звено 3: NAT/провайдер/фаервол)
Пять рабочих схем публикации — выбери свою
СхемаКогда подходитНужен белый IPКому будет видноСложность
A. VPS с nginxВсегда, когда нужен публичный сайт. Эталонный путьда, даёт хостервсему интернетунизкая
B. Свой сервер + проброс портовЖелезо дома/в офисе, провайдер даёт белый IPда, на роутеревсему интернетусредняя
C. Туннель (Cloudflare Tunnel)CGNAT, серый IP, «не хочу открывать порты»нетвсему интернетунизкая
D. VPS + VPN/SSH-туннельСвой сервер дома, но точка входа — арендованный VPSтолько у VPSвсему интернетувысокая
E. Tailscale / WireGuardДоступ только себе и коллегам, публиковать не нужнонеттолько своим устройствамочень низкая

Схема A — VPS с белым IP (эталон, с него стоит начинать)

BASH Полный путь: пустая VPS → рабочий https://myapp.ru 
# 1. Приложение слушает ТОЛЬКО локально — наружу его пустит nginx:
#    uvicorn app.main:app --host 127.0.0.1 --port 8000
ss -tlnp | grep 8000        # LISTEN 127.0.0.1:8000  ✅

# 2. Открыть 80 и 443 (и НЕ открывать 8000!):
sudo firewall-cmd --add-service=http --add-service=https --permanent
sudo firewall-cmd --reload

# 3. DNS: у регистратора домена создать A-запись
#      myapp.ru      A    203.0.113.10     (IP твоей VPS)
#      www.myapp.ru  A    203.0.113.10
#    Проверить (⚠️ обновление занимает от минут до часов — это TTL):
dig +short myapp.ru
#    ⭐ Пока DNS не обновился, тестировать можно так:
curl -I --resolve myapp.ru:80:203.0.113.10 http://myapp.ru

# 4. nginx: положить конфиг сайта (файл ниже) и проверить:
sudo nginx -t && sudo systemctl reload nginx

# 5. HTTPS — certbot всё сделает сам:
sudo dnf install -y certbot python3-certbot-nginx
sudo certbot --nginx -d myapp.ru -d www.myapp.ru
#    Он проверит владение доменом (ACME http-01: положит файл в /.well-known/),
#    выпустит сертификат, ПЕРЕПИШЕТ конфиг под 443 и добавит редирект с 80.
#    Автопродление уже настроено таймером:
systemctl list-timers | grep certbot
sudo certbot renew --dry-run       # репетиция продления

# 6. Проверка снаружи:
curl -I https://myapp.ru
curl -sIL http://myapp.ru | grep -E 'HTTP/|location'   # цепочка редиректов
NGINX /etc/nginx/conf.d/myapp.conf — базовый рабочий конфиг 
server {
    listen 80;
    server_name myapp.ru www.myapp.ru;

    # ⭐ до выпуска сертификата certbot кладёт проверочный файл сюда —
    #    поэтому редирект на https ставят ПОСЛЕ получения сертификата
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    listen [::]:443 ssl;
    http2 on;
    server_name myapp.ru www.myapp.ru;

    ssl_certificate     /etc/letsencrypt/live/myapp.ru/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/myapp.ru/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;

    access_log /var/log/nginx/myapp.access.log;
    error_log  /var/log/nginx/myapp.error.log;

    # Статика фронтенда — отдаёт сам nginx, это быстро
    location / {
        root /var/www/myapp;
        try_files $uri $uri/ /index.html;   # SPA: неизвестные пути → index.html
    }

    # ⭐ API на ТОМ ЖЕ домене — и никакого CORS не возникнет
    location /api/ {
        proxy_pass http://127.0.0.1:8000/;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;   # ⭐ иначе приложение
                                                       # будет строить http-ссылки
        proxy_read_timeout 60s;             # долгие запросы → иначе 504
    }

    # WebSocket (live-логи, чаты) — без этих двух строк соединение рвётся
    location /ws/ {
        proxy_pass http://127.0.0.1:8000/ws/;
        proxy_http_version 1.1;
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}

Схема B — свой железный сервер дома или в офисе

СХЕМА Как трафик доходит до машины за роутером 
Интернет
   │  запрос на 203.0.113.10:443   (белый IP роутера)
   ▼
РОУТЕР провайдера           ← ⭐ здесь настраивается ПРОБРОС ПОРТОВ
   │  Port Forwarding / Virtual Server / NAT:
   │     внешний 443  →  192.168.1.50:443
   ▼
192.168.1.50  (твой сервер)  ← ⭐ обязательно СТАТИЧЕСКИЙ локальный адрес
   │                             (или DHCP-резервация по MAC на роутере)
   ├─ firewalld: 80/443 открыты
   ├─ nginx: server_name myapp.ru → proxy_pass 127.0.0.1:8000
   └─ приложение на 127.0.0.1:8000

ПОШАГОВО:
 1. Дать серверу постоянный локальный IP (резервация по MAC на роутере).
 2. На роутере: Port Forwarding 80→192.168.1.50:80 и 443→192.168.1.50:443.
 3. Убедиться, что провайдер не блокирует входящие 80/443
    (у домашних тарифов иногда блокируют — тогда схема C или D).
 4. IP от провайдера обычно ДИНАМИЧЕСКИЙ — нужен DDNS,
    иначе домен «отвалится» после переподключения:
       ddclient / inadyn / скрипт от Cloudflare API по крону
    Схема: домашний IP сменился → скрипт обновляет A-запись → домен снова живой.
 5. Дальше всё как в схеме A: DNS → nginx → certbot.

⚠️ ЧТО ОБЯЗАТЕЛЬНО ПЕРЕД ПУБЛИКАЦИЕЙ ДОМАШНЕГО СЕРВЕРА:
   - SSH только по ключам, PasswordAuthentication no, root-логин запрещён
   - наружу торчат ТОЛЬКО 80/443. SSH — не на 22 наружу, а лучше вообще
     через VPN (схема E)
   - fail2ban на sshd и nginx
   - автообновления безопасности (dnf-automatic)
   - сервер в отдельной подсети/VLAN, если в той же сети домашние устройства
   - бэкапы: публичный сервер = мишень

Схема C — туннель, когда белого IP нет (CGNAT)

Идея: сервер сам устанавливает исходящее соединение к публичному сервису, и трафик идёт обратно по этому же каналу. Входящие порты не нужны вообще — а значит, работает даже за CGNAT и без прав на роутер.

BASH Cloudflare Tunnel — «сервер сам звонит наружу» 
Как это выглядит:
   Клиент → Cloudflare (у них белые IP и TLS) → ↓ туннель ↓ → твой cloudflared
                                                              → localhost:8000
   ⭐ Твой сервер НИЧЕГО не слушает из интернета. Он сам держит соединение.

# Установка и подключение:
cloudflared tunnel login                       # откроет браузер, выберешь домен
cloudflared tunnel create myapp                # создаст туннель и креды
cloudflared tunnel route dns myapp myapp.ru    # заведёт DNS-запись автоматически

# ~/.cloudflared/config.yml
tunnel: myapp
credentials-file: /root/.cloudflared/<ID>.json
ingress:
  - hostname: myapp.ru
    service: http://localhost:8000
  - service: http_status:404          # обязательное правило-заглушка в конце

cloudflared tunnel run myapp                   # проверить руками
sudo cloudflared service install               # поставить как systemd-сервис

ПЛЮСЫ: не нужен белый IP и проброс портов; TLS-сертификат делает Cloudflare;
       твой реальный IP скрыт; защита от DDoS и ботов «в комплекте».
МИНУСЫ: зависимость от стороннего сервиса; весь трафик идёт через него;
       нужен домен, делегированный на Cloudflare.

# ⚡ Быстрый временный вариант «показать коллеге на 10 минут»:
cloudflared tunnel --url http://localhost:8000    # выдаст случайный *.trycloudflare.com
ssh -R 80:localhost:8000 serveo.net               # без установки чего-либо
#   ngrok http 8000 — то же самое, самый известный. ⚠️ Всё это — для демо,
#   не для прода: адрес меняется, лимиты, чужой сервис в середине.

Схема D — свой VPS как точка входа (когда хочется всё своё)

СХЕМА Дешёвый VPS с белым IP + туннель до домашнего сервера 
Идея: арендуешь самую дешёвую VPS ради белого IP. Она принимает трафик
и по защищённому каналу передаёт его домой. Свой «Cloudflare Tunnel»,
только полностью под контролем.

Интернет → VPS (белый IP, nginx + certbot)
             │  внутренний адрес туннеля 10.8.0.2
             ▼
       WireGuard / обратный SSH
             ▼
     домашний сервер (за CGNAT) → приложение :8000

── ВАРИАНТ 1: WireGuard (правильный, стабильный) ────────────────
# На VPS и дома поднимается VPN, у каждого адрес в сети 10.8.0.0/24.
# После этого на VPS в nginx просто:
location / {
    proxy_pass http://10.8.0.2:8000;      # ⭐ домашний сервер как соседняя машина
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
}
# Плюс: канал держится сам, переживает разрывы, низкие задержки (UDP).

── ВАРИАНТ 2: обратный SSH-туннель (быстро, для начала) ─────────
# ЗАПУСКАЕТСЯ НА ДОМАШНЕМ СЕРВЕРЕ:
ssh -N -R 127.0.0.1:8080:127.0.0.1:8000 tunnel@vps.example.com
#        │  └ на VPS появится порт 8080, ведущий к нам на 8000
#        └ -N: только туннель, без шелла
# На VPS: proxy_pass http://127.0.0.1:8080;
# ⚠️ Чтобы не падало — autossh + systemd-юнит:
#    autossh -M 0 -N -o ServerAliveInterval=30 -o ServerAliveCountMax=3 #            -R 127.0.0.1:8080:127.0.0.1:8000 tunnel@vps.example.com
# ⚠️ GatewayPorts на VPS оставить выключенным: пусть порт слушается только
#    на 127.0.0.1, наружу отдаёт nginx с TLS, а не голый туннель.

Про -L и -R подробнее — в разделе Сеть и SSH.

Схема E — Tailscale/WireGuard: не публиковать вообще

BASH Когда доступ нужен только тебе и коллегам 
⭐ Самый недооценённый вариант. Прежде чем выставлять сервис в интернет,
   спроси: а он вообще должен быть публичным? Панель мониторинга,
   Grafana, тестовый стенд, домашний NAS — почти никогда.

TAILSCALE (WireGuard с автоматикой, ставится за 2 минуты):
   curl -fsSL https://tailscale.com/install.sh | sh
   sudo tailscale up
   # То же на ноутбуке и телефоне. Готово: устройства видят друг друга
   # по адресам 100.x.x.x, где бы физически ни находились.
   # NAT, CGNAT, разные страны — Tailscale пробивает соединение сам.

   tailscale status                       # кто в сети
   tailscale ip -4                        # мой адрес в сети
   # Приложение доступно как http://100.101.102.103:8000 — только своим.

   ⭐ MagicDNS: обращаться по имени машины — http://homeserver:8000
   ⭐ tailscale serve / funnel — отдать сервис по HTTPS внутри сети,
      а при желании и наружу, без своего домена и сертификатов.

ЧИСТЫЙ WIREGUARD (без сторонних сервисов, но настраивать руками):
   wg genkey | tee privatekey | wg pubkey > publickey
   # /etc/wireguard/wg0.conf на обеих сторонах, ключи, AllowedIPs
   systemctl enable --now wg-quick@wg0
   # Нужен хотя бы один узел с белым IP (обычно VPS) как точка встречи.

СРАВНЕНИЕ:
   Tailscale  — быстро, работает везде, зависит от их координационного сервера
   WireGuard  — полностью своё, нужен белый IP у одного узла и ручная настройка
   VPN ≠ публикация: сервис остаётся невидимым для интернета. Это самая
   безопасная схема — публиковать имеет смысл только то, что ДОЛЖНО быть публичным.
Как выбрать за 10 секунд: нужен публичный сайт и есть немного денег → VPS (A). Есть железо и белый IP → проброс портов (B). Провайдер за CGNAT или порты закрыты → Cloudflare Tunnel (C). Хочется всё своё и железо дома → дешёвая VPS + WireGuard (D). Нужно только себе → Tailscale (E), и не выставляй наружу вообще ничего.

🧭 Куда меня перекидывает: DNS → 443 → Host → редиректы

«Захожу по адресу, а меня куда-то пробрасывает и открывается не то» — самый частый вопрос новичка. Разберём весь путь запроса по шагам: где именно принимается решение, куда тебя отправить.

⭐ ПУТЬ ЗАПРОСА Что происходит между «ввёл адрес» и «увидел страницу» 
Ты вводишь:  myapp.ru

1. БРАУЗЕР ДОСТРАИВАЕТ СХЕМУ
   Современные браузеры сразу пробуют https://myapp.ru
   (а если в списке HSTS-preload — то только https, без вариантов).
   ⭐ Отсюда ощущение «меня пробрасывают на 443» — это ещё до сети.

2. DNS: ИМЯ → IP
   myapp.ru → A-запись → 203.0.113.10
   (CNAME может увести на другое имя, а оно — уже на IP)
   dig +short myapp.ru

3. TCP-СОЕДИНЕНИЕ на порт 443
   Порт берётся из схемы: https → 443, http → 80.
   Если в адресе явно указан порт (myapp.ru:8443) — берётся он.

4. TLS-HANDSHAKE + SNI                    ⭐ ключевой момент
   Сертификатов на одном IP может быть много, поэтому клиент
   в открытом виде сообщает, к КАКОМУ имени идёт — это SNI.
   По нему nginx выбирает, каким сертификатом отвечать.

5. HTTP-ЗАПРОС с заголовком Host
   GET / HTTP/1.1
   Host: myapp.ru                          ⭐ по нему nginx выбирает server{}

6. NGINX ВЫБИРАЕТ server { }
   server_name совпал → этот сайт.
   Не совпал ни один → default_server (или первый в конфиге)
   ⭐ Вот почему иногда открывается «Welcome to nginx» или ЧУЖОЙ сайт.

7. NGINX ВЫБИРАЕТ location { }
   → отдать файл (root/try_files) или передать бэкенду (proxy_pass)

8. ОТВЕТ
   200 — страница; 301/302 — «иди по другому адресу» (и браузер идёт);
   502/504 — бэкенд недоступен или не успел.
РЕДИРЕКТЫ Кто и зачем тебя перенаправляет 
ИСТОЧНИК 1 — nginx, редирект 80 → 443 (самый частый)
   server { listen 80; return 301 https://$host$request_uri; }
   Именно эту строку добавляет certbot. Ты стучишься на 80 —
   тебя вежливо отправляют на 443. Это норма.

ИСТОЧНИК 2 — nginx, нормализация имени
   return 301 https://myapp.ru$request_uri;    # www → без www (или наоборот)
   ⭐ Делают, чтобы у сайта был ОДИН канонический адрес.

ИСТОЧНИК 3 — HSTS (сервер сказал «сюда только по https»)
   add_header Strict-Transport-Security "max-age=31536000" always;
   Браузер ЗАПОМИНАЕТ это на год и больше даже не пробует http.
   ⚠️ Отсюда «редиректит на https, хотя я убрал редирект из конфига» —
      это кэш браузера, а не сервер. Чистится в chrome://net-internals/#hsts

ИСТОЧНИК 4 — САМО ПРИЛОЖЕНИЕ
   Не авторизован → 302 на /login. Старый путь → 301 на новый.
   ⭐ Если приложение редиректит на http:// вместо https:// —
      значит, ему не передали X-Forwarded-Proto (см. блок про заголовки).

ИСТОЧНИК 5 — nginx добавляет слэш к каталогу
   Запрос /admin → 301 на /admin/ . Это штатное поведение.

ИСТОЧНИК 6 — CDN / Cloudflare
   Может добавить свои редиректы и правила ещё до твоего сервера.

⚠️ ERR_TOO_MANY_REDIRECTS (петля) — классика:
   nginx редиректит 80 → 443, а перед ним стоит Cloudflare в режиме
   «Flexible», который ходит к тебе по http. Получается кольцо.
   Лечение: режим Full (strict) на стороне CDN.
BASH ⭐ Диагностика: где именно меня разворачивает 
# 1. Куда указывает имя (и указывает ли вообще):
dig +short myapp.ru
dig myapp.ru A +noall +answer
#    пусто → проблема в DNS, дальше идти бессмысленно

# 2. ⭐ ВСЯ ЦЕПОЧКА РЕДИРЕКТОВ ОДНОЙ КОМАНДОЙ:
curl -sIL http://myapp.ru | grep -E '^HTTP/|^[Ll]ocation:'
#    HTTP/1.1 301 Moved Permanently
#    Location: https://myapp.ru/          ← первый прыжок
#    HTTP/2 200                           ← финиш
#    ⭐ Видно каждый шаг и кто его сделал

# 3. Полный диалог, включая TLS и SNI:
curl -v https://myapp.ru 2>&1 | head -30

# 4. Проверить КОНКРЕТНЫЙ сервер, минуя DNS
#    (переезд, тест нового сервера, подозрение на кэш):
curl -I --resolve myapp.ru:443:203.0.113.10 https://myapp.ru

# 5. Какой сертификат и на какие имена он выдан:
echo | openssl s_client -connect myapp.ru:443 -servername myapp.ru 2>/dev/null   | openssl x509 -noout -subject -dates -ext subjectAltName
#    ⭐ -servername = тот самый SNI. Без него можно получить ЧУЖОЙ
#       сертификат — сервер отдаст дефолтный.

# 6. Какой server{} на самом деле отвечает — подсунуть Host руками:
curl -I -H 'Host: myapp.ru' http://127.0.0.1/
#    ⭐ Так проверяют server_name прямо на машине, без DNS и интернета

# 7. Что реально в конфиге (со всеми include):
sudo nginx -T | grep -n -E 'server_name|listen|return 30|proxy_pass'

# 8. Долетел ли запрос до сервера вообще:
sudo tail -f /var/log/nginx/access.log
#    записи нет → тебя развернуло РАНЬШЕ: браузер, DNS, CDN, HSTS

Правило отладки: идти снаружи внутрь и на каждом шаге спрашивать «долетело сюда или нет». DNS → TCP → TLS → Host → server_name → location → бэкенд. Как только нашёл шаг, где запрос пропадает, — там и проблема; всё, что дальше, чинить бессмысленно. Про то, как читать коды ответов и curl -v, — в разделе API.
Итог темы: nginx — мастер + воркеры, по одному на ядро. Конфиг в /etc/nginx/nginx.conf, свои файлы — в conf.d/. Структура: http → server → location. «Welcome to nginx» — это /usr/share/nginx/html/index.html. server выбирается по Host:, location — по правилам приоритета (точное → префикс с ^~ → регулярки → обычный префикс). proxy_pass со слэшем подменяет префикс, без слэша — оставляет путь как есть. Бэкенду нужны заголовки X-Real-IP, X-Forwarded-Proto, Host. На Fedora — обязательно setsebool -P httpd_can_network_connect on, иначе 502 при правильном конфиге. Балансировка через upstream с алгоритмами round-robin/ip_hash/least_conn. HTTPS — certbot --nginx делает всё сам. Перед reload — всегда nginx -t. Публикация наружу — это цепочка из шести звеньев (процесс → firewall → маршрут снаружи → DNS → server_name → TLS), и способ прокинуть трафик выбирается по одному вопросу: есть ли белый IP. «Меня перекидывает» — это почти всегда 301 с 80 на 443, HSTS в кэше браузера или несовпавший server_name; разбирается связкой dig + curl -sIL + nginx -T.
