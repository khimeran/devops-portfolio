Git — система контроля версий

Git запоминает каждое изменение файлов. Как "сохранение игры" — в любой момент можно вернуться к любой точке истории.

Основные команды

BASH Добавить файл в список для сохранения 
git add README.md        # добавить конкретный файл
git add backend/         # добавить всю папку
git add .                # добавить все изменённые файлы
BASH Создать сохранение (коммит) 
git commit -m "описание изменений"
# -m означает message (сообщение)
# описание пишем кратко и по делу
BASH Отправить на GitHub 
git push                 # отправить текущую ветку
git push origin main     # явно указать: ветка main → сервер origin
BASH Проверить состояние и адреса 
git status               # что изменено, что добавлено
git remote -v            # показать адрес GitHub (origin)

Типичные ошибки

Authentication failed — ошибка авторизации
remote: No anonymous write access.
fatal: Authentication failed

Причина: токен не сохранён или устарел.

Решение
git config --global credential.helper store
GIT_TERMINAL_PROMPT=1 GIT_ASKPASS="" git push
# Ввести логин и токен — сохранится автоматически
refusing to allow — нет прав на workflow
refusing to allow a Personal Access Token to create or update workflow

Причина: токен не имеет права изменять GitHub Actions файлы.

Решение

Зайди на GitHub → Settings → Developer settings → Tokens. Добавь галочку workflow к токену.

Запомни: origin — это не коммит и не ветка. Это просто сохранённый адрес GitHub репозитория. Можно проверить: git remote -v

Docker — контейнеризация

Docker упаковывает приложение со всеми зависимостями в контейнер. Контейнер работает одинаково на любом компьютере — у тебя, у коллеги, на сервере.

Аналогия: Контейнер — как коробка с пиццей. Внутри всё что нужно: тесто, начинка, соус. Открыл коробку в любом месте — пицца одинаковая.

Dockerfile — инструкция сборки

DOCKERFILE backend/Dockerfile 
FROM python:3.12-slim
# FROM — взять готовый образ как основу
# python:3.12-slim — Python 3.12, slim = облегчённая версия

WORKDIR /app
# WORKDIR — все команды выполнять в /app внутри контейнера

COPY requirements.txt .
# COPY откуда куда
# . означает текущую папку = /app

RUN pip install -r requirements.txt
# RUN — выполнить команду во время сборки
# pip — менеджер пакетов Python

COPY . .
# копировать весь код — делаем после pip install
# чтобы при изменении кода не переустанавливать библиотеки

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
# CMD — запустить при старте контейнера
# 0.0.0.0 — слушать все сетевые интерфейсы

Основные команды

BASH Управление контейнерами 
docker ps                    # запущенные контейнеры
docker ps -a                 # все включая остановленные
docker logs имя_контейнера   # логи контейнера
docker volume ls             # список volumes
docker volume prune          # удалить неиспользуемые volumes

Типичные ошибки

Permission denied — нет доступа к папке
ls: cannot open directory '/docker-entrypoint-initdb.d/': Permission denied

Причина: SELinux блокирует доступ контейнера к папке на хосте (Fedora).

Решение — добавить :z к volume
volumes:
  - ./db:/docker-entrypoint-initdb.d:z
# :z — метка для SELinux: разреши контейнеру читать папку
Port already in use — порт занят
failed to bind host port 0.0.0.0:3000/tcp: address already in use

Причина: другая программа уже использует этот порт.

Решение — найти и сменить порт
ss -tlnp | grep 3000    # найти что занимает порт

# изменить левый порт в docker-compose.yml
ports:
  - "3030:3000"   # Grafana теперь на localhost:3030
Запомни: image: берёт готовый образ с Docker Hub, build: собирает из Dockerfile. Используй image для стандартных сервисов (PostgreSQL, Redis), build — только для своего кода.

Docker Compose — управление стеком

Docker Compose позволяет запустить несколько контейнеров одной командой. Все настройки описаны в одном файле docker-compose.yml.

Аналогия: Если Docker — это один повар, то Docker Compose — это ресторан с несколькими поварами. Один файл описывает всю кухню: кто что делает, как связан с другими.

Структура файла

YAML docker-compose.yml 
services:              # список всех сервисов
  backend:             # название сервиса (придумываем сами)
    build: ./backend   # собрать из Dockerfile в папке backend/
    ports:
      - "8000:8000"    # левое:правое = хост:контейнер
    depends_on:
      - db             # запускать только после db и redis
      - redis

  db:
    image: postgres:16     # готовый образ с Docker Hub
    environment:           # переменные окружения
      POSTGRES_USER: devops
      POSTGRES_PASSWORD: devops
      POSTGRES_DB: portfolio
    ports:
      - "5432:5432"
    volumes:
      - ./db:/docker-entrypoint-initdb.d:z
      # ./db — папка на компьютере
      # /docker-entrypoint-initdb.d — папка в контейнере
      # :z — разрешение SELinux (нужно на Fedora)

  redis:
    image: redis:7
    ports:
      - "6379:6379"

  prometheus:
    image: prom/prometheus
    ports:
      - "9090:9090"

  grafana:
    image: grafana/grafana
    ports:
      - "3030:3000"   # 3000 был занят VS Code — поменяли на 3030

Основные команды

BASH Управление стеком 
docker compose up            # запустить все сервисы
docker compose up --build    # запустить с пересборкой образов
docker compose up -d         # запустить в фоне (терминал свободен)
docker compose down          # остановить и удалить контейнеры
docker compose down -v       # + удалить volumes (данные БД)
docker compose restart db    # перезапустить конкретный сервис

YAML — синтаксис

YAML — формат файла конфигурации. Главное правило — отступы строго через пробелы, не табы.

Неправильные отступы в YAML
services:
    backend:      # 4 пробела — ОШИБКА
      ports:
        - "8000:8000"

Причина: сервисы должны иметь 2 пробела, а не 4.

Правильные отступы
services:          # 0 пробелов
  backend:         # 2 пробела
    ports:         # 4 пробела
      - "8000:8000"  # 6 пробелов
Запомни: depends_on задаёт порядок запуска, но не ждёт пока сервис полностью готов. Если база стартует медленно — бэкенд может упасть и перезапуститься.

FastAPI — бэкенд на Python

FastAPI — фреймворк для создания API на Python. Быстрый, современный, автоматически генерирует документацию.

Аналогия: API — это официант в ресторане. Ты (фронтенд) говоришь официанту что хочешь, он идёт на кухню (база данных) и приносит результат. Ты не знаешь как устроена кухня — тебе важен только результат.

Структура приложения

PYTHON backend/app/main.py 
from fastapi import FastAPI, HTTPException
# import — подключить библиотеку
# FastAPI — основной класс приложения
# HTTPException — возвращать ошибки с кодом (400, 500...)

from fastapi.middleware.cors import CORSMiddleware
# CORS — разрешить фронтенду обращаться к API с другого адреса

import psycopg2
# драйвер для подключения к PostgreSQL

import os
# встроенная библиотека Python для работы с переменными окружения

app = FastAPI(title="DevOps Portfolio API")
# создаём приложение

app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],   # * = разрешить всем сайтам
    allow_methods=["*"],
    allow_headers=["*"],
)

Эндпоинты

Эндпоинт — адрес на который можно отправить запрос. Каждый эндпоинт делает одно конкретное действие.

PYTHON GET запросы — получить данные 
@app.get("/")
# @app.get — декоратор: при GET запросе на "/" вызвать функцию ниже
def root():
    return {"status": "ok"}
# return — вернуть JSON ответ

@app.get("/topics")
def get_topics():
    conn = get_db()          # открыть соединение с базой
    cur = conn.cursor()      # инструмент для SQL запросов
    cur.execute("SELECT id, name, progress, notes FROM topics")
    rows = cur.fetchall()    # получить все строки
    cur.close()
    conn.close()             # закрыть соединение
    return [
        {"id": r[0], "name": r[1], "progress": r[2], "notes": r[3]}
        for r in rows        # list comprehension — создать список из строк
    ]
PYTHON PUT запрос — обновить данные 
@app.put("/topics/{topic_id}")
# {topic_id} — переменная в URL, например /topics/3
def update_topic(topic_id: int, progress: int, notes: str = ""):
# topic_id: int — FastAPI проверит что это число
# notes: str = "" — необязательный параметр, по умолчанию пустая строка

    if progress < 0 or progress > 100:
        raise HTTPException(status_code=400, detail="Progress must be 0-100")
    # 400 — код ошибки "неправильный запрос"

    conn = get_db()
    cur = conn.cursor()
    cur.execute(
        "UPDATE topics SET progress=%s, notes=%s WHERE id=%s",
        (progress, notes, topic_id)
    )
    # %s — заполнитель для значений (защита от SQL инъекций)
    conn.commit()   # подтвердить изменения — без этого не сохранится
    cur.close()
    conn.close()
    return {"status": "updated"}

SQL и PostgreSQL

SQL — язык запросов к базе данных. PostgreSQL — одна из самых популярных реляционных баз данных.

Аналогия: База данных — это Excel таблица. SQL — это команды для работы с ней: добавить строку, найти строку, изменить, удалить.

Миграция — создание таблицы

SQL db/001_create_topics.sql 
CREATE TABLE IF NOT EXISTS topics (
-- CREATE TABLE — создать таблицу
-- IF NOT EXISTS — не падать с ошибкой если таблица уже есть

    id         SERIAL PRIMARY KEY,
    -- SERIAL — автоматически увеличивается (1, 2, 3...)
    -- PRIMARY KEY — уникальный идентификатор строки

    name       VARCHAR(100) NOT NULL,
    -- VARCHAR(100) — текст до 100 символов
    -- NOT NULL — обязательное поле, не может быть пустым

    progress   INTEGER DEFAULT 0 CHECK (progress >= 0 AND progress <= 100),
    -- INTEGER — целое число
    -- DEFAULT 0 — по умолчанию 0
    -- CHECK — ограничение: только от 0 до 100

    notes      TEXT,
    -- TEXT — текст любой длины, может быть пустым

    updated_at TIMESTAMP DEFAULT NOW()
    -- TIMESTAMP — дата и время
    -- NOW() — автоматически ставит текущее время
);

INSERT INTO topics (name, progress, notes) VALUES
-- INSERT INTO — добавить строки в таблицу
    ('Docker',         80, 'Образы, контейнеры, docker-compose'),
    ('Git',            70, 'add, commit, push, ветки'),
    ('GitHub Actions', 40, 'Первый workflow, GitHub Pages');

Основные SQL команды

SQL Базовые операции 
SELECT * FROM topics;
-- SELECT — получить данные, * — все колонки

SELECT id, name, progress FROM topics WHERE progress > 50;
-- WHERE — условие фильтрации

UPDATE topics SET progress = 90 WHERE id = 1;
-- UPDATE — обновить строку

DELETE FROM topics WHERE id = 5;
-- DELETE — удалить строку (осторожно без WHERE удалит всё!)

ORDER BY id ASC   -- сортировать по id по возрастанию
ORDER BY id DESC  -- по убыванию
Миграция не выполнилась при запуске
ls: cannot open directory '/docker-entrypoint-initdb.d/': Permission denied

Причина: PostgreSQL выполняет SQL файлы из этой папки только при первом запуске — если данные уже существуют, миграция пропускается.

Решение — удалить старые данные и перезапустить
docker compose down
docker volume prune    # удалить старые данные БД
docker compose up -d   # запустить заново — миграция выполнится
Запомни: %s в Python запросах — это не строка формата, а защита от SQL инъекций. Всегда передавай значения вторым аргументом в cur.execute(), никогда не вставляй их напрямую в строку запроса.

HTML и CSS

HTML описывает структуру страницы, CSS — её внешний вид. Браузер читает оба файла и рисует то что видит пользователь.

Аналогия: HTML — это скелет здания (стены, окна, двери). CSS — это дизайн интерьера (цвет стен, мебель, освещение). Без HTML нечего оформлять, без CSS всё выглядит как текст на белом фоне.

Структура HTML файла

HTML Базовая структура любой страницы 
<!DOCTYPE html>
<!-- DOCTYPE — говорим браузеру что это HTML документ -->

<html lang="ru">
<!-- html — корневой элемент, lang — язык страницы -->

<head>
  <!-- head — служебная информация, не видна пользователю -->
  <meta charset="UTF-8">
  <!-- charset — кодировка, UTF-8 поддерживает русские буквы -->

  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <!-- viewport — страница нормально выглядит на телефоне -->

  <title>Название вкладки</title>
  <style> ... </style>
  <!-- style — CSS стили внутри HTML файла -->
</head>

<body>
  <!-- body — всё что видит пользователь -->
  <h1>Заголовок</h1>
  <p>Параграф текста</p>
  <div>Блок-контейнер</div>
  <span>Строчный элемент</span>
  <a href="page.html">Ссылка</a>
</body>
</html>

CSS Цвет, шрифт, отступы

CSS Flexbox — расположение элементов

Типы блоков

CSS display: block vs inline 
/* block — занимает всю ширину строки, следующий элемент на новой строке */
div, h1, h2, p, pre { display: block; }

/* inline — занимает только место текста, элементы идут в строку */
span, a, code, strong { display: inline; }

/* inline-block — как inline но можно задать ширину и высоту */
.badge { display: inline-block; padding: 0.2rem 0.7rem; }
Запомни: каждый HTML тег нужно закрыть — <div> закрывается </div>. Исключения: <meta>, <input>, <br> — самозакрывающиеся теги.

IntersectionObserver — отслеживание видимости

Браузерный API который следит за тем, какой элемент сейчас виден на экране. Мы используем его для scroll spy — автоматического переключения активного пункта в меню при прокрутке.

JAVASCRIPT Scroll spy в notes.html 
const sections = document.querySelectorAll('section');
// querySelectorAll — найти все элементы на странице по селектору
// 'section' — все теги <section>

const observer = new IntersectionObserver(entries => {
// IntersectionObserver — создать наблюдателя
// entries — список элементов которые изменили видимость

  entries.forEach(entry => {
  // forEach — пройти по каждому изменению

    if (entry.isIntersecting) {
    // isIntersecting — элемент сейчас виден в области просмотра

      const id = entry.target.id;
      // target — сам элемент, id — его атрибут id (например "git")

      links.forEach(l => l.classList.remove('active'));
      // убрать выделение у всех ссылок

      const active = document.querySelector(`.sidebar a[href="#${id}"]`);
      // найти ссылку в меню которая ведёт на этот раздел
      // [href="#git"] — ссылка с атрибутом href равным "#git"

      if (active) active.classList.add('active');
      // добавить выделение найденной ссылке
    }
  });

}, { rootMargin: '0px 0px -70% 0px', threshold: 0 });
// rootMargin — сжимаем область срабатывания:
//   '0px 0px -70% 0px' = сверху 0, справа 0, снизу -70%, слева 0
//   срабатывает когда верх секции входит в верхние 30% экрана
// threshold: 0 — срабатывать как только хоть пиксель виден

sections.forEach(section => observer.observe(section));
// observe — начать наблюдать за каждой секцией
Scroll spy не переключается на длинных разделах

Причина: threshold: 0.3 требует что 30% элемента видно. Для длинных разделов это может не выполняться никогда.

Решение — использовать rootMargin вместо threshold
{ rootMargin: '0px 0px -70% 0px', threshold: 0 }
// threshold: 0 — срабатывает при любой видимости
// rootMargin -70% снизу — активируется когда верх секции
// попадает в верхние 30% экрана

GitHub Actions — автоматизация

GitHub Actions выполняет задачи автоматически при определённых событиях — например при каждом git push. Мы используем его для автоматической публикации сайта.

Аналогия: GitHub Actions — это помощник которому ты дал инструкцию заранее. Ты отправил файлы (git push) — помощник автоматически опубликовал сайт. Ты занимаешься своим делом, он своим.

Структура workflow файла

YAML .github/workflows/pages.yml 
name: Deploy to GitHub Pages
# название — только для читаемости

on:
  push:
    branches:
      - main
# когда запускать — при каждом push в ветку main

permissions:
  contents: read
  pages: write
  id-token: write
# разрешения — что этому скрипту разрешено делать
# pages: write — разрешить публикацию на GitHub Pages

jobs:
  deploy:
    runs-on: ubuntu-latest
    # runs-on — на какой виртуальной машине выполнять
    # ubuntu-latest — GitHub предоставляет бесплатно

    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    # environment — окружение деплоя, сюда пишется URL сайта

    steps:
      - name: Checkout
        uses: actions/checkout@v4
        # скачать репозиторий на виртуальную машину

      - name: Setup Pages
        uses: actions/configure-pages@v4
        with:
          enablement: true
        # настроить GitHub Pages

      - name: Upload artifact
        uses: actions/upload-pages-artifact@v3
        with:
          path: ./frontend
        # упаковать папку frontend/ для публикации

      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v4
        # опубликовать на GitHub Pages

Что происходит после git push

BASH Полный цикл деплоя 
1. git push                          # ты отправляешь изменения
2. GitHub читает pages.yml           # находит инструкцию
3. Запускает виртуальную машину Ubuntu
4. actions/checkout — скачивает репозиторий
5. actions/configure-pages — настраивает Pages
6. actions/upload-pages-artifact — упаковывает frontend/
7. actions/deploy-pages — публикует на сайт
8. Сайт обновлён за 1-2 минуты
refusing to allow — нет прав на workflow
refusing to allow a Personal Access Token to update workflow

Причина: токен не имеет галочки workflow в правах.

Prometheus + Grafana — мониторинг

Prometheus собирает и хранит метрики. Grafana читает их из Prometheus и рисует графики. Вместе — полноценная система мониторинга для любого приложения.

Аналогия: Prometheus — это бортовой компьютер машины: постоянно записывает скорость, обороты, температуру. Grafana — это приборная панель: берёт эти данные и показывает красивыми стрелками и графиками.

Prometheus сохраняет эти числа с меткой времени.
Grafana читает из Prometheus и рисует график по времени.

Метрики в FastAPI — prometheus-client

PYTHON backend/app/main.py — добавить метрики 
import time
from fastapi import Request
from prometheus_client import Counter, Histogram, make_asgi_app

# Counter — счётчик, только растёт (количество запросов)
REQUEST_COUNT = Counter(
    'http_requests_total',           # название метрики в Prometheus
    'Total number of HTTP requests', # описание
    ['method', 'endpoint', 'status'] # labels — разрезы данных
)

# Histogram — гистограмма (распределение времени ответа)
REQUEST_LATENCY = Histogram(
    'http_request_duration_seconds',
    'HTTP request latency in seconds',
    ['endpoint']
)

# /metrics — эндпоинт куда заходит Prometheus
app.mount("/metrics", make_asgi_app())

# Middleware — перехватчик всех запросов
@app.middleware("http")
async def track_requests(request: Request, call_next):
    start = time.time()                  # время начала
    response = await call_next(request)  # выполнить запрос
    duration = time.time() - start       # сколько заняло

    if request.url.path != "/metrics":   # сами метрики не считаем
        REQUEST_COUNT.labels(
            method=request.method,
            endpoint=request.url.path,
            status=response.status_code
        ).inc()                          # +1 к счётчику
        REQUEST_LATENCY.labels(
            endpoint=request.url.path
        ).observe(duration)              # записать время в гистограмму

    return response

PromQL — язык запросов Prometheus

PromQL — специальный язык для запросов к метрикам. Пишется в Prometheus UI или в Grafana в режиме Code.

PROMQL Основные запросы 
http_requests_total
# просто показать все значения метрики

sum(http_requests_total) by (endpoint)
# сложить по группам: отдельно /topics, отдельно /metrics/

rate(http_requests_total[1m])
# скорость роста за последнюю минуту (запросов в секунду)

increase(http_requests_total[5m])
# прирост за последние 5 минут (сколько запросов пришло)

histogram_quantile(0.95, sum(rate(http_request_duration_seconds_bucket[5m])) by (le, endpoint))
# 95-й перцентиль времени ответа за 5 минут
# 95% запросов выполнились быстрее чем это значение
Перцентиль p95: Если p95 = 0.3 секунды — значит 95% запросов ответили быстрее чем за 0.3с. Оставшиеся 5% — медленнее. Это стандартная метрика производительности в продакшн системах. Среднее (average) врёт — один медленный запрос портит картину. Перцентиль честнее.

Ansible — автоматизация конфигурации

Ansible — инструмент для автоматического управления настройками серверов. Вместо того чтобы вручную настраивать каждый сервер по-очереди, ты описываешь в YAML файле что должно быть установлено и настроено — Ansible сам всё сделает на всех серверах.

Аналогия: Представь что у тебя 50 серверов и на каждый нужно установить nginx, создать пользователя и скопировать конфиг. Вручную — это 50 раз одно и то же. С Ansible — пишешь инструкцию один раз, запускаешь — готово на всех сразу.

Ключевые концепции

Managed nodes   — серверы которыми управляет Ansible
Inventory       — список серверов (адреса, группы)
Playbook        — YAML файл с инструкциями что делать
Task            — одно конкретное действие (установить пакет, скопировать файл)
Role            — набор tasks сгруппированных по функции (nginx, postgres)
Module          — встроенный инструмент Ansible (apt, copy, service, template)

# Ansible не требует агента на серверах!
# Подключается по SSH — нужен только SSH доступ и Python на сервере

Playbook — главный файл инструкций

YAML playbook.yml — установить и запустить nginx 
---
# --- обязательно в начале YAML файла

- name: Настроить веб-серверы
  # name — описание для читаемости

  hosts: webservers
  # hosts — на каких серверах выполнять (из inventory)

  become: true
  # become: true — выполнять с правами root (sudo)

  tasks:
    # tasks — список действий по порядку

    - name: Установить nginx
      apt:
        name: nginx
        state: present
        update_cache: true
      # apt — модуль для управления пакетами (Ubuntu/Debian)
      # state: present — убедиться что установлен
      # state: absent — убедиться что удалён

    - name: Скопировать конфиг nginx
      copy:
        src: files/nginx.conf
        dest: /etc/nginx/nginx.conf
        owner: root
        mode: '0644'
      # copy — скопировать файл с control node на сервер

    - name: Запустить и включить nginx
      service:
        name: nginx
        state: started
        enabled: true
      # service — управление системными сервисами
      # enabled: true — запускать автоматически при загрузке

    - name: Создать пользователя deploy
      user:
        name: deploy
        shell: /bin/bash
        groups: sudo
      # user — управление пользователями

Идемпотентность — главный принцип

Идемпотентность — запусти playbook 10 раз, результат всегда одинаковый. Если nginx уже установлен — Ansible не будет устанавливать снова. Это безопасно: можно запускать повторно без риска сломать то что работает. state: present означает "убедись что есть", а не "установи заново".
UNREACHABLE — не может подключиться к серверу
UNREACHABLE! => {"msg": "Failed to connect to the host via ssh"}

Причина: неверный IP, закрытый порт SSH, неверный ключ, или сервер выключен.

Диагностика
ssh ubuntu@192.168.1.10               # проверить SSH вручную
ansible all -m ping -vvv -i hosts     # подробный вывод (-vvv)
# в inventory проверить ansible_user, ansible_port, ansible_host
Changed: 0 но ошибки нет — ничего не применилось

Причина: задача уже в нужном состоянии (идемпотентность). Это нормально — Ansible не меняет то что уже правильно.

Jenkins — CI/CD сервер

Jenkins — сервер автоматизации. Он следит за репозиторием и при каждом изменении автоматически: собирает приложение, запускает тесты, деплоит на сервер. Это и называется CI/CD — непрерывная интеграция и доставка.

Аналогия: Jenkins — как конвейер на заводе. Ты положил деталь (сделал push в Git) — конвейер сам проверил, собрал, упаковал и отправил. Каждый шаг автоматический, ты только следишь за результатом.
Разница с GitHub Actions: GitHub Actions встроен в GitHub и бесплатен для открытых проектов. Jenkins — самостоятельный сервер, его нужно развернуть и поддерживать. Зато Jenkins более гибкий и популярен в корпоративной среде.

Jenkinsfile — описание pipeline

Jenkinsfile хранится в корне репозитория. Jenkins читает его и знает что делать при каждом push.

GROOVY Jenkinsfile — декларативный pipeline 
pipeline {
    // pipeline — объявляем что это Jenkins pipeline

    agent any
    // agent any — запускать на любом доступном агенте (исполнителе)

    environment {
        IMAGE_NAME = 'my-app'
        // environment — переменные доступные во всех stages
    }

    stages {
        // stages — список этапов, выполняются по порядку

        stage('Checkout') {
            // stage — один этап с именем
            steps {
                checkout scm
                // checkout scm — скачать код из Git репозитория
            }
        }

        stage('Build') {
            steps {
                sh 'docker build -t ${IMAGE_NAME}:${BUILD_NUMBER} .'
                // sh — выполнить shell команду
                // BUILD_NUMBER — встроенная переменная Jenkins (номер сборки)
            }
        }

        stage('Test') {
            steps {
                sh 'docker run --rm ${IMAGE_NAME}:${BUILD_NUMBER} pytest'
                // pytest — запустить тесты внутри контейнера
            }
        }

        stage('Deploy') {
            when {
                branch 'main'
                // when — условие: этот этап только для ветки main
            }
            steps {
                sh 'docker compose up -d --build'
            }
        }
    }

    post {
        // post — что делать после всех stages

        success {
            echo 'Деплой прошёл успешно!'
        }
        failure {
            echo 'Что-то сломалось — проверь логи!'
            // здесь можно добавить уведомление в Slack
        }
        always {
            sh 'docker system prune -f'
            // always — выполнить в любом случае (чистка)
        }
    }
}

Отказоустойчивые кластеры

Отказоустойчивость (High Availability, HA) — система продолжает работать даже если один из серверов упал. Достигается за счёт дублирования: нет ни одной точки отказа.

Аналогия: Один мост через реку — он упал, движение остановилось. Три моста через реку — один закрыт на ремонт, машины едут по двум другим. HA-кластер работает как три моста: один упал — остальные берут его нагрузку.

Ключевые понятия

BASH Словарь HA 
SPoF (Single Point of Failure)
— единственная точка отказа. HA = устранить все SPoF.

Replication (репликация)
— копирование данных в реальном времени на несколько серверов.
— Master → Slave. Пишем в Master, читаем с Slave.

Failover (переключение при сбое)
— автоматическое переключение на резервный сервер при падении основного.

Quorum (кворум)
— минимальное количество узлов для принятия решений.
— Нечётное количество узлов: 3 или 5. При 2 кластер может "застыть".

Load Balancer (балансировщик нагрузки)
— распределяет запросы между несколькими серверами.
— Пользователь всегда идёт в одну точку (VIP-адрес), не знает сколько серверов за ней.

VIP (Virtual IP)
— плавающий IP адрес. При падении одного сервера переходит на другой.
— Пользователи и приложения всегда используют VIP, не знают о переключении.

RTO (Recovery Time Objective) — максимальное время восстановления
RPO (Recovery Point Objective) — максимальная потеря данных

Инструменты для HA

BASH Популярные инструменты HA 
HAProxy          — балансировщик нагрузки для TCP/HTTP
                 — распределяет запросы, проверяет здоровье серверов
                 — порт: 80/443 для входящих, 8080 статистика

Keepalived       — управляет плавающим VIP адресом
                 — если основной сервер упал → VIP переходит на резервный
                 — работает через VRRP протокол

Pacemaker +      — кластер ресурсов (сложные конфигурации)
Corosync         — управляют любыми ресурсами: VIP, сервисы, диски
                 — используется в PostgreSQL кластерах

Patroni          — HA для PostgreSQL
                 — автоматический failover мастера
                 — интегрируется с etcd/consul/ZooKeeper для хранения состояния

Kubernetes       — оркестратор контейнеров
                 — встроенная HA: при падении пода запускает новый
                 — несколько replica для каждого сервиса

HAProxy — пример конфигурации

BASH /etc/haproxy/haproxy.cfg 
global
    daemon                    # запускать как демон

defaults
    mode http                 # режим HTTP (или tcp для баз данных)
    timeout connect 5s
    timeout client  30s
    timeout server  30s

frontend web_front
    # frontend — точка входа (принимает запросы)
    bind *:80                 # слушать на порту 80
    default_backend web_back  # передавать в этот backend

backend web_back
    # backend — список серверов куда распределять запросы
    balance roundrobin        # алгоритм: по кругу
    # balance leastconn       # или: наименее загруженному

    option httpchk GET /health
    # httpchk — проверять здоровье: GET /health каждые N секунд
    # если сервер отвечает не 200 — исключается из балансировки

    server web1 192.168.1.11:8000 check
    server web2 192.168.1.12:8000 check
    server web3 192.168.1.13:8000 check backup
    # check — включить проверку здоровья
    # backup — использовать только если все основные упали

listen stats
    bind *:8080
    stats enable
    stats uri /stats          # http://haproxy:8080/stats — дашборд

HA PostgreSQL с Patroni

BASH Архитектура Patroni кластера 
# Минимальная конфигурация: 3 узла
#
# [etcd]  — хранит состояние кластера (кто лидер)
#    ↓
# [Patroni] на каждом узле — управляет PostgreSQL
#    ↓
# [PostgreSQL] — сама база данных
#
# Схема:
# node1 (Master) ← пишем сюда
#    ↓ репликация
# node2 (Replica) ← читаем отсюда
#    ↓ репликация
# node3 (Replica) ← читаем отсюда
#
# Если node1 упал:
# Patroni + etcd выбирают нового лидера (node2 или node3)
# Failover занимает ~30 секунд

# Проверить статус кластера:
patronictl -c /etc/patroni.yml list
# NAME     HOST           ROLE     STATE   TL  LAG IN MB
# node1    192.168.1.11   Leader   running  1
# node2    192.168.1.12   Replica  running  1   0
# node3    192.168.1.13   Replica  running  1   0

etcdctl endpoint health
etcdctl member list

# Симуляция сбоя (для тестирования):
systemctl stop patroni   # остановить на одном узле
# кластер должен автоматически выбрать нового лидера

# Логи переключения:
journalctl -u patroni -n 100 --no-pager | grep -E "promoted|demoted|failover"
Split-brain — два сервера думают что они лидеры

Причина: потеря связи между узлами. Оба считают себя мастером и принимают записи — данные расходятся.

Решение — нечётное число узлов и кворум
# Минимум 3 узла — при потере 1 оставшиеся 2 составляют кворум
# и могут решить кто лидер. При 2 узлах — кворума нет.

# etcd/consul/ZooKeeper хранят "замок лидера":
# только тот кто держит замок — лидер.
# Если связь потеряна — замок истекает, другой узел берёт его.
Запомни: HA не защищает от всего. Она защищает от падения одного узла. Бэкапы — это другое: они защищают от потери данных (удалили таблицу, вирус, ошибка приложения). HA + регулярные бэкапы = надёжная система.

Jira и Confluence

Jira — инструмент для управления задачами и проектами. Confluence — корпоративная wiki для документации. Оба продукта от Atlassian, тесно интегрированы друг с другом.

Аналогия: Jira — это список дел команды на доске (кто что делает, когда). Confluence — это папка с инструкциями, схемами и решениями (как это делать). Вместе: задача в Jira ссылается на инструкцию в Confluence.

Jira — управление задачами

⚡ Важно для DevOps

Универсальный справочник — инструменты, подходы и хитрости которые нужны в работе независимо от проекта. Раздел пополняется по мере работы.

Главная задача DevOps: приложение должно работать стабильно, быстро восстанавливаться после сбоев, и любой инженер должен разобраться в проблеме за минуты — не часы. Тебе неважно на чём написано приложение — важно чтобы оно запускалось, мониторилось и чинилось.

curl — проверка HTTP запросов

curl — универсальный инструмент для отправки HTTP запросов. Незаменим для проверки API и диагностики.

BASH curl — основные флаги 
# Основной синтаксис:
curl [флаги] URL

# Флаги (можно комбинировать):
-X GET/POST/PUT/DELETE  # метод запроса (по умолчанию GET)
-H "Key: Value"         # добавить заголовок
-d '{"key":"value"}'    # тело запроса (данные)
-o файл.json            # сохранить ответ в файл
-s                      # тихий режим (без прогресса)
-v                      # подробный вывод (запрос + ответ)
-L                      # следовать редиректам
-u user:password        # базовая авторизация

# Примеры:
curl http://localhost:8000/topics
# простой GET запрос

curl -s http://localhost:8000/topics | python3 -m json.tool
# -s убирает прогресс, json.tool форматирует JSON красиво

curl -X PUT "http://localhost:8000/topics/1?progress=90" \
  -H "Content-Type: application/json"
# PUT запрос с заголовком
# \ в конце строки — перенос команды на следующую строку

curl -v http://localhost:8000/health
# подробный вывод — видно заголовки запроса и ответа
# полезно при отладке CORS и авторизации

sed — замена текста в файлах

sed — потоковый редактор. Позволяет менять текст в файлах без открытия редактора. Незаменим в скриптах.

BASH sed — основные операции 
# Замена текста:
sed 's/старое/новое/' файл.txt
# s — substitute (заменить), заменит первое вхождение в каждой строке

sed 's/старое/новое/g' файл.txt
# g — global, заменит все вхождения

sed -i 's/старое/новое/g' файл.txt
# -i — изменить файл на месте (без -i только выводит результат)

# Примеры:
sed -i 's/localhost/production-server/g' config.yml
# заменить адрес во всём файле конфига

sed -n '5,10p' файл.txt
# показать строки с 5 по 10

grep "ERROR" app.log | sed 's/ERROR/❌ ERROR/g'
# найти ошибки и подсветить их

Bash скрипты

Скрипт — файл с набором команд которые выполняются по порядку. Автоматизирует рутинные задачи.

BASH Структура скрипта 
#!/bin/bash
# !/bin/bash — шебанг, указывает какой интерпретатор использовать
# без этой строки скрипт может не запуститься

# Переменные:
NAME="world"

# $NAME — обращение к переменной

# Условия:

    echo "файл существует"
else

fi

# -d — проверить что это папка
# -z — проверить что строка пустая

# Цикл:
for i in 1 2 3; do
    echo "Число: $i"
done

# Запуск скрипта:
chmod +x script.sh     # дать права на выполнение
./script.sh            # запустить

Cron — планировщик задач

Cron запускает команды по расписанию. Бэкапы, очистка логов, проверки — всё это делается через cron.

BASH Синтаксис cron 
# Открыть редактор cron задач:
crontab -e

# Формат записи:
# минута час день месяц день_недели команда
# *      *   *    *     *            команда

# Примеры:
0 2 * * *    /scripts/backup.sh
# каждый день в 2:00 ночи запускать бэкап

*/5 * * * *  curl http://localhost:8000/health
# каждые 5 минут проверять здоровье сервиса

0 0 * * 1    docker system prune -f
# каждый понедельник в полночь чистить Docker

# Спецсимволы:
*    — любое значение
*/5  — каждые 5 единиц
1-5  — от 1 до 5
1,3,5 — конкретные значения

# Проверить список задач:
crontab -l

SELinux — безопасность на Fedora/RHEL

SELinux — дополнительный слой защиты. Часто мешает Docker и другим инструментам на Fedora.

BASH Диагностика и управление SELinux 
getenforce

# Permissive — только логирует, не блокирует
# Disabled — выключен

sestatus               # подробный статус
ausearch -m avc -ts recent  # что заблокировал недавно

Это SELinux — не права файловой системы. chmod не поможет. Добавь :z к volume.
