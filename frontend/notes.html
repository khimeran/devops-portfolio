🐧 Linux

Большой блок про устройство Linux. Делится на три темы: бинарники и ссылки (что запускается и как программы находят библиотеки), навигация по файловой системе (где что лежит, как монтируются диски, откуда брать метрики) и права в Linux (как файлы защищены, что такое chmod/chown/umask, спецбиты, SELinux и Docker-капкан).

Бинарники и ссылки

Из чего состоит исполняемый файл, как ядро его запускает, чем симлинк отличается от hard link и как читать вывод ls -l.

Системные папки и /usr merge

В Linux всё разложено по назначению. Бинарники — в bin-папках, библиотеки — в lib-папках.

FS Где лежат программы и библиотеки 
/bin    → команды для всех юзеров (ls, cat, cp, grep)
/sbin   → админские команды (mount, fdisk, mkfs, reboot)
          s = system, НЕ super
/lib    → 32-битные общие библиотеки (.so файлы)
/lib64  → 64-битные общие библиотеки
/usr/bin, /usr/sbin, /usr/lib64 → то же самое, основное место

# где шелл ищет команды — переменная PATH:
echo $PATH
# /usr/local/bin:/usr/bin:/usr/sbin:/home/kirill/.local/bin ...
# слева направо: какая папка раньше — та команда и выигрывает

which ls        # покажет полный путь найденной команды
type ls         # команда / алиас / встроенная в шелл / функция
/usr merge: на современной Fedora /bin, /sbin, /lib, /lib64 — это симлинки на /usr/bin, /usr/sbin, /usr/lib, /usr/lib64. Раньше папки были отдельными (на маленьких дисках /usr монтировался позже корня), сейчас всё унифицировано в /usr. Проверить: readlink -f /bin → /usr/bin.

ELF — формат бинарников

Каждый исполняемый файл — это ELF (Executable and Linkable Format), аналог .exe в Windows. Внутри: заголовок + машинный код + список нужных .so библиотек. Опознаётся по первым 4 байтам: 0x7F 'E' 'L' 'F' («магическое число»).

BASH Заглянуть внутрь бинарника 
file /usr/bin/ls
# ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV),
# dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2,
# BuildID[sha1]=..., for GNU/Linux 3.2.0, stripped

hexdump -C /usr/bin/ls | head -1
# 00000000  7f 45 4c 46 02 01 01 00  ...  |.ELF............|
#           └ те самые магические байты 7f 'E' 'L' 'F'
РАЗБОР Что означает каждое поле вывода file 
ELF 64-bit       — формат + битность (64-битные адреса)
LSB              — little-endian (порядок байт, как у всех x86)
pie executable   — Position Independent Executable:
                   можно грузить в любой адрес памяти.
                   Нужно для ASLR — защиты от эксплойтов
                   (адреса в памяти случайны при каждом запуске)
x86-64           — архитектура процессора (Intel/AMD 64-bit;
                   у ARM было бы aarch64)
SYSV             — System V ABI, стандарт общения с ядром
dynamically linked  — программа ЗОВЁТ .so из системы,
                      а не носит код в себе
interpreter /lib64/ld-linux-x86-64.so.2
                 — динамический линкер, стартует ПЕРВЫМ
BuildID          — уникальный хэш сборки (для debug/core dumps)
stripped         — без отладочных символов (имён функций) —
                   меньше размер, так делают для прода

Dynamic vs static linking

Динамическая линковка — программа использует общие .so библиотеки из системы. Статическая — весь код «вшит» в бинарник, он самодостаточен (так собирают Go-программы, busybox).

FLOW Как запускается dynamically linked ls 
1. Ядро видит ELF + interpreter в заголовке
2. Запускает ld-linux-x86-64.so.2 (динамический линкер) ПЕРВЫМ
3. Линкер читает список зависимостей из ELF
4. Находит .so файлы в /lib64, /usr/lib64
5. Подгружает их в память, подставляет адреса функций
6. И только ТОГДА стартует main() твоей программы
Dynamic (по умолчанию):
+ ls весит ~140 КБ вместо ~2 МБ — не носит код стандартных функций в себе
+ Обновили libc один раз — все программы стали безопаснее, пересобирать не надо
− Если удалить libc.so.6 — НИЧЕГО не запустится, даже ls. Восстановить только с live-USB.

Static (Go, busybox, scratch-образы Docker):
+ Один файл, ни от чего не зависит — кинул на любой сервер и работает
− Большой размер, обновление libc не подхватывается автоматически

Команда ldd — зависимости бинарника

BASH Список .so библиотек 
ldd /usr/bin/ls
# формат строки:  имя.so => /реальный/путь (адрес_в_памяти)

libc.so.6           # стандартная C (printf, malloc, open) — главная
libpthread.so.0     # многопоточность
libdl.so.2          # динамическая подгрузка .so на лету
librt.so.1          # POSIX real-time (таймеры, async I/O)
libpcre2-8.so.0     # регулярные выражения
libselinux.so.1     # поддержка SELinux

# особые строки без "=>":
linux-vdso.so.1     # ВИРТУАЛЬНАЯ библиотека: её нет на диске,
                    # ядро впрыскивает в каждый процесс, чтобы
                    # ускорить частые вызовы (gettimeofday и т.п.)
/lib64/ld-linux-x86-64.so.2  # сам динамический линкер

# где линкер вообще ищет библиотеки:
ldconfig -p | head        # кэш всех известных .so в системе
cat /etc/ld.so.conf.d/*   # доп. пути для поиска библиотек

LD_PRELOAD — впрыснуть свою библиотеку

Переменная окружения. Если выставлена — динамический линкер подгрузит указанную .so ПЕРВОЙ, и её функции перекроют системные.

BASH Проверить и найти, где задаётся 
echo $LD_PRELOAD                 # переменная текущего юзера
cat /etc/ld.so.preload           # системный preload (для ВСЕХ)
sudo grep -r "LD_PRELOAD" /etc   # широкий поиск, где задаётся

# может выставляться в:
# ~/.bashrc, ~/.bash_profile     — на уровне юзера
# /etc/profile, /etc/profile.d/  — система, всем юзерам
# /etc/ld.so.preload             — глобально, для ВСЕХ программ
# /etc/xdg//env/             — графическая сессия (KDE/GNOME)
Зачем нужен LD_PRELOAD:
✅ Дебаг и профилирование (Valgrind, AddressSanitizer подменяют malloc)
✅ Перехват вызовов (NoMachine так перехватывает графику — на этой машине он впрыснут через KDE-сессию)
🔥 Атаки: подсунуть вредоносный .so. Поэтому SUID-программы (passwd, sudo) игнорируют LD_PRELOAD — защита от эскалации прав.

Симлинки и hard links

Два способа сослаться на файл. Симлинк — отдельный файл-указатель с путём внутри. Hard link — ещё одно имя того же физического файла (inode).

SYMLINK Символическая ссылка (мягкая) 
# маленький файл, внутри которого записан ПУТЬ (текстом)
# в ls -la: первая буква l, есть стрелка ->
# может указывать на директорию
# может пересекать файловые системы
# если цель удалить/переименовать — симлинк ломается (dangling)

ln -s /usr/bin/python3 /tmp/py     # создать (-s = symbolic)
readlink -f /tmp/py                # куда указывает (до конца цепочки)
ls -la /tmp/py                     # увидеть стрелку ->

# пример из системы:
# lrwxrwxrwx 1 root root 7 янв 16 /bin -> usr/bin
#                        └ размер 7 = длина строки "usr/bin"
HARD LINK Жёсткая ссылка 
# второе ИМЯ того же inode (один физический файл — два имени)
# в ls -la выглядит как обычный файл (счётчик ссылок > 1)
# ТОЛЬКО на файлы, НЕ на директории
# ТОЛЬКО внутри одной файловой системы (inode привязан к ФС)
# удалили "оригинал" — файл жив, доступен по второму имени

ln /path/file /path/hardlink       # создать (без -s)
ls -li file hardlink               # одинаковый номер inode слева
stat file                          # Links: 2 — счётчик имён
Запомни: симлинк — указатель с путём, может «протухнуть». Hard link — второе имя того же inode, неуязвим к удалению оригинала. Симлинк на собеседованиях спрашивают часто.

Как читать ls -la

Строка вывода ls -l состоит из полей. Разберём на примере симлинка /bin.

РАЗБОР lrwxrwxrwx. 1 root root 7 янв 16 /bin -> usr/bin 
l           тип файла (см. таблицу ниже)
rwxrwxrwx   права: владелец | группа | остальные (r/w/x)
.           есть SELinux-контекст (на Ubuntu точки нет)
1           счётчик жёстких ссылок на этот inode
root        владелец (юзер)
root        группа-владелец
7           размер в байтах
янв 16      дата последнего изменения (mtime)
/bin        имя
-> usr/bin  куда указывает (только у симлинков)
МАРКЕРЫ Первая буква = тип файла 
-   обычный файл
d   директория
l   симлинк (символическая ссылка)
c   character device  (/dev/null, /dev/tty)
b   block device      (/dev/sda, /dev/nvme0n1)
p   named pipe (FIFO)
s   unix socket       (/var/run/docker.sock)

Шпаргалка: разбор файлов

BASH Команды этой темы 
file <путь>          # тип файла по содержимому (не по расширению)
ldd <бинарник>       # список .so зависимостей
ldconfig -p         # кэш всех библиотек системы
readlink -f <путь>   # куда указывает симлинк (вся цепочка)
which <cmd>          # полный путь команды из PATH
type <cmd>           # команда / алиас / встроенная / функция
ls -la <путь>        # длинный формат + скрытые файлы
ls -li <путь>        # + номер inode (для hard links)
stat <путь>          # inode, права, размер, времена, счётчик ссылок
ln -s target link    # создать симлинк
ln target hardlink   # создать hard link
Итог темы: бинарник = ELF, который зовёт код из общих .so. Линкер ld-linux стартует первым и подгружает зависимости. LD_PRELOAD впрыскивает свою библиотеку (SUID её игнорирует). Симлинк — указатель, hard link — второе имя inode. Тип файла видно по первой букве ls -l.

Навигация по файловой системе

Где что лежит в корне, как читать конфиги системы, как монтируются диски и откуда берутся метрики для мониторинга.

Карта корневой ФС

В Linux папки сгруппированы по назначению, а не по приложениям (как C:\Program Files\App\ в Windows).

FS Что где лежит в / 
/etc    → конфиги системы и сервисов (текстовые файлы)
/var    → изменяемые данные программ:
            /var/log    — логи (сюда смотрят, когда упало)
            /var/lib    — данные сервисов (БД, docker)
            /var/cache  — кэши пакетов и программ
/usr    → установленные программы и их статичные данные
/opt    → сторонний/коммерческий софт целым каталогом
/tmp    → временные файлы (чистятся при ребуте)
/run    → runtime работающих сервисов (PID-файлы, сокеты)
/home   → домашние папки обычных юзеров
/root   → домашняя папка администратора
/proc   → ВИРТУАЛЬНАЯ ФС: процессы и параметры ядра
/sys    → ВИРТУАЛЬНАЯ ФС: железо и драйверы
/dev    → файлы устройств (диски, /dev/null, терминалы)
/boot   → ядро Linux + initramfs + загрузчик GRUB
Где живёт девопс: /etc (настроить сервис), /var/log (понять, почему упало), /proc + /sys (диагностика и метрики).

/etc/os-release — версия дистрибутива

Стандартный файл на любом Linux. Скрипты читают его, чтобы понять, на чём бегут, и выбрать правильный пакетный менеджер.

BASH Кросс-дистрибутивный скрипт 
cat /etc/os-release      # NAME, VERSION_ID, ID, PRETTY_NAME, SUPPORT_END...

source /etc/os-release   # загрузить переменные из файла в шелл
if [ "$ID" = "fedora" ] && [ "$VERSION_ID" -ge 40 ]; then
  sudo dnf install ...
elif [ "$ID" = "ubuntu" ]; then
  sudo apt install ...
fi
# ID         — машиночитаемый (fedora, ubuntu, rhel) — стабилен
# VERSION_ID — числовая версия для сравнений
# SUPPORT_END — дата конца поддержки (важно для прода)

/etc/fstab и монтирование

Список разделов, которые ОС автоматически монтирует при старте. 6 колонок на строку.

FSTAB Формат строки 
<device>  <mountpoint>  <fstype>  <options>  <dump>  <pass>
   1            2           3         4        5       6

1 device     — откуда: UUID=..., LABEL=..., /dev/sda1
2 mountpoint — куда: /, /home, /boot
3 fstype     — ext4, btrfs, xfs, vfat, tmpfs, nfs
4 options    — defaults, ro, noatime, subvol=...
5 dump       — бэкап утилитой dump (почти всегда 0)
6 pass       — порядок fsck: 0 не проверять, 1 корень, 2 остальное

# пример:
UUID=eaa658da-... /     btrfs subvol=root,compress=zstd:1 0 0
UUID=d6a84d64-... /boot ext4  defaults                    1 2

mount             # что сейчас примонтировано
findmnt           # то же, но деревом и читаемо
Почему UUID, а не /dev/sda1: имена устройств (sda, sdb, nvme0n1) ядро назначает в порядке обнаружения железа — он НЕ гарантирован. Воткнул флешку → она стала /dev/sda, системный диск съехал → система не грузится. UUID записан внутри самой ФС и не меняется.

Диски: lsblk, btrfs, zram

BASH Карта дисков и разделов 
lsblk        # дерево: диски → разделы
lsblk -f     # + тип ФС, метка, UUID, заполнение, mountpoint
df -h        # сколько места занято по точкам монтирования
du -sh *     # размер папок в текущем каталоге

# btrfs-сабволумы: / и /home могут жить на ОДНОМ разделе
# (один UUID, разные subvol=root и subvol=home)
# → можно переустановить ОС, оставив /home нетронутым

# zram — swap в СЖАТОМ виде прямо в RAM (Fedora по умолчанию):
# выгруженные страницы сжимаются (zstd/lz4), ~2-3x экономии,
# RAM в тысячи раз быстрее диска, SSD не изнашивается записями

/proc и /sys — виртуальные ФС

Этих файлов нет на диске. Когда читаешь файл из /proc, ядро генерирует ответ на лету. Принцип Unix: «всё есть файл» — спросить ядро о CPU = прочитать файл (ls -la /proc/cpuinfo покажет размер 0 байт).

BASH Диагностика через /proc 
cat /proc/cpuinfo        # процессор: модель, ядра, flags
cat /proc/meminfo        # память: MemTotal, MemAvailable
cat /proc/loadavg        # средняя нагрузка за 1/5/15 минут
cat /proc/uptime         # сколько система работает (секунды)
nproc                    # число логических ядер (для make -j)

# проверить, можно ли поднять виртуалки/KVM-ноду:
grep -E "vmx|svm" /proc/cpuinfo
# vmx = Intel VT-x, svm = AMD-V
# пусто → виртуализация выключена в BIOS, KVM не запустить
Связь с мониторингом: node_exporter (агент Prometheus из твоего проекта) читает ровно эти файлы — /proc/meminfo, /proc/cpuinfo, /proc/stat, /proc/loadavg — и отдаёт Prometheus. Графики RAM/CPU в Grafana = красиво нарисованный /proc.

Память: free vs available

BASH free -h — использование памяти 
free -h
#         total  used  free  shared  buff/cache  available
# Mem:    15Gi   6,5Gi 1,1Gi 1,4Gi   9,5Gi       8,8Gi

# total       — всего RAM
# used        — реально занято процессами
# free        — совсем нетронуто
# buff/cache  — дисковый кэш (копии файлов для скорости)
# available   — ⭐ сколько РЕАЛЬНО доступно новым программам
🪤 Ловушка: маленький free — это НЕ проблема. Ядро забивает свободную RAM дисковым кэшем (buff/cache) и мгновенно отдаёт её программам по требованию. Реальная метрика «сколько свободно» — это available, а не free. Высокий buff/cache = здоровая система (см. linuxatemyram.com).
Итог темы: папки сгруппированы по назначению; конфиги — в /etc, логи — в /var/log. fstab монтирует разделы по UUID (надёжнее имён устройств). /proc и /sys — виртуальные ФС, ядро отдаёт через них метрики (их и читает Prometheus). available — настоящая свободная память, не free.

Права в Linux

Третья большая тема: кто чем владеет и кто что может делать. Каждый файл и папка в Linux принадлежит одному юзеру и одной группе, и для каждого из них (плюс «всех остальных») независимо настроены три права: читать, писать, выполнять. Здесь — как читать строку прав в ls -l, как её менять (chmod, chown, chgrp), откуда берутся «дефолтные» права у новых файлов (umask), что такое SUID/SGID/sticky, и про два капкана Fedora: SELinux и владение от root у файлов из контейнера.

Модель rwx × ugo

Linux разделяет права по трём «ролям» и трём «действиям». Это и есть знаменитые девять битов.

МОДЕЛЬ Три роли × три действия 
роли:                       действия:
  u (user)  — владелец-юзер     r (read)    — читать
  g (group) — владелец-группа   w (write)   — писать
  o (other) — все остальные     x (execute) — выполнять / войти
  a (all)   — u + g + o

Как читать строку прав из ls -l

РАЗБОР -rwxr-xr--. 1 kirill devs 1240 ноя 26 14:02 deploy.sh 
-           тип файла (-, d, l, c, b, p, s)
rwx         u: владелец  (читать + писать + выполнять)
r-x         g: группа    (читать + выполнять)
r--         o: остальные (только читать)
.           SELinux-контекст (на Fedora; на Ubuntu точки нет)
1           счётчик жёстких ссылок на инод
kirill      владелец-юзер
devs        владелец-группа
1240        размер в байтах
ноя 26      mtime — время последнего изменения
deploy.sh   имя
Запомни: у каждой роли всегда ровно три слота в фиксированном порядке r-w-x. Чёрточка - — это не «нет буквы», а «право отнято». Длина блока прав всегда 9 символов (плюс тип файла слева).

На файле и на папке биты значат РАЗНОЕ

СМЫСЛ файл vs папка — главный подвох 
            файл                папка
r           прочитать байты     увидеть СПИСОК имён (ls)
w           изменить байты      создать / удалить / переименовать файлы
x           запустить           ВОЙТИ (cd), обратиться к файлу по имени

Четыре типичных режима папок — r и x на папке независимы:

PRACTICE Проверь руками на vault/ с файлом внутри 
r-x   листать можно, менять нельзя       — обычная публичная папка
r--   ls видит имена, но cat падает      — почти бесполезно
--x   ls не работает, cat по имени — да  — «папка-сейф»
---   полностью закрыта                  — приватная

chmod 711 vault                      # --x для остальных
sudo -u nobody ls vault/             # Permission denied
sudo -u nobody cat vault/treasure    # читает по имени — ОК

chmod 744 vault                      # r-- для остальных
sudo -u nobody ls vault/             # имена видит
sudo -u nobody cat vault/treasure    # Permission denied (нет x)
Удалить файл = «выкинуть запись из списка» в родительской папке. Право на удаление лежит у папки, а не у файла. Если у тебя w на папке — ты удалишь даже чужой файл, который тебе не принадлежит и который ты не можешь редактировать. От этого защищает sticky-бит (см. ниже про /tmp).

Алгоритм проверки прав в ядре

FLOW Первое совпадение выигрывает 
1. Ты владелец-юзер?      ДА → берётся блок u, дальше НЕ смотрим
2. Ты в группе-владельце?  ДА → берётся блок g, дальше НЕ смотрим
3. Иначе                       → берётся блок o
4. root (UID 0)                → пропускается ВСЕГДА, проверка не делается
🪤 Парадокс на собесе: chmod 077 file даст права ----rwxrwx. И ты, владелец, НЕ сможешь читать этот файл (Permission denied), хотя у группы и остальных rwx. Потому что владелец подпадает под первый блок — на нём проверка останавливается. Шире права у других — не помогает.

В Linux расширение НЕ запускает программу

Это самый частый миф у людей с Windows-фоном. Linux не смотрит на расширение. Файл запускается, если:

RULE Что нужно, чтобы файл запустился 
1) стоит бит x                       — ядро вообще соглашается запустить
2) первая строка — shebang (#!...)   — ядро знает, КОМУ передать содержимое
                                       Например: #!/bin/bash, #!/usr/bin/env python3

# маркер "забыл chmod +x":
./script.sh
# bash: ./script.sh: Отказано в доступе (Permission denied)

chmod — меняем права

У chmod два эквивалентных синтаксиса: символьный (u+x) и числовой (755).

BASH Символьная запись 
# кому:     u user, g group, o other, a all
# оператор: +добавить, -убрать, =выставить ровно
# что:      r/w/x  (+ позже s/t — спецбиты)

chmod +x script.sh         # +x всем сразу (с учётом umask)
chmod u+x script.sh        # x только владельцу  → rwxr--r--
chmod g-w file             # отобрать запись у группы
chmod o= secret.txt        # «другим — ничего» (= o-rwx)
chmod a+r README           # дать чтение всем
chmod u=rwx,go=rx script   # выставить ровно — самый предсказуемый вариант
BASH Числовая (восьмеричная) запись 
chmod 755 file
# r=4, w=2, x=1, складываем для каждой роли:
# rwx = 4+2+1 = 7
# rw- = 4+2   = 6
# r-x = 4+0+1 = 5
# r-- = 4
# --x = 1
# --- = 0

# типовые маски, которые встретишь в Dockerfile / Ansible / SSH:
644   rw-r--r--   обычный файл (конфиг, README)
600   rw-------   секрет (приватный ключ SSH, .env)
755   rwxr-xr-x   исполняемый скрипт, папка
700   rwx------   приватная папка (~/.ssh)
777   rwxrwxrwx   🚩 КРАСНЫЙ ФЛАГ. Никогда в проде.
Рекурсивно — флаг -R: chmod -R 755 dir/. Это разовая правка дерева, не «наследование». Новые файлы внутри будут получать права от umask, а не от папки. Настоящее наследование группы — только через SGID (см. ниже).

chown / chgrp — меняем владельца

BASH chown — поменять юзера и/или группу 
chown user file             # сменить юзера
chown user:group file       # сменить и юзера, и группу
chown :group file           # сменить только группу (= chgrp)
chown -R user:group dir/    # рекурсивно

# самый частый кейс на проде — починить владение
# после контейнера или после переноса данных:
sudo chown -R "$(id -u):$(id -g)" db/data
# $(id -u) — твой UID числом
# $(id -g) — твой GID числом
# подстановка надёжнее имени: работает даже если в этой системе
# твоего юзера зовут иначе (внутри контейнера, например)
BASH chgrp — поменять только группу 
chgrp devs file
chgrp -R devs dir/
groups                # список твоих групп
# группу можно менять только на ту, в которой ты сам состоишь
⚠️ Правило безопасности: поменять юзера-владельца может только root. Обычный юзер не может ни «присвоить» чужой файл, ни «отдать» свой. Иначе любой создал бы SUID-скрипт, перевёл владельца на root — и эскалировал привилегии. Передача владения = операция рута.
Группы юзера и зачем они: id покажет UID/GID и группы. На Fedora важны:
• wheel — членство = возможность sudo (на Debian/Ubuntu роль играет группа sudo).
• docker — можешь docker run без sudo. ⚠️ Эквивалентно root: docker run -v /:/host alpine даёт доступ ко всей хост-ФС. На проде дают редко и осознанно.

umask — дефолтные права новых файлов

umask — это «маска вычитания». От базового «потенциала» ядро отнимает биты umask, и так получаются права свежесозданного файла.

FORMULA потенциал − umask = реальные права 
файл:  666 − umask = реальные права   (x по умолчанию НЕ дают — опасно)
папка: 777 − umask = реальные права

# обычный юзер на Fedora: umask 022
файл:  666 − 022 = 644  →  rw-r--r--
папка: 777 − 022 = 755  →  rwxr-xr-x

# umask 077 — только владельцу всё, остальным ничего
файл:  666 − 077 = 600  →  rw-------
папка: 777 − 077 = 700  →  rwx------

# umask 002 — командная папка, группа может писать
файл:  666 − 002 = 664  →  rw-rw-r--
BASH Проверить и поменять 
umask                # 0022 — первая 0 это спецбиты, дальше u/g/o
umask -S             # символьная форма: u=rwx,g=rx,o=rx
umask 077            # параноидальный режим
umask 022            # вернуть как было

# где umask живёт постоянно:
~/.bashrc                       — твой персональный umask
/etc/profile, /etc/login.defs   — системные дефолты
UMask= в systemd-юните          — umask для конкретного демона
Типовые значения в проде: 022 — десктоп; 027 — параноидальный сервер (остальные не видят); 002 — командная папка; 077 — приватные ключи и токены. Для .env-файла и id_rsa поставь chmod 600 вручную, не надейся на umask.

Спецбиты: SUID, SGID, sticky

К девяти обычным битам добавляются три «специальных» — они меняют поведение исполнения и создания файлов. В ls -l показаны буквой на месте x:

МАРКЕРЫ буква на месте x = спецбит 
позиция u (4-я)   s / S    — SUID    (запуск от ВЛАДЕЛЬЦА файла)
позиция g (7-я)   s / S    — SGID    (на dir: новые файлы наследуют группу)
позиция o (10-я)  t / T    — sticky  (на dir: удалить файл = только его владелец)

маленькая буква = бит установлен И x тоже стоит
большая буква   = бит установлен, но x НЕТ (обычно ошибка)

SUID — пример с passwd

BASH Почему обычный юзер может поменять свой пароль 
ls -l /usr/bin/passwd
# -rwsr-xr-x. 1 root root 91424 ... /usr/bin/passwd
#    ^ маленькая 's' = SUID

# /etc/shadow имеет права ---------- — никому ничего.
# Но программа passwd должна туда писать.
# SUID-бит говорит ядру: при запуске сделать процесс
# от имени ВЛАДЕЛЬЦА файла (root), а не запустившего (kirill).

# найти ВСЕ SUID-бинарники в системе (классика собеса по безопасности):
find /usr/bin /usr/sbin -perm -4000 -type f 2>/dev/null
# -perm -4000 — установлен SUID; минус = «как минимум этот бит»
# -type f     — только файлы
# 2>/dev/null — выбросить ошибки «нет доступа»
SUID-программы игнорируют LD_PRELOAD. Иначе атакующий подсунул бы свою .so и через passwd стал бы рутом. Это связь со старым разделом про бинарники и динамический линкер.

SGID на папке — единственное реальное «наследование»

BASH Командная папка, где файлы наследуют группу 
sudo mkdir /srv/teamspace
sudo chown root:devs /srv/teamspace
sudo chmod 2775 /srv/teamspace       # 2 спереди = SGID
ls -ld /srv/teamspace
# drwxrwsr-x. root devs ...
#       ^ s — SGID стоит

# теперь любой файл, созданный внутри, получит группу devs —
# даже если у создателя основная группа другая.
# подкаталоги тоже становятся SGID — наследование идёт вниз по дереву.

Sticky на /tmp

BASH Почему /tmp общая, но безопасная 
ls -ld /tmp
# drwxrwxrwt. ...
#         ^ t — sticky

# rwx у всех = любой юзер может писать в /tmp.
# Но t-бит ограничивает: УДАЛИТЬ файл может только его владелец
# (или владелец папки, или root).
# Без sticky любой бы пощёлкал rm -rf /tmp/* и снёс чужие сессии.

Числовая запись спецбитов

CHMOD 4 = SUID, 2 = SGID, 1 = sticky 
chmod 4755 file    # SUID + rwxr-xr-x   (как passwd)
chmod 2775 dir/    # SGID + rwxrwxr-x   (командная папка)
chmod 1777 dir/    # sticky + rwxrwxrwx (как /tmp)
chmod 6755 file    # SUID + SGID + rwxr-xr-x

SELinux — MAC поверх DAC (Fedora/RHEL)

На Fedora и RHEL над обычными правами сидит второй слой контроля. Точка в конце прав (rw-r--r--.) — маркер, что у файла есть SELinux-контекст.

МОДЕЛЬ DAC vs MAC 
DAC — Discretionary Access Control
       классические rwx / u / g / o, владелец сам решает кому что дать
       проверяется ПЕРВОЙ

MAC — Mandatory Access Control (SELinux)
       политики прописаны в системе, их НЕ обходит даже root
       проверяется ВТОРОЙ

# Если DAC разрешает, но MAC запрещает — итог: запрет.
# Если в Fedora ты root и тебя всё равно "Permission denied" —
# почти всегда виноват SELinux.

Самый частый случай: Docker volume на Fedora

BASH Симптом и лечение 
# симптом: внутри контейнера Permission denied при записи в bind-mount
docker run --rm -v "$PWD/data:/data" alpine touch /data/x
# touch: /data/x: Permission denied   ← НЕ помогает chmod 777!

# причина — SELinux-контекст: твой каталог user_home_t,
# а контейнерному домену container_t писать в user_home_t нельзя.

# проверка контекста:
ls -Zd data/
# unconfined_u:object_r:user_home_t:s0  data/

# лечение — добавить :z к volume:
docker run --rm -v "$PWD/data:/data:z" alpine touch /data/x
# :z — перелейблить как container_file_t, общий контекст
# :Z — то же, но ПРИВАТНО под этот контейнер
#      ⚠️ НЕ ставь :Z на /etc, ~/.ssh, /var — испортит систему
Подсказки для отладки: временно вырубить SELinux — sudo setenforce 0; вернуть — sudo setenforce 1; посмотреть последние блокировки — sudo ausearch -m AVC -ts recent. На Ubuntu роль SELinux играет AppArmor — симптомы похожие, лечение другое.

Docker-капкан: файлы от root

Стандартный сценарий: docker-compose up поднял PostgreSQL, в смонтированной папке ./db/data появились файлы. ls -l показывает root:root (или цифры 999:999). rm -rf db/data падает с Permission denied.

ПОЧЕМУ Ядру плевать на «контейнер» 
1. Внутри alpine по умолчанию ты root (UID 0).
2. Docker namespaces изолируют процессы, но НЕ UID.
   UID 0 в контейнере = UID 0 на хосте (если не настроен userns-remap).
3. Файл, созданный процессом, получает владельцем UID этого процесса.
4. На хосте ты видишь файлы от root:root — это и есть твой процесс UID 0.

# в случае официального postgres-образа создаётся внутренний юзер
# с UID 999 — поэтому на хосте файлы будут принадлежать "999:999"
# (имени для этого UID на хосте нет, ls покажет цифры).
FIX Четыре способа 
1. chown -R после факта (костыль, но работает)
   sudo chown -R "$(id -u):$(id -g)" db/data

2. флаг --user в docker run
   docker run --user "$(id -u):$(id -g)" -v "$PWD/data:/data:z" alpine ...
   + просто
   - внутри контейнера UID может не иметь имени → whoami падает

3. USER в Dockerfile (правильный путь для прод-образов)
   FROM python:3.12-slim
   RUN useradd -u 10001 -m appuser
   USER appuser
   CMD ["python", "app.py"]

4. Rootless Docker / Podman (современный путь)
   Демон работает от твоего юзера, userns-remap:
   "root внутри" = твой UID снаружи.
   Podman на Fedora — рутлесс из коробки, капкана нет.
Итог темы: 9 битов rwxrwxrwx делятся на u/g/o; на файле и папке смысл разный; ядро берёт ОДИН блок (u → g → o, первое совпадение); root проходит мимо проверки; SUID/SGID/sticky — спецбиты с числами 4/2/1; umask = маска вычитания для дефолтных прав; на Fedora поверх DAC сидит SELinux — лечится :z в Docker; chown от не-рута менять юзера-владельца не может. Эти восемь пунктов закрывают 95% вопросов по правам на собесе джуна DevOps.

Процессы и systemd

Четвёртая большая тема: всё, что бежит на Linux — это процесс, а всё, чем управляет DevOps — это сервис под systemd. Здесь модель процессов (PID, PPID, fork+exec), мониторинг (ps, top, htop), сигналы, особенности PID 1 в Docker, и systemd целиком — юниты, systemctl, journalctl, написание своего .service-файла.

Процессы: что это и как смотреть

Программа — это файл на диске (ELF-бинарник). Процесс — это запущенный экземпляр программы в памяти со своим PID, состоянием, открытыми файлами, кусочком памяти. Из одного бинарника можно одновременно запустить сколько угодно процессов.

PID, PPID и дерево процессов

КОНЦЕПТ Каждый процесс знает своего родителя 
PID   — уникальный номер процесса в системе (выдаёт ядро)
PPID  — Parent PID, PID родительского процесса

# В Linux ЛЮБОЙ процесс (кроме PID 1) имеет родителя.
# Новый процесс создаётся ТОЛЬКО через fork() от существующего.
# PID 1 — это init-процесс (systemd на современных дистрах).
# Все остальные — его потомки.

echo "мой PID:  $$"
ps -p $$ -o pid,ppid,user,stat,cmd

fork + exec — как создаются процессы

FLOW Что делает шелл, когда ты набираешь команду 
1. bash делает fork() → появляется КОПИЯ bash с новым PID
2. копия делает exec("/usr/bin/ls") → её код заменяется на код ls
3. PID сохраняется, но теперь это процесс ls
4. ls работает, печатает файлы
5. ls завершается → ядро шлёт родителю SIGCHLD
6. bash забирает статус через wait() → освобождает запись в таблице
7. bash возвращает приглашение $

# Если родитель умер РАНЬШЕ детей — детей усыновляет PID 1.
# Если родитель не вызвал wait() для мёртвого ребёнка — остаётся ЗОМБИ
# (запись в таблице процессов, но ресурсов не ест).

pstree — родословная процесса

BASH Цепочка предков от текущего процесса до PID 1 
pstree -psa $$
# -p — показать PID
# -s — показать предков (от $$ до PID 1)
# -a — показать аргументы запуска

# пример вывода:
# systemd,1
#   └─systemd,2618 --user
#       └─code,18964
#           └─bash,19245
#               └─bash,61348 ← наш текущий шелл
Два уровня systemd: PID 1 — системный systemd (один на машину), а systemd --user — пользовательский (по одному на каждого залогиненного юзера). Запомни на собес: «systemd работает на двух уровнях — system и user».

ps aux — снимок всех процессов

BASH Колонки и их значения 
ps aux | head -10

USER  PID  %CPU  %MEM  VSZ  RSS  TTY  STAT  START  TIME  COMMAND
                       ↑    ↑          ↑
                       │    │          └─ состояние (см. ниже)
                       │    └─ Resident Set Size — РЕАЛЬНАЯ RAM в KB
                       │                          (главная метрика памяти)
                       └─ Virtual Size — адресное пространство
                                         (часто большое, не пугайся)

# STAT-коды:
R   running   — крутится на CPU прямо сейчас
S   sleeping  — спит, ждёт событие (90% процессов)
D   uninterruptible — ждёт I/O, kill -9 НЕ убьёт
Z   zombie    — труп без вести пропавшего родителя
T   stopped   — Ctrl+Z
I   idle      — простаивает (kernel thread)

# модификаторы:
s   session leader
+   foreground в терминале
<   высокий приоритет
Имя процесса в [квадратных скобках] в ps aux означает kernel thread — поток ядра, не пользовательский процесс. У них VSZ/RSS = 0 (живут в адресном пространстве ядра), нельзя дебажить и убивать обычным kill. Пример: [kthreadd] (PID 2) — «отец всех kernel threads».

Сигналы и kill

Сигнал — это «постучали в окошко» от ядра процессу. Процесс может зарегистрировать обработчик, или будет применено действие по умолчанию (обычно — завершение). Команда kill посылает сигнал, не обязательно убивает.

ТАБЛИЦА Главные 5 сигналов на собес 
№   имя         действие             когда шлют
─────────────────────────────────────────────────────────────────
1   SIGHUP      terminate            «трубку повесили»: терминал закрыт
                                     демоны это перехватывают и
                                     ПЕРЕЧИТЫВАЮТ конфиг (nginx, sshd)
2   SIGINT      terminate            Ctrl+C
9   SIGKILL     terminate насильно   ⚠️ нельзя поймать или проигнорить
15  SIGTERM     terminate            «остановись по-хорошему» — дефолт kill
17  SIGCHLD     ignore               у тебя умер ребёнок, забери статус

kill -CONT PID        # разморозить

PID 1 в Docker — главный капкан

Внутри контейнера первый процесс получает PID 1 — как systemd в системе. И ядро относится к нему по-особому: сигналы без обработчиков просто игнорируются. Поэтому «обычное приложение как PID 1» — это бомба замедленного действия.

ПРАВИЛА PID 1 То, что обычные процессы НЕ обязаны делать 
1. Хоронить осиротевших детей (reap zombies)
   Если родитель умер раньше детей — дети усыновляются PID 1.
   PID 1 ОБЯЗАН их хоронить через wait().

2. Принимать SIGTERM при остановке
   Ядро шлёт SIGTERM системе через PID 1, ждёт корректного выхода.

3. ⚠️ Игнорировать сигналы без обработчика
   Защита от случайного самоубийства init'а.
   Это и есть КАПКАН: твой python без signal.signal(SIGTERM, ...)
   получает SIGTERM от Docker и ПРОСТО ЕГО НЕ ВИДИТ.

Симптом: docker stop ждёт 10 секунд

FLOW Что происходит при docker stop 
0.0 s   docker stop → SIGTERM процессу PID 1 контейнера
0.0 s   ядро видит: обработчика нет → сигнал ПРОИГНОРИРОВАН
0-10 s  Docker daemon ждёт «вежливый» grace period (по умолчанию 10s)
10.0 s  терпение кончилось → SIGKILL (-9)
10.0 s  ядро убивает БЕЗ предупреждения, ничего не сохраняется

# На проде это = недописанные транзакции, висячие коннекты, обрезанные логи.

Три способа лечения

FIX 1 docker run --init — самый ленивый 
docker run --init -v $PWD:/app python:3.12-slim python app.py
# или в docker-compose.yml:
#   services:
#     backend:
#       init: true

# Docker вставит крошечный tini (~20 КБ) как PID 1,
# твоё приложение получит PID 2.
# tini умеет: reap zombies + forward сигналы детям.
# docker stop → 0.2 секунды вместо 10.
FIX 2 Signal handler в приложении (production way) 
import signal
import sys

def shutdown(signum, frame):
    print(f"got signal {signum}, shutting down nicely", flush=True)
    # тут закрыть БД-коннекты, сбросить буферы и т.д.
    sys.exit(0)

signal.signal(signal.SIGTERM, shutdown)
signal.signal(signal.SIGINT, shutdown)

# теперь docker stop → ~0.2 секунды + аккуратное завершение
FIX 3 Exec form vs Shell form в Dockerfile 
# ❌ SHELL FORM — оборачивает в /bin/sh -c '...'
CMD python app.py
# реально: /bin/sh -c 'python app.py'
# PID 1 = sh, который НЕ форвардит сигналы детям → 10 секунд!

# ✅ EXEC FORM — запускается напрямую
CMD ["python", "app.py"]
# PID 1 = python (всё ещё нужен signal handler, но хотя бы без sh-обёртки)

# Bash имеет оптимизацию: `bash -c "single_cmd"` экзекает себя
# и СТАНОВИТСЯ единым процессом с PID 1.
# А `sh -c "..."` обычно НЕ оптимизируется → sh остаётся жить как обёртка.
Запомни на собес: 1) docker stop шлёт SIGTERM, через 10 сек — SIGKILL. 2) SIGKILL нельзя поймать. 3) PID 1 без обработчика SIGTERM = 10-секундная задержка остановки + потерянные данные. 4) Лечится --init, signal-handler, либо STOPSIGNAL в Dockerfile.

systemd: юниты и systemctl

systemd — это init-система (PID 1) и менеджер сервисов на большинстве современных Linux. Заменил SysV-init (bash-скрипты в /etc/init.d/). Даёт параллельный старт, автоперезапуск, централизованные логи, cgroups для изоляции ресурсов.

Юниты и их типы

.mount     точка монтирования (альтернатива /etc/fstab)
.timer     запуск по расписанию (замена cron)
.target    «уровень загрузки»: multi-user.target, graphical.target
.path      следить за файлом/папкой, реагировать на изменения

Где живут юнит-файлы

journalctl -p warning -u myapp
# уровни: emerg(0) alert(1) crit(2) err(3) warning(4) notice(5) info(6) debug(7)

На проде вместе с этим часто ставят journal → Loki или journal → Vector → Elastic, но локально достаточно journalctl.

Свой .service: docker-compose стек под systemd

Реальный паттерн на сервере: твой проект описан в docker-compose.yml. Чтобы он запускался при загрузке сервера, перезапускался при падении и логировался в journal — оборачиваем в systemd-юнит.

UNIT /etc/systemd/system/portfolio.service 
[Unit]
Description=DevOps Portfolio Stack
After=docker.service network-online.target
Requires=docker.service

[Service]
Type=simple
WorkingDirectory=/home/kirill/devops-portfolio
ExecStart=/usr/bin/docker compose up
ExecStop=/usr/bin/docker compose down
Restart=on-failure
RestartSec=5
User=kirill

[Install]
WantedBy=multi-user.target
РАЗБОР Что зачем 
After=docker.service        ждать поднятия Docker'а перед стартом
Requires=docker.service     если Docker упадёт — мы тоже падаем
WorkingDirectory=           docker compose ищет yml относительно cwd
ExecStart=docker compose up — главная команда (НЕ -d, чтобы systemd
                             видел процесс и мог следить за ним)
ExecStop=docker compose down — корректная остановка контейнеров
User=kirill                 — стек крутится от твоего юзера,
                             файлы НЕ будут root:root на хосте
Restart=on-failure          — если упадёт — поднять через 5 сек
WantedBy=multi-user.target  — запускать при загрузке системы
BASH Регистрация и запуск 
sudo tee /etc/systemd/system/portfolio.service > /dev/null <<'EOF'
... содержимое выше ...
EOF

sudo systemctl daemon-reload          # перечитать юниты
sudo systemctl start portfolio        # запустить
systemctl status portfolio            # проверить
sudo journalctl -u portfolio -f       # смотреть логи стека в реальном времени

# когда дошли до прода:
sudo systemctl enable --now portfolio # автозапуск при boot
Итог темы: процесс — это запущенная программа с PID. ps/top/htop — три способа посмотреть. kill шлёт сигналы (TERM = вежливо, KILL = насильно). PID 1 в Docker — особенный, без обработчика SIGTERM docker stop ждёт 10 сек. Лечится --init или signal handler. systemd управляет сервисами через юниты в /etc/systemd/system/; systemctl для управления, journalctl для логов. После любой правки юнита — daemon-reload. Restart=on-failure заменяет pm2/supervisord/forever одной строкой.

Юзеры и sudo

Пятая большая тема: кто такие юзеры в Linux, как их создавать (useradd), управлять (usermod, passwd), и как давать им точечные административные права через /etc/sudoers.d/. Это база безопасности на любом сервере: у каждого админа свой юзер, и каждый шаг с повышением прав логируется.

/etc/passwd, /etc/shadow, /etc/group

Три текстовых файла, которые держат всю информацию о юзерах. Их можно прочесть глазами (passwd и group — без sudo, shadow — только под рутом).

РАЗБОР /etc/passwd — одна строка на юзера, 7 полей через : 
kirill:x:1000:1000:Kirill:/home/kirill:/bin/bash
  1     2  3    4    5         6           7

1. имя для входа
2. ПЛЕЙСХОЛДЕР пароля (x = «реальный хэш в /etc/shadow»)
3. UID — числовой ID. 0 = root. 1-999 системные. 1000+ обычные.
4. GID — основной группы (обычно совпадает с UID)
5. GECOS — комментарий, обычно полное имя
6. домашний каталог
7. login shell. /sbin/nologin = «существует, но войти нельзя»
                                (используется для postgres, nginx и т.д.)
РАЗБОР /etc/shadow — хэш пароля + политика 
kirill:$y$j9T$SALT$HASH:20581:0:99999:7:::

# Формат поля пароля: $ID$SALT$HASH
# ID = алгоритм:
$1$  MD5         — ⚠️ старый, небезопасный
$5$  SHA-256     — старые серверы
$6$  SHA-512     — RHEL 7-8, Ubuntu <22
$y$  yescrypt    — Fedora 35+, современный (memory-hard, GPU-resistant)

# Маркеры «логин запрещён»:
!  или  *      — пароль заблокирован, через пароль войти нельзя
                 (для системных юзеров и для свежесозданных без passwd)
РАЗБОР /etc/group — описание групп 
wheel:x:10:kirill,iosic
docker:x:964:kirill
 1     2 3    4

1. имя группы
2. плейсхолдер пароля группы (почти никогда не используется)
3. GID
4. участники через запятую (НЕ считая тех, у кого это основная группа)

# Проверить, в каких группах юзер:
groups kirill
id kirill

useradd, usermod, userdel

BASH Создание юзера 
# ⚠️ adduser vs useradd:
#   на Fedora/RHEL — adduser = СИМЛИНК на useradd (одно и то же)
#   на Debian/Ubuntu — adduser — отдельный Perl-скрипт (интерактивный)
# Универсально писать useradd явно.

sudo useradd -m -s /bin/bash -c "Test User" testuser
#         │   │              │
#         │   │              └─ GECOS-комментарий
#         │   └─ login shell
#         └─ создать домашний каталог + копировать /etc/skel/

# Под капотом одной командой:
# 1. найти следующий свободный UID ≥ 1000
# 2. создать ОТДЕЛЬНУЮ группу с тем же именем (user private group)
# 3. строки в /etc/passwd, /etc/shadow (заперто), /etc/group
# 4. /home/testuser/ от него, права 700, скопировать /etc/skel/

# Задать пароль (снимает замок !):
sudo passwd testuser

# Добавить в дополнительные группы:
sudo usermod -aG wheel,docker testuser     # ⭐ -a = APPEND, без него ЗАТРЁТ группы!

# Удалить юзера + домашний каталог:
sudo userdel -r testuser
⚠️ usermod -G без -a = ЗАМЕНИТЬ список групп. Это означает «выкинуть из всех остальных». Один из главных способов случайно вылететь из wheel и потерять sudo. Запомни: всегда usermod -aG.

su vs sudo

РАЗНИЦА Полная смена личности vs точечный доступ 
su        смена ПОЛНОЙ личности на одну сессию
          требует ПАРОЛЬ ЦЕЛЕВОГО юзера (root'а — для перехода в root)
          один запрос пароля → всё подряд от его имени

sudo      выполнить ОДНУ команду от имени root (или другого юзера)
          требует ТВОЙ пароль (если ты в правах)
          КАЖДАЯ команда логируется (аудит!)
          можно дать точечно «только перезапуск nginx»

# На проде везде sudo — потому что есть аудит и точечные права.
BASH Варианты sudo su / sudo -i / machinectl 
sudo su          стать root БЕЗ перезагрузки окружения
                 cwd, PATH, env остаются твои
                 # вместо $, но контекст твой

sudo su -        стать root С полным login-окружением
                 cwd = /root, прочитан /root/.bashrc
                 PATH сброшен на root'овский

sudo -i          ⭐ современная замена sudo su - (чище)
sudo -s          современная замена sudo su (без login-env)

sudo -u oracle -i        перейти в oracle с полным окружением
machinectl shell user@   ⭐ ЛУЧШЕЕ для прода — чистая login-сессия,
                         как если бы юзер физически зашёл с консоли
                         (закрывает PAM/D-Bus-капканы при работе с
                          сервисами от имени другого юзера)

sudoers и точечный sudo

PATHS Где живут правила 
/etc/sudoers       главный файл, НЕ редактировать напрямую!
/etc/sudoers.d/    папка с фрагментами — сюда кладём свои правила

# ⚠️ NEVER do: sudo nano /etc/sudoers
# Битый синтаксис = потеря sudo навсегда (надо single-user mode чинить).

# Правильный путь:
sudo visudo                              # /etc/sudoers
sudo visudo -f /etc/sudoers.d/myapp      # фрагмент
# visudo проверяет синтаксис при сохранении и не даст сохранить битое.
SYNTAX Формат правила 
USER  MACHINE=(RUNAS_USER) [TAGS:] COMMANDS

# Примеры:
root    ALL=(ALL)        ALL                     # root всё может
%wheel  ALL=(ALL)        ALL                     # группа wheel всё может
%wheel  ALL=(ALL) NOPASSWD: ALL                  # ⚠️ без пароля — на проде не делать!
appuser ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart nginx
                                                 # ТОЛЬКО эта команда, без пароля
deploy  ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart *.service
                                                 # любой *.service — wildcard
backup  ALL=(ALL) NOPASSWD: /usr/bin/rsync /data /backup
                                                 # ровно эта команда, в проде так дают cron-задачам

# Поля:
#   USER          — кто (юзер) или %группа
#   MACHINE       — с какой машины (для NIS-сетей; обычно ALL)
#   (RUNAS_USER)  — от чьего имени можно (после sudo -u; обычно ALL)
#   TAGS          — например NOPASSWD: или NOLOG:
#   COMMANDS      — какие команды разрешены (полный путь!)
PRACTICE Создание точечного sudo для сервиса 
# Дать appuser право рестартить только Docker:
sudo bash -c 'echo "appuser ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart docker" \
              > /etc/sudoers.d/appuser-docker'
sudo chmod 440 /etc/sudoers.d/appuser-docker     # обязательные права

# Проверить, что разрешено юзеру:
sudo -u appuser sudo -n -l        # -l = list rules, -n = non-interactive
# выведет: (ALL) NOPASSWD: /usr/bin/systemctl restart docker

# Проверить запрет:
sudo -u appuser sudo -n cat /etc/shadow
# > sudo: a password is required

# Проверить разрешение:
sudo -u appuser sudo -n systemctl restart docker
# > (без вывода = OK)

Итог темы: юзер = строка в /etc/passwd + хэш в /etc/shadow + членство в группах в /etc/group. UID — то, что видит ядро, имя — для людей. useradd -m создаёт юзера + домашний каталог. На Fedora adduser = useradd, на Debian — другой скрипт. passwd ставит пароль (без него юзер заперт). usermod -aG добавляет в группы (без -a затрёт существующие!). su — полная смена личности, sudo — точечная команда + аудит. Правила в /etc/sudoers и /etc/sudoers.d/, правка через visudo. Прод-паттерн: фрагмент в /etc/sudoers.d/ с одной разрешённой командой, без NOPASSWD на ALL. Группа docker = эквивалент root.

Пакеты (dnf) и ротация логов

Шестая тема: как ставить, обновлять и откатывать пакеты через dnf на Fedora/RHEL, и как настроить автоматическую ротацию логов через logrotate, чтобы они не съели диск.

dnf — пакетный менеджер Fedora/RHEL

ИСТОРИЯ rpm → yum → dnf → dnf5 
rpm    низкоуровневый, ставит ОДИН .rpm-файл, без зависимостей
yum    поверх rpm, разрешает зависимости (RHEL 5-7, CentOS 7)

# === ПОИСК И ИНФА ===

logrotate — чтобы логи не съели диск

Логи на сервере растут постоянно: nginx-access, докер-контейнеры, application-логи. Если их не подрезать — рано или поздно /var/log заполнит диск и сервисы упадут с «No space left on device». logrotate автоматически обрезает, упаковывает и удаляет старые логи.

PATHS Где живут конфиги 
/etc/logrotate.conf    глобальные дефолты + include /etc/logrotate.d
/etc/logrotate.d/      ⭐ папка с конфигом ДЛЯ КАЖДОГО сервиса:
                       rsyslog, httpd, fail2ban, samba, mariadb, ...

# Запускается СИСТЕМНЫМ ТАЙМЕРОМ ежедневно:
systemctl list-timers logrotate.timer

# Интересный момент: таймер ежедневный, но сами конфиги могут быть weekly.
# logrotate проверяет ВНУТРИ конфига: «прошла ли неделя?» и решает сам.
CONFIG Типовой конфиг /etc/logrotate.d/rsyslog 
/var/log/cron
/var/log/maillog
/var/log/messages
/var/log/secure
/var/log/spooler
{
    missingok               ← если файл отсутствует — не ругаться
    sharedscripts           ← postrotate ОДИН на весь блок (не для каждого)
    postrotate
        /usr/bin/systemctl reload rsyslog.service >/dev/null 2>&1 || true
                            ← после ротации — SIGHUP сервису,
                              чтобы он переоткрыл новый файл
    endscript
}
DIRECTIVES Самые частые директивы 
daily / weekly / monthly    как часто ротировать
rotate 7                    хранить 7 старых копий, остальное удалить
compress                    ⭐ упаковать старые в .gz (экономит место)
delaycompress               не сжимать самую свежую копию
                            (нужно если приложение ещё в неё пишет)
dateext                     суффикс — дата (messages-20260603), не число
missingok                   файла нет → не паниковать
notifempty                  пустые не ротировать
create 0640 root adm        создать новый файл с такими правами/владельцем
copytruncate                ⚠️ копировать содержимое + обнулить ОРИГИНАЛ
                            нужно для приложений, которые НЕ умеют SIGHUP
                            (NodeJS, многие самописы)
size 100M                   ротировать если файл > 100 МБ
maxage 30                   ⭐ удалять копии старше 30 дней
postrotate / endscript      команды ПОСЛЕ ротации (обычно SIGHUP сервису)
prerotate  / endscript      команды ДО ротации
BASH Тест и отладка 
# ⭐ DEBUG-режим: ничего не делает, только говорит ЧТО БЫ сделал
sudo logrotate -d /etc/logrotate.d/myapp 2>&1 | head -30

# Вывод покажет:
# considering log /var/log/myapp.log
#   Now: 2026-06-03 18:00
#   Last rotated at 2026-06-01 03:14
#   log does not need rotating  ← или «log needs rotating»

# FORCE-режим: ротировать сейчас, игнорируя расписание
sudo logrotate -f /etc/logrotate.d/myapp

# Где logrotate помнит «когда что последний раз ротировалось»:
cat /var/lib/logrotate/logrotate.status
PRACTICE Свой конфиг для самописного сервиса 
# Допустим, твой FastAPI пишет в /var/log/myapp/*.log
# Создаём /etc/logrotate.d/myapp:

sudo tee /etc/logrotate.d/myapp > /dev/null <<'EOF'
/var/log/myapp/*.log {
    daily
    rotate 14
    compress
    delaycompress
    missingok
    notifempty
    create 0640 myapp myapp
    sharedscripts
    postrotate
        systemctl reload myapp.service > /dev/null 2>&1 || true
    endscript
}
EOF

# Проверить, что не сломан:
sudo logrotate -d /etc/logrotate.d/myapp
Итог темы: dnf search — fuzzy, dnf info — точное имя. dnf install -y, dnf update, dnf history undo <ID> для отката (фича dnf, у apt такого нет). dnf provides <файл> — найти пакет по файлу. logrotate запускается ежедневным systemd-timer'ом и сам решает по конфигу daily/weekly/monthly. Конфиги в /etc/logrotate.d/. Главные директивы: rotate N, compress, missingok, copytruncate (для NodeJS/самописа без SIGHUP), postrotate с SIGHUP для сервисов. Тест через logrotate -d — ничего не делает, только говорит ЧТО БЫ сделал.

Bash — скрипты и автоматизация

Bash (Bourne Again SHell) — это командная оболочка: программа, которая читает твои команды и заставляет ядро их выполнять. Когда ты что-то печатаешь в терминале — с тобой разговаривает именно bash. А скрипт — это те же команды, сложенные в файл, чтобы bash прогнал их пачкой, сверху вниз, без тебя.

Как работает bash — принципы

bash — тупой, буквальный и честный солдат: делает ровно то, что написано, и ни о чём не догадывается. Отсюда все его принципы:

PRINCIPLES Из чего складывается логика bash 
# 1. Читает файл СВЕРХУ ВНИЗ, строку за строкой.
# 2. Почти всё в bash — это ВЫЗОВ КОМАНДЫ. Команда бывает:
#      внешняя программа   — ls, pg_dump, tar, scp, find
#      встроенная (builtin)— cd, echo, export
#      твоя функция        — log() { ... }
# 3. Каждая команда возвращает КОД ЗАВЕРШЕНИЯ (exit code):
#      0     = успех
#      не 0  = ошибка
#    Именно по этому коду работают && , || и set -e.
# 4. Пробелы и символы ЗНАЧИМЫ — bash сам не догадается:
#    a=1     — присваивание переменной
#    a = 1   — для bash это попытка запустить КОМАНДУ 'a' с аргументами = и 1

Зачем скрипт: руками против автоматизации

Допустим, надо снимать бэкап базы каждую ночь. Руками это значит: зайти на сервер, набрать pg_dump, дождаться, набрать tar, дождаться, набрать scp, дождаться, не забыть удалить сырьё, не забыть подчистить старые архивы. И так каждую ночь — а забыл шаг или уехал в отпуск, и бэкапов нет.

Скриптом мы описываем всё это ОДИН раз и по уму: сначала выносим в переменные всё, что меняется (имя базы, папка, адрес сервера) — чтобы не повторять их в каждой строке и менять в одном месте. Потом перечисляем шаги по порядку. А запуск отдаём cron, чтобы машина делала это сама в три ночи, пока мы спим. Дальше — как такой скрипт растёт от одной команды до боевого, шаг за шагом.

Шаг 1. Одна команда

Любой скрипт начинается с одного действия. Снять дамп базы — это одна команда pg_dump:

STEP 1 С чего всё начинается 
pg_dump production > dump.sql
#  pg_dump    — утилита постгреса: выгружает базу в текстовый SQL
#  production — имя базы
#  > dump.sql — "положи вывод в файл dump.sql" (перенаправление stdout)

Работает, но это пока просто команда в терминале. Чтобы оно стало скриптом — заводим файл и первой строкой пишем шебанг:

BASH Шебанг — паспорт скрипта 
#!/bin/bash
#  шебанг: "запускай этот файл интерпретатором /bin/bash"
#  без него система не знает, чем выполнять файл

Шаг 2. Переменные, кавычки и подстановка команд

В имя бэкапа хочется впихнуть дату, чтобы файлы не затирали друг друга. Дату выдаёт команда date, а чтобы подставить её РЕЗУЛЬТАТ — оборачиваем в $( ):

VARS Переменные и заморозка значения 
DATE=$(date +"%Y-%m-%d")   # $( ) = выполни команду, подставь результат
DB=production
pg_dump $DB > dump_$DATE.sql   # → dump_2026-06-12.sql

# Форматы date:
#  %F = 2026-06-12   %T = 14:30:05   %Y год %m месяц %d день
#  %H часы %M минуты %S секунды

Ключевой момент: переменная вычисляется ОДИН раз — в момент присваивания — и замораживается. $(date) отработала, в DATE легла строка, и дальше $DATE — это «достать из кармана», а не «снова посмотреть на часы». Поэтому имя файла одинаковое на всех шагах, даже если скрипт работает час. Если бы мы звали $(date) в каждой строке заново — время бы разъехалось, и tar искал бы файл, которого нет.

Кавычки тоже не для красоты — это разные режимы работы bash:

QUOTES Двойные vs одинарные 
"двойные"   — bash подставляет переменные:  echo "$DB"  → production
'одинарные' — всё буквально, $ не трогается: echo '$DB'  → $DB

# Спецсимволы ($ ! @ в паролях) — только в ОДИНАРНЫХ:
echo "P@$$w0rd"   # в двойных $$ = PID процесса → пароль испорчен
echo 'P@$$w0rd'   # в одинарных — символ в символ, как надо

Шаг 3. Связываем команды: ; && ||

Один шаг — это мало. Нам надо: создать папку → снять дамп → запаковать → отправить → почистить. Команды соединяют операторами, и разница между ними критична:

LOGIC Операторы связки и перенаправление 
cmd1 ; cmd2     по очереди (cmd2 пойдёт ДАЖЕ если cmd1 упала)
cmd1 && cmd2    "И":   cmd2 только если cmd1 УСПЕШНА (код возврата 0)
cmd1 || cmd2    "ИЛИ": cmd2 только если cmd1 УПАЛА (код НЕ 0)

# Это НЕ стрелки блок-схемы! Логировать каждый шаг через || — путь
# к вывернутой логике, где реальная работа уезжает в "ветку ошибки".

# Перенаправление в файл — два вида:
cmd > file      ЗАТЕРЕТЬ файл заново
cmd >> file     ДОПИСАТЬ в конец (для логов — только так!)

Для бэкапа нужен &&: «паковать имеет смысл, только если дамп реально снялся; отправлять — только если запаковалось».

Шаг 4. Пароль — отдельно от кода (~/.pgpass)

pg_dump ходит на чужой сервер и хочет пароль. Под cron'ом в три ночи ввести его некому — скрипт повиснет или упадёт. Засунуть пароль прямо в скрипт тоже нельзя: скрипт уедет в git, а git помнит всё навсегда — пароль достанут из истории за три секунды. Правильно — спрятать пароль в файл ~/.pgpass, откуда постгрес сам его возьмёт:

SECRET ~/.pgpass + флаг -w 
# формат: hostname:port:database:username:password
echo '192.168.1.50:5432:production:admin:ПАРОЛЬ' > ~/.pgpass
chmod 600 ~/.pgpass
#  600 = читать/писать только владельцу. Если права шире —
#  постгрес-параноик МОЛЧА проигнорирует файл (не ошибка, просто "не вижу").

# в скрипте добавляем -w: "пароль руками не клянчи, нет — сразу падай"
pg_dump -h $DB_HOST -U $DB_USER -w $DB_NAME > "$BACKUP_DIR/dump_$DATE.sql"

Правило на всю жизнь: секрет и код не лежат в одном файле.

Шаг 5. Убираем за собой: rm и find

Скрипт создаёт файлы каждую ночь. Если не чистить — две беды: рядом с архивом валяется сырой .sql (двойной расход места), и старые архивы копятся вечно, пока диск не забьётся — и тогда бэкапы вообще перестанут делаться.

CLEANUP rm сырья + find для старья 
rm "$BACKUP_DIR/dump_$DATE.sql"   # сырой дамп после упаковки уже не нужен

find "$BACKUP_DIR" -name "*.tar.gz" -mtime +7 -delete
#  find  ГДЕ           ФИЛЬТР            ДЕЙСТВИЕ
#  -name "*.tar.gz"  только архивы (кавычки! иначе bash раскроет * сам)
#  -mtime +7         старше 7 дней   (+N = старше, -N = младше)
#  -delete           снести найденное

# ⚠️ СНАЧАЛА запусти БЕЗ -delete — посмотреть, кого find нашёл.
# Убедился, что там только старьё — ТОЛЬКО потом дописывай -delete.

Шаг 6. Свой инструмент: функции и DRY

Логировать хочется на каждом шаге, но копировать echo ... >> log двадцать раз — позор. Пишем СВОЮ команду — функцию log — один раз и зовём как родную:

FUNC Функция log() — принцип DRY 
log() { echo "$(date '+%F %T') $1" >> /var/log/backup.log; }
#  log()      объявляем функцию по имени log
#  { ... ; }  тело (пробелы и ; внутри обязательны)
#  $1         первый аргумент:  log "привет"  → внутри $1 = "привет"

log "Бэкап создан"   # формат лога теперь меняется в ОДНОМ месте

Это принцип DRY — Don't Repeat Yourself, «не дублируй». Захотел поменять формат записи — правишь функцию, а не двадцать строк по всему скрипту.

Шаг 7. Чтобы скрипт не врал: set -e и trap

По умолчанию bash — пофигист: команда упала, а он спокойно бежит дальше и пакует пустоту. Чиним заклинанием в начале скрипта и ставим «дежурного», который ловит любое падение:

SAFE set -euo pipefail + trap 
set -euo pipefail
#  -e          упасть на первой же ошибке (иначе bash тащит дальше)
#  -u          ругаться на необъявленную переменную (ловит опечатки)
#  -o pipefail в конвейере a|b: провал любого звена = провал всего

trap 'log "ОШИБКА на шаге: $STEP"; exit 1' ERR
#  trap 'код' ERR — "дежурный": при ЛЮБОМ падении выполнит код (лог + выход).
#  АПОСТРОФЫ важны! они откладывают подстановку $STEP до момента ПАДЕНИЯ,
#  а не вычисляют сейчас (сейчас $STEP ещё пустой).

STEP="дамп базы"   # ярлычок перед командой → trap скажет, ГДЕ рвануло
pg_dump ...

Теперь не нужно лепить || log "ошибка" после каждой строки: одна сигнализация стережёт весь скрипт, а переменная STEP подсказывает, на каком именно шаге случилась беда. Логика разделена: за «падать или нет» отвечает set -e, за «куда писать о падении» — trap, а сами log между шагами просто ведут летопись.

Итог: боевой backup.sh

Складываем все кирпичи вместе. Вот тот самый «лютый скрипт», в который вырос наш одинокий pg_dump из шага 1:

BASH backup.sh целиком 
#!/bin/bash
set -euo pipefail

DATE=$(date +"%Y-%m-%d")
BACKUP_DIR='/var/backups'
SERVER='backup@msk-files.dns.ru:/storage/backups/'
DB_HOST=192.168.1.50
DB_NAME=production
DB_USER=admin

log() { echo "$(date '+%F %T') $1" >> /var/log/backup.log; }

trap 'log "ОШИБКА: бэкап $DATE упал на шаге: $STEP"; exit 1' ERR

log "=== Старт бэкапа $DATE ==="

STEP="создание директории"
mkdir -p "$BACKUP_DIR"
log "Папка готова. Снимаю дамп базы..."

STEP="дамп базы"
pg_dump -h $DB_HOST -U $DB_USER -w $DB_NAME > "$BACKUP_DIR/dump_$DATE.sql"
log "Дамп снят. Архивирую..."

STEP="архивация"
tar -czf "$BACKUP_DIR/dump_$DATE.tar.gz" "$BACKUP_DIR/dump_$DATE.sql"
log "Заархивировано. Удаляю сырьё..."

STEP="удаление сырья"
rm "$BACKUP_DIR/dump_$DATE.sql"
log "Сырьё удалено. Отправляю в Москву..."

STEP="отправка в Москву"
scp "$BACKUP_DIR/dump_$DATE.tar.gz" "$SERVER"
log "Архив улетел. Чищу старьё..."

STEP="чистка старья"
find "$BACKUP_DIR" -name "*.tar.gz" -mtime +7 -delete
log "=== ГОТОВО: бэкап $DATE создан и отправлен ==="
Итог темы: скрипт растят по кирпичу: одна команда → переменные с $( ) (значение замораживается при присваивании) → связка через && (следующий шаг только при успехе предыдущего) → секреты в ~/.pgpass (chmod 600!), а не в коде → уборка за собой через rm и find -mtime +7 -delete → свой инструмент log() (DRY, не дублируй) → защита set -euo pipefail + trap ... ERR с ярлычком STEP, чтобы скрипт падал честно и говорил, ГДЕ упал. Кавычки: двойные подставляют переменные, одинарные — буквально (пароли и trap — в одинарных). Перенаправление: > затирает, >> дописывает. Запускать такой скрипт по расписанию — через cron (см. раздел ниже).

Firewall (firewalld)

Ядро фильтрует пакеты через netfilter. Управляли через iptables, потом nftables. На современном Fedora/RHEL стандарт — firewalld (обёртка над nftables с моделью зон).

КОНЦЕПТ Зоны firewalld 
Каждый интерфейс попадает в ЗОНУ.
У зоны свой список разрешённых сервисов и портов.

Самые частые зоны:
public              ⭐ дефолт серверов — закрыта, нужно явно открывать
home, internal      доверенная локальная сеть
work                рабочая сеть
trusted             всё разрешено (используется для VPN иногда)
drop                всё дропать (без ответа)
block               всё дропать (с ICMP-reject)
docker              автоматическая для docker-мостов
FedoraWorkstation   ⚠️ десктоп-зона, ПЕРМИССИВНАЯ
                    (открыты 1025-65535/tcp+udp по умолчанию)
                    НА ПРОДЕ НЕ ИСПОЛЬЗОВАТЬ
BASH Управление 
# === ПОСМОТРЕТЬ ===
sudo firewall-cmd --get-active-zones
sudo firewall-cmd --list-all                   # текущая зона целиком
sudo firewall-cmd --get-services | head        # ВСЕ доступные имена

# === ДОБАВИТЬ ===
sudo firewall-cmd --permanent --add-service=https
sudo firewall-cmd --permanent --add-port=8080/tcp
sudo firewall-cmd --reload                     # ⚠️ применить permanent!

# === УБРАТЬ ===
sudo firewall-cmd --permanent --remove-service=samba-client
sudo firewall-cmd --reload

# === ПРОВЕРИТЬ ===
sudo firewall-cmd --query-port=8080/tcp        # yes/no
sudo firewall-cmd --query-service=ssh

# === ПЕРЕМЕСТИТЬ ИНТЕРФЕЙС В ДРУГУЮ ЗОНУ ===
sudo firewall-cmd --permanent --zone=public --change-interface=eth0
sudo firewall-cmd --reload
⚠️ Главная ошибка с firewalld: сделал --permanent --add-service=..., попробовал — не работает. Забыл --reload. Permanent-изменения попадают в файлы, но в runtime не применяются до reload. Запомни: после permanent — всегда reload.
FAMILY Эволюция инструментов фильтрации

nftables    новый, единый синтаксис, ядро 4.0+ — на современных дистрах
firewalld   обёртка над nftables, концепция зон (Fedora, RHEL)
ufw         обёртка над iptables (Ubuntu) — простая, не в Fedora

# На собес: на современном RHEL/Fedora под капотом nftables,
# но управляют через firewalld. На Ubuntu — ufw поверх iptables.

DNS — имена в IP

FLOW Как программа резолвит имя в IP 
1. /etc/hosts          локальный файл — статические соответствия
                       ⭐ ядро смотрит сюда ПЕРВЫМ
                       пример: "127.0.0.1 myapp.local" — кастомный домен

2. /etc/resolv.conf    куда идти за DNS, если в hosts нет
                       на современной Fedora указывает на 127.0.0.53
                       (systemd-resolved — локальный кэш)

3. systemd-resolved    локальный stub-resolver
                       кэширует ответы, форвардит апстриму
                       апстрим в /etc/systemd/resolved.conf или
                       пришёл от DHCP через NetworkManager
BASH dig — главный инструмент диагностики DNS 
dig +short github.com               # ⭐ только IP, без шапки
dig github.com                      # полный вывод со всеми секциями
dig @8.8.8.8 github.com             # ⭐ спросить КОНКРЕТНЫЙ DNS
                                    # (обойти локальный кэш)

# Типы записей:
dig A    github.com +short          # IPv4-адрес (по умолчанию)
dig AAAA github.com +short          # IPv6-адрес
dig MX   gmail.com  +short          # почтовые серверы
dig TXT  google.com +short          # текстовые (SPF, DKIM, верификации)
dig NS   github.com +short          # сами DNS-серверы домена
dig CNAME www.github.com +short     # алиасы (имя → имя)
dig -x 140.82.121.4 +short          # ОБРАТНЫЙ — IP → имя (PTR)

# Системный кэш:
resolvectl status                   # что systemd-resolved знает
sudo resolvectl flush-caches        # сбросить кэш
Чеклист «не резолвится»:
1. dig X — резолвится ли через локальный кэш?
2. dig @8.8.8.8 X — резолвится через сторонний DNS? Если да — у тебя битый локальный.
3. cat /etc/resolv.conf — куда вообще шлёт.
4. resolvectl status — что systemd-resolved знает про апстримы.

SSH — удалённое управление

Модель работы с ключами

FLOW Как ssh пускает по ключу без пароля 
1. Ты генерируешь ПАРУ:
   id_ed25519       приватная часть (НИКОГДА никому, никуда)
   id_ed25519.pub   публичная (можно копировать куда угодно)

2. Публичную часть копируешь на сервер:
   ~/.ssh/authorized_keys (по строке на ключ)

3. При подключении:
   сервер шлёт «вызов» (challenge)
   твой ssh-клиент подписывает приватным ключом
   сервер проверяет подпись твоим публичным
   если ок → впускает БЕЗ пароля

# Приватный ключ НИКОГДА не покидает твою машину. Только подписи.
BASH Создание и копирование 
ssh-keygen -t ed25519 -C "kirill@laptop"
# -t тип, -C комментарий (метка для человека)
# спросит пароль для шифрования приватного ключа (passphrase)
# можно оставить пустым на десктопе

# Копировать публичный на сервер:
ssh-copy-id -p 2222 user@server.example.com
# спросит пароль ОДИН раз и положит ~/.ssh/authorized_keys

# Подключиться:
ssh -p 2222 user@server.example.com
RSA vs Ed25519: На современных серверах используй Ed25519 — ключи ~100 байт, быстрая подпись, безопасность ≈ RSA-4096 при меньшем размере. RSA нужен только если сервер очень старый.
⚠️ ПРАВА SSH откажется работать с неправильными правами 
~/.ssh/             700      drwx------
id_ed25519          600      -rw------- (приватный — только владелец)
id_ed25519.pub      644      -rw-r--r-- (публичный — секрета нет)
authorized_keys     600      -rw------- (на сервере)
known_hosts         644      -rw-r--r--

# Если права слабее — ssh выдаст "WARNING: UNPROTECTED PRIVATE KEY FILE"
# и откажется использовать ключ. Это защита от случайных утечек.

/etc/ssh/sshd_config Чеклист для прода

+ fail2ban: отдельный демон, смотрит в /var/log/secure, банит IP после N неудачных SSH-попыток (через iptables/firewalld). Дополнительный слой защиты — обязателен на любом боевом сервере с открытым SSH.

SSH-туннели (port forwarding)

BASH -L и -R 
# === LOCAL FORWARD (-L) ===
# «у меня НЕТ доступа к Grafana на серверной сети,
#  но я могу зайти по SSH на bastion, у которого есть»

ssh -L 3000:grafana.internal:3000 user@bastion
# теперь у меня на localhost:3000 → это Grafana на удалённой сети
# открой http://localhost:3000 в браузере — попадёшь на Grafana

# === REMOTE FORWARD (-R) ===
# «сервер за NAT, я хочу пробросить его порт к себе»

ssh -R 8080:localhost:80 user@public-server
# на public-server:8080 → ведёт в МОЙ localhost:80

# === ЗАПОМНИТЬ ===
# -L (Local)  : локальный порт → удалённый адрес
# -R (Remote) : удалённый порт → локальный адрес

# === SOCKS-ПРОКСИ ===
ssh -D 1080 user@server          # запустить SOCKS5 на localhost:1080
                                  # дальше браузер настраивается на SOCKS — весь трафик через сервер
Итог темы: ip -br a — интерфейсы, ip route — куда идут пакеты. ss -tlnp — кто слушает порты; 127.0.0.1 = только локально, 0.0.0.0 = всем. firewalld управляется зонами; permanent-изменения требуют --reload. На Fedora под капотом — nftables. DNS: /etc/hosts → /etc/resolv.conf → systemd-resolved → апстрим; диагностика — dig @сервер имя тип. SSH: Ed25519-ключи, ~/.ssh/config для алиасов, прод-чеклист — порт не 22, PermitRootLogin no, PasswordAuthentication no, fail2ban. Туннели: -L локальный→удалённый, -R наоборот, -D SOCKS.

🟢 nginx — веб-сервер и reverse proxy

nginx — программа, которая слушает TCP-порт и отвечает на HTTP-запросы. То же делают Python http.server, Apache, Node Express, Go net/http — но nginx сделан под высокую нагрузку и обычно стоит перед другими приложениями (reverse proxy). Этот блок: модель процессов, конфиги, server/location, proxy_pass, балансировка, SSL, SELinux-ловушка на Fedora.

Модель процессов

FLOW Что происходит при systemctl start nginx 
1. systemd запускает /usr/sbin/nginx (от root — нужно чтобы привязаться к :80)
2. nginx форкается в МАСТЕР-процесс
3. Мастер читает /etc/nginx/nginx.conf
4. Мастер форкает РАБОЧИЕ процессы (workers) —
   по одному на ядро CPU (worker_processes auto)
5. Мастер дальше следит за воркерами, перечитывает конфиг по reload
6. Воркеры слушают порты, сразу понижают права до юзера nginx
   ⭐ безопасность: дыра в воркере = атакующий получит права nginx,
   а не root

# Проверь:
ps -ef | grep nginx
# увидишь: 1 master + N workers (N = nproc)

Структура файлов

PATHS Где что лежит на Fedora/RHEL 
/usr/sbin/nginx           бинарник
/etc/nginx/               конфиги, ты их редактируешь
   nginx.conf             корневой
   conf.d/*.conf          ⭐ СЮДА кладёшь свои server-блоки
   default.d/*.conf       в дефолтный server-блок добавочные location'ы
   mime.types             расширение → MIME-тип
   *.default              нетронутые копии заводских (на случай факапа)
/usr/share/nginx/html/    дефолтная папка со статикой ("Welcome to nginx")
/var/log/nginx/
   access.log             ⭐ каждый запрос — строка
   error.log              ⭐ ошибки конфига и обработки
/var/cache/nginx/         кэш (если включён)
/run/nginx.pid            файл с PID мастера

# ⚠️ На Debian/Ubuntu схема ДРУГАЯ:
#    /etc/nginx/sites-available/  +  /etc/nginx/sites-enabled/
#    (симлинки between them, аналог /etc/systemd/system/*.wants/)

Структура конфига

HIERARCHY Блоки nginx.conf 
main context (глобальные настройки)
  ├─ user nginx;                       воркеры от этого юзера
  ├─ worker_processes auto;            по одному на ядро
  └─ events { worker_connections 1024; }  каждый воркер тянет 1024 коннекта
       # 4 ядра × 1024 = ~4096 одновременных соединений

  http {
       sendfile on;                    ⭐ zero-copy отдача статики (быстро)
       keepalive_timeout 65;           держать коннект 65 сек после ответа
       include /etc/nginx/mime.types;

       log_format main '$remote_addr - $remote_user [$time_local] ...';
       access_log /var/log/nginx/access.log main;

       server {                        ВИРТУАЛЬНЫЙ ХОСТ (сайт)
           listen 80;
           server_name example.com;
           root /var/www/example;

           location / { ... }          КАК обрабатывать конкретный путь
           location /api/ { ... }
       }

       include /etc/nginx/conf.d/*.conf;    ⭐ подгрузить твои конфиги
  }

Как nginx выбирает server и location

VIRTUAL HOSTS Несколько сайтов на одном IP 
# На один порт может слушать несколько server { } блоков:
server {
    listen 80;
    server_name example.com;       ← если Host: example.com → сюда
    root /var/www/example;
}
server {
    listen 80;
    server_name kirill.dev;        ← если Host: kirill.dev → сюда
    root /var/www/kirill;
}
server {
    listen 80 default_server;
    server_name _;                 ← всё, что не подошло → сюда
    root /usr/share/nginx/html;
}

# nginx смотрит ЗАГОЛОВОК Host: в HTTP-запросе (его шлёт браузер всегда)
# и выбирает подходящий server. На одном IP — сотни сайтов.
LOCATION Правила выбора внутри server 
location = /exact          ТОЧНОЕ совпадение — самый высокий приоритет
location ^~ /assets/       префикс, не проверять регулярки после
location ~ \.php$          регулярка, регистрозависимая
location ~* \.(png|jpg)$   регулярка, БЕЗ учёта регистра
location /api/             обычный префикс — самый длинный выигрывает
location /                 «всё остальное», fallback

# Алгоритм:
# 1. Точное совпадение (=) — если есть, ВЫИГРАЛО, стоп.
# 2. Префиксы с ^~ — если есть, регулярки не смотрим.
# 3. Регулярки (~ и ~*) — по порядку записи.
# 4. Обычные префиксы — самый длинный выигрывает.

Reverse proxy через proxy_pass

EXAMPLE Передача запросов бэкенду 
location /api/ {
    proxy_pass http://127.0.0.1:9000/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
⚠️ Слэш в proxy_pass — главная грабля nginx:
proxy_pass http://backend:9000/; (со слэшем) — УДАЛИТЬ /api/ из URL, передать остаток. Запрос /api/users уйдёт бэкенду как /users.
proxy_pass http://backend:9000; (без слэша) — оставить путь как есть. Запрос /api/users уйдёт как /api/users.
Запомни: есть слэш = подменить префикс, нет слэша = оставить весь путь.
HEADERS Зачем proxy_set_header 
По умолчанию бэкенд видит:
   Host: имя из proxy_pass (т.е. "127.0.0.1:9000")
   IP клиента: IP nginx'а (т.е. 127.0.0.1)
   Схема: всегда HTTP, не HTTPS

⭐ Это часто ЛОМАЕТ приложение:
   — генерация ссылок будет на "127.0.0.1:9000"
   — логи будут показывать nginx как клиента
   — приложение не знает, что снаружи был HTTPS

Поэтому стандартный набор заголовков:
   proxy_set_header Host $host;
                    ← передать оригинальный Host: ("example.com")
   proxy_set_header X-Real-IP $remote_addr;
                    ← реальный IP клиента
   proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
                    ← цепочка прокси (если их несколько)
   proxy_set_header X-Forwarded-Proto $scheme;
                    ← была ли изначально HTTPS-схема

# Приложение (FastAPI, Django) умеет читать эти заголовки
# через middleware (например, TrustedHostMiddleware + ProxyHeadersMiddleware).

SELinux-ловушка на Fedora

SYMPTOM 502 Bad Gateway при правильном конфиге 
# Конфиг правильный, бэкенд жив:
curl http://127.0.0.1:9000/      ✓ работает напрямую
curl http://localhost:8080/api/  ✗ 502 Bad Gateway

# В /var/log/nginx/error.log:
connect() to 127.0.0.1:9000 failed (13: Permission denied)
                                    ↑ это SELinux, не файловые права!

# Причина: SELinux запрещает nginx делать ИСХОДЯЩИЕ TCP-соединения.
# Политика httpd_t не пускает в обычные порты.

# Лечение:
sudo setsebool -P httpd_can_network_connect on
                ↑ -P = persistent (сохранить через ребут)

# Проверка:
getsebool httpd_can_network_connect       # должно: on

# Альтернатива (для конкретного порта):
sudo semanage port -a -t http_port_t -p tcp 9000

Балансировка нагрузки через upstream

EXAMPLE Несколько бэкендов за одним nginx 
http {
    upstream backend {
        server 127.0.0.1:9000;
        server 127.0.0.1:9001;
        server 127.0.0.1:9002 weight=2;        ← в 2 раза больше нагрузки
        server backup.local:9000 backup;        ← резерв, если все основные упали

        # Алгоритм:
        # (по умолчанию) round-robin — по очереди
        # least_conn;      — кому меньше всего соединений
        # ip_hash;         — один клиент всегда на один сервер (sticky)
        # hash $request_uri consistent;  — по URL (для кэшей)

        # Таймауты:
        keepalive 32;     ← держать 32 коннекта к каждому бэкенду
    }

    server {
        listen 8080;
        location / {
            proxy_pass http://backend;          ← упомянуть имя из upstream
            proxy_set_header Host $host;
        }
    }
}

# Если бэкенд не ответил — nginx сам перенаправит к следующему,
# и пометит мёртвый как недоступный на fail_timeout (по умолчанию 10 сек).

Git Advanced — merge, rebase, конфликты, reflog

Базовая модель

Коммит — это снимок проекта + ссылка на родителя + сообщение. Все коммиты выстраиваются в цепочку: A → B → C → D. Ветка — это просто указатель на последний коммит, буквально файл с хэшем внутри (в .git/refs/heads/имя). HEAD — указатель «где я сейчас стою».

EXAMPLE Развилка двух веток 
A ── B ── C ── X ── Y      (main: ушли вперёд)
             \
              D ── E         (feature: я делал свою фичу)

merge vs rebase — главное отличие

MERGE «Гостеприимный хозяин» 
git checkout main
git merge feature

Результат:
A ── B ── C ── X ── Y ── M     ← M = merge-коммит, ДВА родителя
            \             /
             D ── E ─────/

✅ Безопасно. Ничего не переписывается.
✅ Видно когда что слили.
❌ История становится «спагетти» из развилок.
❌ Мусорные коммиты "Merge branch feature into main".
REBASE «Переписыватель истории» 
git checkout feature
git rebase main

Результат:
A ── B ── C ── X ── Y          (main)
                     \
                      D' ── E'  (feature, "висит" от Y, не от C)

# D' и E' — НОВЫЕ коммиты с НОВЫМИ хэшами.
# Те же изменения, но "переигранные" поверх Y.
# Старых D и E больше нет в истории — git подделал дневник.

✅ Линейная история, читается как книга.
✅ Нет мусорных merge-коммитов.
❌ Переписывает историю → хэши меняются.
❌ ⚠️ ОПАСНО для shared-веток.
👑 Золотое правило rebase: НИКОГДА не делай rebase на коммитах, которые уже запушены в shared-ветку (main, develop), где работают другие люди. Иначе после твоего --force-push у коллеги при git pull старые коммиты сольются с новыми, и в логе окажутся ДВА набора одних и тех же изменений с разными хэшами. Полный ад. Rebase можно — только на своих локальных ветках, до пуша.
КОГДА ЧТО Шпаргалка 
Делаешь фичу в одиночку, готовишь PR        → rebase на main перед пушем
Запушил ветку, коллега с ней работает       → ⚠️ только merge
Сливаешь PR в main                          → merge (или squash merge)
Локальные коммиты, ещё не отправлял         → rebase свободно

Конфликты: <<<<<<<

Возникают когда обе ветки правили одну и ту же строку по-разному. Git не может выбрать сам — оставляет тебе маркеры в файле:

FILE Что видишь после конфликта 
<<<<<<< HEAD
print("hello from MAIN")          ← версия твоей текущей ветки
=======
print("hello from FEATURE")       ← версия ветки, которую сливаешь
>>>>>>> feature
BASH Процесс разрулирования 
# 1. посмотреть, какие файлы в конфликте
git status

# 2. открыть файл в редакторе, УБРАТЬ маркеры (<<<, ===, >>>)
#    оставить нужную версию (или гибрид)
nano file.py
cat file.py            # проверить — никаких маркеров не осталось

# 3. сообщить git'у, что конфликт решён
git add file.py

# 4. закрыть слияние
git commit             # для merge — пишет автоматический message
git rebase --continue  # для rebase
git cherry-pick --continue  # для cherry-pick

# === ЕСЛИ ЗАПУТАЛСЯ И ХОЧЕШЬ НАЧАТЬ ЗАНОВО ===
git merge --abort         # вернуть всё как было до начала merge
git rebase --abort        # для rebase
git cherry-pick --abort   # для cherry-pick
                          # ⭐ "--abort" работает для всех трёх — твой лучший друг

reflog — машина времени git'а

Git ведёт журнал всех движений HEAD'а — каждый коммит, checkout, reset, merge, rebase. Из reflog'а можно вернуться в любое состояние из прошлого, даже если ветка удалена и коммит «висит в воздухе». Хранится 90 дней по умолчанию.

BASH Спасение из «всё пропало» 
git reflog                       # увидеть все ходы за последнее время

# вывод:
# f990d6b HEAD@{0}: commit (merge): merge feature
# 8b9eeb6 HEAD@{1}: checkout: moving from feature to main
# 5be66c1 HEAD@{2}: commit: feature: change greeting
#         ↑           ↑
#         хэш         "N шагов назад от текущего"

# Вернуться к состоянию N ходов назад:
git reset --hard HEAD@{1}        # на состояние ОДИН ход назад
git reset --hard f990d6b         # или прямо по хэшу

# Восстановить удалённую ветку:
git checkout -b восстановленная HEAD@{5}
Что reflog НЕ спасёт: файлы, которые ты редактировал, но никогда не добавлял в git (нет git add). Если делал git reset --hard с такими файлами — они уничтожены навсегда. Reflog отслеживает коммиты и движения HEAD, не сами файлы.

reset — три режима

МОДЫ От мягкого к жёсткому 
git reset --soft HEAD~1
    ↓
    "откатить КОММИТ, оставить файлы в STAGING"
    как будто ты сделал git add, но ещё не commit'нул
    ⭐ хочешь переписать сообщение или сразу пересобрать коммит

git reset --mixed HEAD~1     (дефолт — флаг можно не указывать)
    ↓
    "откатить коммит И убрать из staging, файлы оставить в РАБОЧЕЙ ПАПКЕ"
    ⭐ хочешь пересобрать заново: выбрать что куда

git reset --hard HEAD~1
    ↓
    ⚠️ "откатить ВСЁ: коммит, staging, файлы на диске перезаписаны"
    правки УНИЧТОЖАЮТСЯ
    ⭐ когда уверен на 100% и хочешь чистого состояния

cherry-pick — скопировать один коммит

«Сорвать вишенку с дерева» — взять один коммит из ветки и применить его поверх текущей. Часто используется чтобы запортить hotfix из main в release-ветку, не таща всю остальную историю.

BASH Использование 
git checkout hotfix-1.2
git cherry-pick 5be66c1          # хэш конкретного коммита
git cherry-pick feature          # последний коммит ветки feature
git cherry-pick A B C            # несколько подряд
git cherry-pick A..D             # диапазон (НЕ включая A)
git cherry-pick A^..D            # диапазон (включая A) — A^ это "родитель A"

# При конфликте — стандартный процесс:
# отредактировать файл → git add → git cherry-pick --continue
# или git cherry-pick --abort

# Если коммит "пустой" после разрешения конфликта
# (значит изменения уже есть в текущей ветке):
git cherry-pick --skip           # пропустить
git commit --allow-empty         # или создать пустой коммит

rebase -i (interactive) — squash и reword

Самый мощный приём: переписать историю последних N коммитов — сжать, переименовать, переставить, выкинуть. Используется перед пушем, чтобы из 5 «WIP/typo/fix» коммитов сделать ОДИН осмысленный.

BASH Запуск 
git rebase -i HEAD~5        # редактировать 5 последних коммитов
git rebase -i <хэш-родителя> # все коммиты ПОСЛЕ указанного

# Git откроет редактор со списком:
pick abc123 первый коммит
pick def456 второй коммит
pick 789abc третий коммит

# Команды (меняешь "pick" на нужную):
# p, pick   = оставить как есть
# r, reword = оставить, но изменить сообщение
# s, squash = слить с предыдущим, оба сообщения объединить
# f, fixup  = как squash, но выкинуть сообщение этого коммита
# d, drop   = выкинуть коммит совсем
# e, edit   = остановиться на нём, можно правки внести
# (строки можно переставлять — порядок коммитов изменится)

# Сохраняешь → git проигрывает план → возможно ещё раз откроет редактор
# (для сжатого сообщения, если был squash).
EXAMPLE Типовой кейс — squash перед PR 
# Было:
pick abc123 WIP
pick def456 typo
pick 789abc опять забыл
pick aaabbb вроде работает
pick cccddd точно работает

# Стало (меняем 4 нижних на squash):
pick abc123 WIP
squash def456 typo
squash 789abc опять забыл
squash aaabbb вроде работает
squash cccddd точно работает

# После сохранения и редактирования сообщения → ОДИН коммит:
feat: add user authentication

# Это и есть "красивая история" для PR.
⚠️ После rebase -i: история ПЕРЕПИСАНА, хэши новые. Если ты УЖЕ запушил эту ветку — git push --force-with-lease (безопаснее чем --force, проверяет что remote не изменился без тебя). Для ШАРЕД ветки — НЕЛЬЗЯ.

bisect — найти коммит-виновник бага

Сценарий: «месяц назад работало, сейчас не работает, в какой из 200 коммитов между ними сломалось?». Ручной перебор — ад. git bisect делает бинарный поиск: ты говоришь «вот этот старый коммит — good, вот этот свежий — bad», git выкатывает середину, ты проверяешь, говоришь good/bad, git выкатывает следующую середину. За log₂(N) шагов находит виновника.

BASH Процесс

git bisect bad                   # текущий — сломан
git bisect good abc123           # коммит abc123 — работал

# git выкатил середину истории.
# Теперь ТЫ запускаешь приложение, тестируешь:
git bisect good                  # если на этом коммите всё работает
# или
git bisect bad                   # если сломано

# git выкатывает следующую середину между good и bad.
# Повторять, пока git не скажет:
# "abc123 is the first bad commit"

# Закончить:
git bisect reset

YAML — синтаксис

YAML — формат файла конфигурации. Главное правило — отступы строго через пробелы, не табы.

Неправильные отступы в YAML
services:
    backend:      # 4 пробела — ОШИБКА
      ports:
        - "8000:8000"

Причина: сервисы должны иметь 2 пробела, а не 4.

Правильные отступы
services:          # 0 пробелов
  backend:         # 2 пробела
    ports:         # 4 пробела
      - "8000:8000"  # 6 пробелов
Запомни: depends_on задаёт порядок запуска, но не ждёт пока сервис полностью готов. Если база стартует медленно — бэкенд может упасть и перезапуститься.

SQL и PostgreSQL

SQL — язык запросов к базе данных. PostgreSQL — одна из самых популярных реляционных баз данных.

Аналогия: База данных — это Excel таблица. SQL — это команды для работы с ней: добавить строку, найти строку, изменить, удалить.

Миграция — создание таблицы

CREATE TABLE IF NOT EXISTS topics (
-- CREATE TABLE — создать таблицу
-- IF NOT EXISTS — не падать с ошибкой если таблица уже есть

    id         SERIAL PRIMARY KEY,
    -- SERIAL — автоматически увеличивается (1, 2, 3...)
    -- PRIMARY KEY — уникальный идентификатор строки

    -- VARCHAR(100) — текст до 100 символов

    -- INTEGER — целое число
    -- DEFAULT 0 — по умолчанию 0
    -- CHECK — ограничение: только от 0 до 100

    notes      TEXT,
    -- TEXT — текст любой длины, может быть пустым

    updated_at TIMESTAMP DEFAULT NOW()
    -- TIMESTAMP — дата и время
    -- NOW() — автоматически ставит текущее время
);

-- EXPLAIN ANALYZE — выполнить запрос и показать реальное время

  Rows Removed by Filter: 4

Execution Time: 0.033 ms

JOIN — объединение таблиц

JOIN объединяет строки из двух таблиц по связанной колонке. Без JOIN нельзя работать с реальными базами где данные разнесены по нескольким таблицам.

SQL Виды JOIN 
-- INNER JOIN — только совпадающие строки в обеих таблицах:
SELECT users.name, topics.name, progress_log.new_progress
FROM progress_log
INNER JOIN users  ON progress_log.user_id = users.id
INNER JOIN topics ON progress_log.topic_id = topics.id;

-- LEFT JOIN — все строки левой таблицы + совпадения из правой:
SELECT users.name, progress_log.new_progress
FROM users
LEFT JOIN progress_log ON users.id = progress_log.user_id;
-- пользователи без записей тоже попадут в результат (NULL вместо данных)

-- RIGHT JOIN — все строки правой таблицы + совпадения из левой
-- FULL JOIN  — все строки из обеих таблиц
Запомни: INNER JOIN — самый частый. LEFT JOIN используют когда нужны все записи из главной таблицы даже если связанных данных нет. Результат JOIN — новая временная таблица из объединённых колонок обеих таблиц.

Капкан: WHERE на правой таблице убивает LEFT JOIN

Главная ловушка LEFT JOIN, на которой палятся даже мидлы. Стоит написать условие на колонку правой таблицы в WHERE — и LEFT JOIN тихо превращается в INNER JOIN. Прямое следствие того, что NULL не проходит WHERE.

SQL Как нечаянно превратить LEFT в INNER — и как не надо 
-- ❌ ЛОВУШКА: условие на правую таблицу (orders) в WHERE
SELECT u.name, o.amount
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.amount > 100;
-- у юзеров БЕЗ заказов o.amount = NULL
-- NULL > 100  =  NULL  (не TRUE!)  → WHERE их выбрасывает
-- итог: беззаказные юзеры исчезли, LEFT работает как INNER

-- ✅ ПРАВИЛЬНО: фильтр правой таблицы — в ON, а не в WHERE
SELECT u.name, o.amount
FROM users u
LEFT JOIN orders o ON o.user_id = u.id AND o.amount > 100;
-- все юзеры на месте; нет заказа >100 → просто NULL в колонке

-- ✅ Найти юзеров БЕЗ заказов ("мёртвые души"):
SELECT u.*
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;          -- заказа нет → колонка NULL → пустой юзер
Правило: фильтр по левой таблице можно класть в WHERE; фильтр по правой (которую LEFT сохраняет) — только в ON, иначе NULL не пройдёт WHERE и LEFT схлопнется в INNER. Прямая связь с разделом «NULL — заражает всё».

GROUP BY и HAVING — группировка

SQL Агрегатные функции и группировка 
-- Агрегатные функции:
SELECT COUNT(*)        FROM topics;  -- количество строк
SELECT AVG(progress)   FROM topics;  -- среднее значение
SELECT SUM(progress)   FROM topics;  -- сумма
SELECT MAX(progress)   FROM topics;  -- максимум
SELECT MIN(progress)   FROM topics;  -- минимум

-- GROUP BY — считать агрегат для каждой группы отдельно:
SELECT
  CASE
    WHEN progress = 0  THEN 'не начато'
    WHEN progress < 50 THEN 'в процессе'
    ELSE                    'почти готово'
  END AS статус,
  COUNT(*) AS количество
FROM topics
GROUP BY статус;

-- HAVING — фильтр ПОСЛЕ группировки (WHERE нельзя использовать с агрегатами):
SELECT name, AVG(progress)
FROM topics
GROUP BY name
HAVING AVG(progress) > 30;
-- WHERE — фильтрует строки ДО группировки
-- HAVING — фильтрует группы ПОСЛЕ GROUP BY

NULL — ловушки

SQL Правильная работа с NULL 
-- НЕПРАВИЛЬНО — всегда вернёт 0 строк:
SELECT * FROM topics WHERE notes = NULL;

-- ПРАВИЛЬНО:
SELECT * FROM topics WHERE notes IS NULL;
SELECT * FROM topics WHERE notes IS NOT NULL;

-- Ловушка с != :
WHERE notes != 'test'
-- строки где notes = NULL тоже НЕ попадут в результат!

-- Правильно:
WHERE notes != 'test' OR notes IS NULL;

-- COALESCE — заменить NULL на значение по умолчанию:
SELECT name, COALESCE(notes, 'нет заметок') FROM topics;

IntersectionObserver — отслеживание видимости

Браузерный API который следит за тем, какой элемент сейчас виден на экране. Мы используем его для scroll spy — автоматического переключения активного пункта в меню при прокрутке.

// querySelectorAll — найти все элементы на странице по селектору
// 'section' — все теги <section>

const observer = new IntersectionObserver(entries => {
// IntersectionObserver — создать наблюдателя
// entries — список элементов которые изменили видимость

  entries.forEach(entry => {
  // forEach — пройти по каждому изменению

    if (entry.isIntersecting) {
    // isIntersecting — элемент сейчас виден в области просмотра

      const id = entry.target.id;
      // target — сам элемент, id — его атрибут id (например "git")

      links.forEach(l => l.classList.remove('active'));

      // найти ссылку в меню которая ведёт на этот раздел
      // [href="#git"] — ссылка с атрибутом href равным "#git"

      // добавить выделение найденной ссылке
    }

}, { rootMargin: '0px 0px -70% 0px', threshold: 0 });
// rootMargin — сжимаем область срабатывания:
//   '0px 0px -70% 0px' = сверху 0, справа 0, снизу -70%, слева 0
//   срабатывает когда верх секции входит в верхние 30% экрана

GitHub Actions — автоматизация

GitHub Actions выполняет задачи автоматически при определённых событиях — например при каждом git push. Мы используем его для автоматической публикации сайта.

Аналогия: GitHub Actions — это помощник которому ты дал инструкцию заранее. Ты отправил файлы (git push) — помощник автоматически опубликовал сайт. Ты занимаешься своим делом, он своим.

Структура workflow файла

YAML .github/workflows/pages.yml

# название — только для читаемости

on:
  push:
    branches:
      - main
# когда запускать — при каждом push в ветку main

permissions:
  contents: read
  pages: write
  id-token: write
# разрешения — что этому скрипту разрешено делать
# pages: write — разрешить публикацию на GitHub Pages

jobs:
  deploy:
    runs-on: ubuntu-latest
    # runs-on — на какой виртуальной машине выполнять

      url: ${{ steps.deployment.outputs.page_url }}

CI/CD pipeline — три джоба

Один workflow может содержать несколько джобов. Они могут работать параллельно или по очереди. Мы построили цепочку: test → build → deploy.

Аналогия: Это как сборочный конвейер на заводе. Сначала ОТК проверяет деталь (test). Параллельно другой рабочий красит корпус (build). Только если оба справились — деталь идёт в упаковку (deploy). Один брак — вся линия стоит.
YAML .github/workflows/pages.yml — три джоба 
jobs:

  test:                          # джоб 1 — запускаем тесты
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - run: |
          cd backend
          pip install -r requirements.txt
          pip install pytest httpx
      - run: |
          cd backend
          pytest tests/ -v         # -v = verbose, показывает каждый тест

  build:                         # джоб 2 — билдим Docker образ
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t portfolio-backend ./backend

  deploy:                        # джоб 3 — деплоим на GitHub Pages
    runs-on: ubuntu-latest
    needs: [test, build]         # ← КЛЮЧЕВОЕ: ждать test И build
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/configure-pages@v4
        with:
          enablement: true
      - uses: actions/upload-pages-artifact@v3
        with:
          path: ./frontend
      - id: deployment
        uses: actions/deploy-pages@v4

Метрики в FastAPI — prometheus-client

PYTHON backend/app/main.py — добавить метрики 
import time
from fastapi import Request
from prometheus_client import Counter, Histogram, make_asgi_app

# Counter — счётчик, только растёт (количество запросов)
REQUEST_COUNT = Counter(
    'http_requests_total',           # название метрики в Prometheus
    'Total number of HTTP requests', # описание
    ['method', 'endpoint', 'status'] # labels — разрезы данных
)

# Histogram — гистограмма (распределение времени ответа)
REQUEST_LATENCY = Histogram(
    'http_request_duration_seconds',
    'HTTP request latency in seconds',
    ['endpoint']
)

# /metrics — эндпоинт куда заходит Prometheus
app.mount("/metrics", make_asgi_app())

# Middleware — перехватчик всех запросов
@app.middleware("http")
async def track_requests(request: Request, call_next):
    start = time.time()                  # время начала
    response = await call_next(request)  # выполнить запрос
    duration = time.time() - start       # сколько заняло

    if request.url.path != "/metrics":   # сами метрики не считаем
        REQUEST_COUNT.labels(
            method=request.method,
            endpoint=request.url.path,
            status=response.status_code
        ).inc()                          # +1 к счётчику
        REQUEST_LATENCY.labels(
            endpoint=request.url.path
        ).observe(duration)              # записать время в гистограмму

    return response

PromQL — язык запросов Prometheus

PromQL — специальный язык для запросов к метрикам. Пишется в Prometheus UI или в Grafana в режиме Code.

PROMQL Основные запросы 
http_requests_total
# просто показать все значения метрики

sum(http_requests_total) by (endpoint)
# сложить по группам: отдельно /topics, отдельно /metrics/

rate(http_requests_total[1m])
# скорость роста за последнюю минуту (запросов в секунду)

increase(http_requests_total[5m])
# прирост за последние 5 минут (сколько запросов пришло)

histogram_quantile(0.95, sum(rate(http_request_duration_seconds_bucket[5m])) by (le, endpoint))
# 95-й перцентиль времени ответа за 5 минут
# 95% запросов выполнились быстрее чем это значение
Перцентиль p95: Если p95 = 0.3 секунды — значит 95% запросов ответили быстрее чем за 0.3с. Оставшиеся 5% — медленнее. Это стандартная метрика производительности в продакшн системах. Среднее (average) врёт — один медленный запрос портит картину. Перцентиль честнее.

«Инфраструктура как код» — описание серверов, сетей, балансировщиков и баз в виде текстовых файлов в git, вместо кликов в админке. Любое изменение прода — это PR с ревью. Terraform vs Ansible: часто путают. Terraform создаёт ресурсы (виртуалки, сети, БД в облаке) — занимается тем, чего ещё нет. Ansible настраивает то, что уже есть (поставить пакеты, поправить конфиги, перезапустить сервисы). На проде их часто комбинируют: terraform поднимает 5 серверов → ansible их настраивает.

Terraform

HashiCorp, написан на Go в 2014-м. Multi-cloud — один синтаксис работает в AWS, GCP, Azure, Yandex Cloud, локальном Docker'е. С 2023-го у HashiCorp поменялась лицензия (BSL), сообщество форкнуло в OpenTofu — полностью совместимый, более «свободный». Синтаксис идентичный.

Боль, которую решает

ДО vs ПОСЛЕ Зачем оно вообще 
ДО Terraform:
   - Клики в AWS-консоли: EC2, RDS, Load Balancer, VPC...
   - Записываю шаги в Confluence (если не забыл)
   - Через неделю "сделай dev" — кликаю снова, получается ИНАЧЕ

   - Поднять dev на копии prod = git checkout dev-branch + apply

Жизненный цикл — 4 команды

BASH init → plan → apply → destroy 
terraform init      # ⭐ скачать провайдеры (раз в проекте)
                    # создаёт .terraform/ и .terraform.lock.hcl

terraform plan      # ⭐ "что будет?" — dry-run, ничего не делает
                    # ВСЕГДА смотри, особенно "destroy" в плане

terraform apply     # сделать
                    # спросит "yes" — нужно вписать ПОЛНОСТЬЮ
                    # -auto-approve = без вопросов (для CI)

terraform destroy   # снести всё, что terraform создал
                    # ⚠️ опасно на проде — снесёт всю инфру

State — главная концепция

terraform.tfstate — JSON-файл, в котором terraform запомнил, какие реальные ресурсы создал и какие у них ID в облаке. При каждом plan terraform сравнивает три вещи:

FLOW Как terraform решает «что изменилось» 
1. Что в твоих .tf-файлах    ← ЖЕЛАЕМОЕ
2. Что в terraform.tfstate    ← что я знаю, что создал
3. Что РЕАЛЬНО в облаке       ← API запрос

# Plan = разница между 1 и (2+3).
⚠️ Грабли state'а на проде:
• В state могут быть секреты (пароли БД, ключи) → в git НЕ кладут.
• Работают двое — нужен remote state (S3 + DynamoDB-lock, Terraform Cloud), иначе apply одновременно сломает инфру.
• Случайно удалил state — terraform забыл, что создал. Нужен terraform import для каждого ресурса вручную.
• terraform state list / state show / state rm — команды для управления.

Идемпотентность

CONCEPT Главная фича 
# Запускаешь terraform apply СНОВА, ничего не меняя:
Apply complete! Resources: 0 added, 0 changed, 0 destroyed.

# Terraform увидел: желаемое == реальное → ничего не трогает.
# Безопасно гонять в CI/CD на каждый коммит.
# В этом ОТЛИЧИЕ от bash-скриптов "ставь nginx" — те бы создали второй.

Boundary: когда что-то застряло в state

Ansible — автоматизация конфигурации

Ansible — инструмент для автоматического управления настройками серверов. Вместо того чтобы вручную настраивать каждый сервер по-очереди, ты описываешь в YAML файле что должно быть установлено и настроено — Ansible сам всё сделает на всех серверах.

Аналогия: Представь что у тебя 50 серверов и на каждый нужно установить nginx, создать пользователя и скопировать конфиг. Вручную — это 50 раз одно и то же. С Ansible — пишешь инструкцию один раз, запускаешь — готово на всех сразу.

Playbook — главный файл инструкций

YAML playbook.yml — установить и запустить nginx 
---
# --- обязательно в начале YAML файла

- name: Настроить веб-серверы
  # name — описание для читаемости

  hosts: webservers
  # hosts — на каких серверах выполнять (из inventory)

  become: true
  # become: true — выполнять с правами root (sudo)

  tasks:
    # tasks — список действий по порядку

    - name: Установить nginx
      apt:
        name: nginx
        state: present
        update_cache: true
      # apt — модуль для управления пакетами (Ubuntu/Debian)
      # state: present — убедиться что установлен
      # state: absent — убедиться что удалён

    - name: Скопировать конфиг nginx
      copy:
        src: files/nginx.conf
        dest: /etc/nginx/nginx.conf
        owner: root
        mode: '0644'
      # copy — скопировать файл с control node на сервер

    - name: Запустить и включить nginx
      service:
        name: nginx
        state: started
        enabled: true
      # service — управление системными сервисами
      # enabled: true — запускать автоматически при загрузке

    - name: Создать пользователя deploy
      user:
        name: deploy
        shell: /bin/bash
        groups: sudo
      # user — управление пользователями

Идемпотентность — главный принцип

Идемпотентность — запусти playbook 10 раз, результат всегда одинаковый. Если nginx уже установлен — Ansible не будет устанавливать снова. Это безопасно: можно запускать повторно без риска сломать то что работает. state: present означает "убедись что есть", а не "установи заново".
UNREACHABLE — не может подключиться к серверу
UNREACHABLE! => {"msg": "Failed to connect to the host via ssh"}

Причина: неверный IP, закрытый порт SSH, неверный ключ, или сервер выключен.

Диагностика
ssh ubuntu@192.168.1.10               # проверить SSH вручную
ansible all -m ping -vvv -i hosts     # подробный вывод (-vvv)
# в inventory проверить ansible_user, ansible_port, ansible_host
Changed: 0 но ошибки нет — ничего не применилось

Причина: задача уже в нужном состоянии (идемпотентность). Это нормально — Ansible не меняет то что уже правильно.

Jenkins — CI/CD сервер

Jenkins — сервер автоматизации. Он следит за репозиторием и при каждом изменении автоматически: собирает приложение, запускает тесты, деплоит на сервер. Это и называется CI/CD — непрерывная интеграция и доставка.

Аналогия: Jenkins — как конвейер на заводе. Ты положил деталь (сделал push в Git) — конвейер сам проверил, собрал, упаковал и отправил. Каждый шаг автоматический, ты только следишь за результатом.
Разница с GitHub Actions: GitHub Actions встроен в GitHub и бесплатен для открытых проектов. Jenkins — самостоятельный сервер, его нужно развернуть и поддерживать. Зато Jenkins более гибкий и популярен в корпоративной среде.

Jenkinsfile — описание pipeline

Jenkinsfile хранится в корне репозитория. Jenkins читает его и знает что делать при каждом push.

GROOVY Jenkinsfile — декларативный pipeline 
pipeline {
    // pipeline — объявляем что это Jenkins pipeline

    agent any
    // agent any — запускать на любом доступном агенте (исполнителе)

    environment {
        IMAGE_NAME = 'my-app'
        // environment — переменные доступные во всех stages
    }

    stages {
        // stages — список этапов, выполняются по порядку

        stage('Checkout') {
            // stage — один этап с именем
            steps {
                checkout scm
                // checkout scm — скачать код из Git репозитория
            }
        }

        stage('Build') {
            steps {
                sh 'docker build -t ${IMAGE_NAME}:${BUILD_NUMBER} .'
                // sh — выполнить shell команду
                // BUILD_NUMBER — встроенная переменная Jenkins (номер сборки)
            }
        }

        stage('Test') {
            steps {
                sh 'docker run --rm ${IMAGE_NAME}:${BUILD_NUMBER} pytest'
                // pytest — запустить тесты внутри контейнера
            }
        }

        stage('Deploy') {
            when {
                branch 'main'
                // when — условие: этот этап только для ветки main
            }
            steps {
                sh 'docker compose up -d --build'
            }
        }
    }

    post {
        // post — что делать после всех stages

        success {
            echo 'Деплой прошёл успешно!'
        }
        failure {
            echo 'Что-то сломалось — проверь логи!'
            // здесь можно добавить уведомление в Slack
        }
        always {
            sh 'docker system prune -f'
            // always — выполнить в любом случае (чистка)
        }
    }
}

Отказоустойчивые кластеры

Отказоустойчивость (High Availability, HA) — система продолжает работать даже если один из серверов упал. Достигается за счёт дублирования: нет ни одной точки отказа.

Аналогия: Один мост через реку — он упал, движение остановилось. Три моста через реку — один закрыт на ремонт, машины едут по двум другим. HA-кластер работает как три моста: один упал — остальные берут его нагрузку.

Ключевые понятия

BASH Словарь HA 
SPoF (Single Point of Failure)
— единственная точка отказа. HA = устранить все SPoF.

Replication (репликация)
— копирование данных в реальном времени на несколько серверов.
— Master → Slave. Пишем в Master, читаем с Slave.

Failover (переключение при сбое)
— автоматическое переключение на резервный сервер при падении основного.

Quorum (кворум)
— минимальное количество узлов для принятия решений.
— Нечётное количество узлов: 3 или 5. При 2 кластер может "застыть".

Load Balancer (балансировщик нагрузки)
— распределяет запросы между несколькими серверами.
— Пользователь всегда идёт в одну точку (VIP-адрес), не знает сколько серверов за ней.

VIP (Virtual IP)
— плавающий IP адрес. При падении одного сервера переходит на другой.
— Пользователи и приложения всегда используют VIP, не знают о переключении.

RTO (Recovery Time Objective) — максимальное время восстановления
RPO (Recovery Point Objective) — максимальная потеря данных

Split-brain — два сервера думают что они лидеры

Причина: потеря связи между узлами. Оба считают себя мастером и принимают записи — данные расходятся.

Решение — нечётное число узлов и кворум
# Минимум 3 узла — при потере 1 оставшиеся 2 составляют кворум
# и могут решить кто лидер. При 2 узлах — кворума нет.

# etcd/consul/ZooKeeper хранят "замок лидера":
# только тот кто держит замок — лидер.
# Если связь потеряна — замок истекает, другой узел берёт его.
Запомни: HA не защищает от всего. Она защищает от падения одного узла. Бэкапы — это другое: они защищают от потери данных (удалили таблицу, вирус, ошибка приложения). HA + регулярные бэкапы = надёжная система.

☸️ Kubernetes — оркестратор контейнеров

Kubernetes (он же K8s — «K», восемь букв, «s») — это автопилот для контейнеров. Docker умеет запустить контейнер на одной машине. K8s умеет держать сотни контейнеров на десятках машин: сам раскидывает их по серверам, перезапускает упавшие, масштабирует под нагрузку и даёт им стабильные адреса. Кубер тяжело заходит не потому что сложный, а потому что в нём много абстракций навалено разом. Поэтому ниже каждое понятие привязано к тому, что ты уже знаешь — Docker, nginx, systemd, etcd.

Аналогия на весь раздел: Docker Compose — это «запусти мне стек на этой машине». Kubernetes — это «вот тебе флот машин и список того, что должно работать; разруливай сам, кто где запущен, кто упал, кого перезапустить». Compose — повар на одной кухне. K8s — управляющий сетью ресторанов, который сам решает, в каком филиале готовить и кого вызвать на замену заболевшему.

Зачем нужен — боль, которую решает

Представь, что у тебя 20 контейнеров на 5 серверах руками через docker run. И вот вопросы, на которые у тебя нет ответа без оркестратора:

БОЛЬ Что делает Kubernetes за тебя 
Контейнер упал в 3 ночи     → K8s сам перезапустит (self-healing)
Сервер целиком умер          → K8s переедет его контейнеры на живые узлы
Нагрузка выросла в 10 раз     → K8s поднимет ещё реплик (autoscaling)
Выкатка новой версии          → K8s обновит поды по одному, без даунтайма
                               (rolling update; сломалось — откат)
Где запущен контейнер?        → K8s сам выбирает узел (scheduler)
Как найти контейнер в сети?   → стабильное DNS-имя через Service
Конфиги и пароли              → вынесены в ConfigMap / Secret
Ключевая идея — декларативность. Ты не командуешь «запусти контейнер» (это императив, как docker run). Ты описываешь желаемое состояние: «хочу, чтобы всегда работало 3 реплики моего приложения». K8s постоянно сравнивает «что хочу» с «что есть» и сам приводит реальность к желаемому. Это ровно та же идея, что у Terraform (желаемое состояние в коде + reconcile), только не для инфры, а для контейнеров в рантайме.

Архитектура: Control Plane и Nodes

Кластер K8s делится на две части: мозг (Control Plane) и мышцы (Worker Nodes — машины, где реально крутятся твои контейнеры).

АРХИТЕКТУРА Кто за что отвечает 
┌─ CONTROL PLANE (мозг кластера) ──────────────────────┐
│  kube-apiserver  — единая точка входа. ВСЁ общение     │
│                    идёт через него (kubectl, узлы).    │
│                    Аналог: API-сервер всего кластера.  │
│  etcd            — база состояния кластера (key-value).│
│                    ХРАНИТ "что должно работать".       │
│                    Тот самый etcd, что в Patroni!      │
│                    Потеряешь etcd — потеряешь кластер.  │
│  scheduler       — решает, на КАКОЙ узел поставить под  │
│                    (по свободным CPU/RAM).             │
│  controller-mgr  — следит "хочу 3 реплики = есть 3?",   │
│                    чинит расхождения (reconcile loop). │
└───────────────────────────────────────────────────────┘
┌─ WORKER NODE (мышцы, таких много) ───────────────────┐
│  kubelet         — агент на узле. Получает от мозга    │
│                    "запусти эти поды" и запускает их.  │
│                    Аналог: docker daemon + systemd.    │
│  kube-proxy      — сетевая магия, делает Service'ы.    │
│  container runtime — сам Docker/containerd, запускает  │
│                    контейнеры.                         │
└───────────────────────────────────────────────────────┘
Связь с тем, что знаешь: etcd ты уже видел в Patroni (раздел HA) — там он хранил «кто лидер PostgreSQL». В K8s etcd хранит всё состояние кластера — это его «source of truth», как terraform.tfstate для Terraform. kubelet на узле — это по сути «systemd + docker daemon», который следит, чтобы назначенные ему контейнеры жили.

Pod — атом Kubernetes

Pod — это минимальная единица, которой управляет K8s. Чаще всего Pod = один контейнер + обёртка вокруг него. Ты не управляешь контейнерами напрямую — ты управляешь подами.

Аналогия: Pod — это один docker run, но в скафандре. Внутри обычно один контейнер (твоё приложение), но у пода есть свой IP, свои тома и свой жизненный цикл. Иногда в поде живёт 2–3 контейнера, которые обязаны быть вместе (приложение + «sidecar» — например сборщик логов). Они делят один IP и localhost — как процессы на одной машине.
YAML Простейший Pod (pod.yaml) 
apiVersion: v1
kind: Pod                 # тип объекта
metadata:
  name: my-app            # имя пода
spec:
  containers:
    - name: web
      image: nginx:1.27   # тот же образ, что в docker run
      ports:
        - containerPort: 80
Важно про Pod: поды смертны и одноразовы (ephemeral). Упал — K8s не «лечит» этот под, а создаёт новый со новым IP. Поэтому на под нельзя ссылаться по IP — он постоянно меняется. Эту проблему решает Service (см. ниже). Сам по себе голый Pod почти не используют — его заворачивают в Deployment.

Deployment — следит, чтобы поды жили

Голый Pod упал — и всё, его никто не поднимет. Deployment — это надсмотрщик: ты говоришь «хочу 3 реплики», а он постоянно следит, чтобы их было ровно 3. Один упал — поднимет новый. Это и есть self-healing.

Аналогия: Deployment — это systemd с Restart=always, но для целой пачки подов сразу. Помнишь, как Restart=on-failure в твоём .service-юните перезапускал упавший процесс? Deployment делает то же самое для подов, плюс держит их заданное количество и умеет обновлять версию без даунтайма.
YAML Deployment с 3 репликами (deployment.yaml) 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-deploy
spec:
  replicas: 3             # ⭐ ЖЕЛАЕМОЕ состояние: всегда 3 пода
  selector:
    matchLabels:
      app: web            # какими подами я управляю (по метке)
  template:              # ШАБЛОН пода, который будут штамповать
    metadata:
      labels:
        app: web          # метка вешается на каждый под
    spec:
      containers:
        - name: web
          image: nginx:1.27
          ports:
            - containerPort: 80

# Поднять/обновить:
kubectl apply -f deployment.yaml
# Убить один под вручную → Deployment СРАЗУ поднимет новый (всегда 3)
# Масштабировать на лету:
kubectl scale deployment web-deploy --replicas=5
Rolling update: меняешь image: nginx:1.27 → 1.28 и делаешь kubectl apply. Deployment обновляет поды по одному: поднял новый — убил старый — и так по кругу. Сервис не падает ни на секунду. Сломалось — kubectl rollout undo deployment web-deploy откатит назад. Это твой CI/CD-деплой без даунтайма, встроенный в кубер.

Service — стабильный адрес для подов

Поды постоянно пересоздаются с новыми IP. Как тогда обратиться к приложению? Через Service — это стабильный виртуальный IP + DNS-имя, которое всегда указывает на актуальные поды и балансирует нагрузку между ними.

Аналогия — и тут ты уже всё знаешь: Service — это nginx upstream внутри кластера. Помнишь свой раздел про reverse proxy и балансировку? Там nginx держал список бэкендов и раскидывал на них запросы. Service делает ровно это: держит постоянный адрес, а за ним — меняющийся пул подов, и балансит между живыми. Поды приходят и уходят с новыми IP — Service-адрес неизменен.
YAML Service перед Deployment (service.yaml) 
apiVersion: v1
kind: Service
metadata:
  name: web-svc
spec:
  selector:
    app: web              # балансирует на поды с меткой app=web
  ports:
    - port: 80            # порт самого Service
      targetPort: 80      # порт внутри пода
  type: ClusterIP         # тип (см. ниже)

# Теперь другие поды зовут приложение по ИМЕНИ, а не по IP:
#   http://web-svc        ← внутренний DNS кластера сам резолвит
ТИПЫ SERVICE Как открыть доступ — изнутри или снаружи 
ClusterIP    — (по умолчанию) доступен ТОЛЬКО внутри кластера.
               Для общения сервисов между собой.
               Аналог: слушать на 127.0.0.1.

NodePort     — открывает порт на КАЖДОМ узле (30000-32767).
               Доступ снаружи по IP_узла:порт. Грубовато, для теста.

LoadBalancer — облако (AWS/GCP) поднимает внешний балансировщик
               с публичным IP. Прод-способ пускать трафик снаружи.

Ingress      — (отдельный объект, не тип Service) умный HTTP-роутер
               перед сервисами: домены, пути, SSL. Это буквально
               nginx/traefik как reverse proxy на входе в кластер.

Namespace, ConfigMap, Secret

ОБЪЕКТЫ Изоляция и конфигурация 
Namespace   — виртуальные "папки" внутри кластера.
              Делят кластер на части: dev / staging / prod,
              или по командам. Объекты в разных namespace
              не мешают друг другу (могут иметь одинаковые имена).
              kubectl get pods -n prod   # поды в namespace prod

ConfigMap   — НЕсекретная конфигурация вынесенная наружу образа:
              переменные окружения, конфиг-файлы.
              Аналог: переменные в docker-compose / .env файл.

Secret      — то же, но для ПАРОЛЕЙ, токенов, ключей.
              Хранится в base64 (это НЕ шифрование!), но
              управляется отдельно и его можно зашифровать в etcd.
              Прокидывается в под как env-переменная или файл.
Зачем выносить конфиг наружу: один и тот же образ должен работать и в dev, и в prod — отличаются только настройки (адрес БД, пароли). Поэтому конфиг не зашивают в образ, а подкидывают через ConfigMap/Secret. Это та же мысль, что «секреты не коммитят в Git, а кладут в переменные окружения» из раздела «Важно для DevOps».

kubectl — главные команды

kubectl (кубоконтроль) — это docker CLI, но для всего кластера. Через него идёт всё общение с kube-apiserver.

BASH Шпаргалка kubectl 
# Применить манифест (создать/обновить объекты):
kubectl apply -f deployment.yaml     # ⭐ главная команда (декларативно)

# Посмотреть что есть:
kubectl get pods                     # список подов
kubectl get pods -o wide             # + на каком узле и IP
kubectl get deploy,svc               # деплойменты и сервисы
kubectl get all                      # вообще всё в namespace
kubectl get pods -A                  # во ВСЕХ namespace

# Диагностика (твои главные инструменты, когда что-то сломалось):
kubectl describe pod my-app          # ⭐ подробности + события (Events!)
kubectl logs my-app                  # логи контейнера (аналог docker logs)
kubectl logs -f my-app               # стримить логи (как tail -f)
kubectl exec -it my-app -- bash      # ⭐ зайти внутрь пода (как docker exec)

# Управление:
kubectl scale deploy web --replicas=5   # масштабировать
kubectl rollout undo deploy web         # откатить обновление
kubectl delete pod my-app               # убить под (Deployment поднимет новый)
kubectl apply -f .                      # применить все yaml в папке

# Контекст и namespace:
kubectl config get-contexts          # к каким кластерам подключён
kubectl get pods -n kube-system      # системные поды самого кластера
Главный приём диагностики: под не поднимается — kubectl describe pod ИМЯ и читай блок Events внизу (там причина: нет образа, мало памяти, упал healthcheck). Не помогло — kubectl logs ИМЯ. Это связка как journalctl -u service + docker logs из прошлых разделов, только для кубера.

Связь с тем, что ты уже знаешь

⭐ КАРТА Кубер через знакомые понятия

Deployment   ≈  systemd с Restart=always + нужное число реплик

Ingress      ≈  nginx на входе: домены, пути, SSL
ConfigMap    ≈  переменные окружения / .env из docker-compose
Secret       ≈  секреты из переменных окружения (не в Git!)
Namespace    ≈  отдельные "проекты"/окружения dev/prod
etcd         ≈  terraform.tfstate / etcd из Patroni (состояние кластера)
kubelet      ≈  docker daemon + systemd на каждом узле
kubectl      ≈  docker CLI, но для всего кластера
apply -f     ≈  terraform apply (декларативно привести к желаемому)
Итог раздела: Kubernetes — автопилот для контейнеров на флоте машин. Ты декларативно описываешь желаемое состояние в YAML, а кластер сам его поддерживает. Pod — атом (контейнер+обёртка), смертен и одноразов. Deployment держит N живых реплик и обновляет без даунтайма. Service даёт стабильный адрес и балансит (как nginx upstream). etcd хранит состояние (как tfstate). kubectl describe + logs — первое, что смотришь, когда сломалось. Дальше по плану: поднять локальный кластер (minikube / kind / k3s) и потрогать всё это руками.

Jira и Confluence

Jira — инструмент для управления задачами и проектами. Confluence — корпоративная wiki для документации. Оба продукта от Atlassian, тесно интегрированы друг с другом.

Аналогия: Jira — это список дел команды на доске (кто что делает, когда). Confluence — это папка с инструкциями, схемами и решениями (как это делать). Вместе: задача в Jira ссылается на инструкцию в Confluence.

curl — проверка HTTP запросов

Bash скрипты

Шпаргалка по синтаксису bash — что с чем не путать (кавычки, скобки, операторы, слеши) плюс лайфхаки. Полный разбор «как из одной команды вырастает боевой скрипт» — в разделе 🐧 Linux → «Bash — скрипты и автоматизация».

BASH Структура скрипта 
#!/bin/bash
# !/bin/bash — шебанг, указывает какой интерпретатор использовать
# без этой строки скрипт может не запуститься

# Переменные:
NAME="world"
echo "Hello, $NAME"    # Hello, world
# $NAME — обращение к переменной

# Условия:
if [ -f файл.txt ]; then
    echo "файл существует"
else
    echo "файла нет"
fi
# -f — проверить что это файл
# -d — проверить что это папка
# -z — проверить что строка пустая

# Цикл:
for i in 1 2 3; do
    echo "Число: $i"
done

# Запуск скрипта:
chmod +x script.sh     # дать права на выполнение
./script.sh            # запустить
QUOTES Кавычки и апострофы — не путать 
"двойные"   — bash ПОДСТАВЛЯЕТ переменные и $( ):  echo "$USER" → kirill
'одинарные' — всё БУКВАЛЬНО, $ не трогается:        echo '$USER' → $USER
`обратные`  — старый аналог $( ); НЕ используй, легко спутать с ' — пиши $( )

# Спецсимволы ($ ! @ \) — только в ОДИНАРНЫХ, иначе bash их съест:
echo "P@$$w0rd"   # $$ = PID процесса → строка испорчена
echo 'P@$$w0rd'   # символ в символ — как надо
# " и ' — это РАЗНЫЕ режимы, не взаимозаменяемы.
BRACKETS Скобки: круглые / квадратные / фигурные 
$( ... )   выполнить команду, подставить РЕЗУЛЬТАТ:  D=$(date +%F)
${ ... }   явные границы имени переменной:           echo "${NAME}_bak"
( ... )    подоболочка (отдельный процесс) / при объявлении функции f()
{ ...; }   группа команд в ТЕКУЩЕЙ оболочке / тело функции (пробелы и ; нужны)
[ ... ]    тест-условие (это команда test!):  if [ -f файл ]; then
[[ ... ]]  продвинутый тест bash: умеет && || и =~ (regex)
(( ... ))  арифметика:  (( i++ )) ,  if (( a > b ))

# НЕ ПУТАТЬ:
#  ( ) подоболочка  ≠  { } та же оболочка
#  [ ] тест         ≠  { } блок команд
#  $(...) команда   ≠  ${...} переменная
OPERATORS Операторы и разделители 
;     разделитель: команды по очереди, независимо друг от друга
&&    "И":   следующее ТОЛЬКО если предыдущее успешно (код 0)
||    "ИЛИ": следующее ТОЛЬКО если предыдущее упало (код ≠ 0)
&     отправить команду в ФОН (не ждать её завершения)
|     пайп: stdout левой команды → stdin правой:  ps aux | grep nginx
>     перенаправить вывод в файл — ЗАТЕРЕТЬ
>>    перенаправить вывод в файл — ДОПИСАТЬ (для логов!)
2>&1  направить ошибки (stderr) туда же, куда обычный вывод (stdout)

# НЕ ПУТАТЬ:
#  &  (фон)      ≠  &&  (логическое И)
#  |  (пайп)     ≠  ||  (логическое ИЛИ)
#  >  (затереть) ≠  >>  (дописать)
BACKSLASH Обратный слеш \ — перенос и экранирование 
# 1) В КОНЦЕ строки — перенос длинной команды на несколько строк:
cmd1 \
  && cmd2 \
  && cmd3            # bash склеит всё в одну команду
# ⚠️ после \ НЕ должно быть ни пробела, ни таба — только конец строки,
#    иначе \ экранирует пробел, а не перенос — и команда развалится.

# 2) Перед символом — экранировать (снять спецсмысл):
echo "цена 5\$"      # \$ = просто доллар, а не начало переменной
cd my\ file          # \(пробел) = пробел внутри имени файла
grep "\." file       # \. = точка как символ, а не "любой символ"
LIFEHACKS Лайфхаки — проверка и защита 
set -euo pipefail        # первые строки взрослого скрипта: падать честно
bash -n script.sh        # проверить СИНТАКСИС, ничего не запуская
bash -x script.sh        # трассировка: печатает каждую команду перед запуском
shellcheck script.sh     # ⭐ линтер: ловит кучу багов и опечаток ДО запуска

"$var"                   # ВСЕГДА бери переменные в кавычки — спасает от пробелов
${VAR:-default}          # подставить default, если VAR пустая/не задана
${#var}                  # длина строки в переменной
cmd && echo OK || echo FAIL   # быстрый одноразовый итог прямо в терминале
mkdir -p a/b/c           # -p создаёт всю цепочку папок и не ругается, если есть
!!                       # повторить прошлую команду целиком:  sudo !!

EDIT Правильная правка чужого юнита 
# НЕ редактируй файл в /usr/lib/systemd/system/ напрямую —
# при обновлении пакета он будет затёрт.

# Вместо этого — override:
sudo systemctl edit nginx
# откроет редактор, сохрани туда ТОЛЬКО изменения:
# [Service]
# Restart=on-failure
# RestartSec=2

# Override сохранится в /etc/systemd/system/nginx.service.d/override.conf
# и automatic daemon-reload + рестарт сервиса.
# Изменения переживут обновление пакета.
TIMER systemd-timer как замена cron 
# Современная альтернатива cron'у — пара юнитов:
# /etc/systemd/system/backup.service — что запускать (Type=oneshot)
# /etc/systemd/system/backup.timer   — когда запускать

# backup.timer:
[Unit]
Description=Daily backup

[Timer]
OnCalendar=*-*-* 02:00:00    # каждый день в 2:00
Persistent=true              # если машина была выключена — догнать запуск
Unit=backup.service

[Install]
WantedBy=timers.target

# Преимущества над cron:
# + Логи в journalctl (cron логирует в /var/log/cron, не везде удобно)
# + Persistent=true — догон пропущенных запусков (cron этого не умеет)
# + Зависимости через After=/Requires=
# + Случайный сдвиг через RandomizedDelaySec= (распределить нагрузку)

# Управление:
sudo systemctl enable --now backup.timer
systemctl list-timers           # увидеть все таймеры с next-trigger
journalctl -u backup.service    # логи прошлых запусков
DOCKER Стек docker-compose под systemd (паттерн) 
# Зачем: автозапуск стека при перезагрузке сервера +
#        автоматический рестарт при падении + единый журнал.

# /etc/systemd/system/myapp.service:
[Unit]
Description=My App Stack
After=docker.service network-online.target
Requires=docker.service

[Service]
Type=simple
WorkingDirectory=/opt/myapp
ExecStart=/usr/bin/docker compose up
ExecStop=/usr/bin/docker compose down
Restart=on-failure
RestartSec=5
User=appuser           # ⭐ НЕ root, иначе файлы данных будут root:root

[Install]
WantedBy=multi-user.target

# Деплой:
sudo systemctl daemon-reload
sudo systemctl enable --now myapp
Главное правило прода: любой сервис должен (1) запускаться через systemd-юнит с Restart=on-failure, (2) логировать в journal (просто пиши в stdout/stderr), (3) обрабатывать SIGTERM для корректного завершения. Без этих трёх — сервис нельзя считать прод-готовым.

LIMIT 10;

WHERE state != 'idle';

FROM pg_stat_user_tables

SELECT pg_size_pretty(pg_database_size('portfolio'));

-- Статистика использования индексов:

NULL — заражает всё

SQL Как NULL ведёт себя в выражениях 
SELECT 1 + NULL;           -- результат: NULL (не 1, не ошибка — именно NULL)
SELECT 'text' || NULL;     -- результат: NULL
SELECT COUNT(notes) FROM topics;  -- не считает строки где notes = NULL
SELECT COUNT(*) FROM topics;      -- считает ВСЕ строки включая NULL

-- NULL "заражает" всё к чему прикасается
-- Любая операция с NULL = NULL

-- COALESCE — спасение от NULL:
SELECT name, COALESCE(notes, 'нет заметок') FROM topics;
-- если notes = NULL → вернёт 'нет заметок'
-- если notes = 'текст' → вернёт 'текст'

-- NULLIF — обратное: вернуть NULL если значение равно чему-то:
SELECT NULLIF(progress, 0) FROM topics;
-- если progress = 0 → вернёт NULL
-- удобно чтобы не делить на ноль
